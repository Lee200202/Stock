## 二、流程如何改

1. 讀取本次原文，保留原文指紋核對與選列紀錄。
2. 擷取、分類、補漏、盤勢、教學共同送 JSON。新增 `price_subject` 表明價位所屬公司；只附本批原文出現的確認別名，降低輸入體積。
3. 既有全文 `context-review` 同時處理漏股、主詞錯接、價位歸屬、持股與未持有人指示。沒有為每檔新增一次 API 呼叫。
4. 官方代號核對後，再處理日期歸屬。純過去成交不因日期不明就變成今天買賣；法人反覆交易也不放進會員成交歷史。
5. 寫入前檢查跨股數字、保留明確現有持股、統一觀望語氣；公開文字做正式名稱與代號整理。
6. 前一版沿用的列也清理公開文字，但保留「沿用待複核」狀態。無法證明的資料不宣稱已驗證。
7. 最終 JSON 產生六章文章；GAS 郵件重建與前端個股／持股表使用相同公開文字處理。
8. 內容更新後印 Gemini 用量，日 K／績效接續在同一個 Actions 執行的後半段處理。缺 K 自動補、保存進度及續跑；等待不偽裝成全部成功。

長原文仍按完整請求預算分批，不依賴模型跨 API 呼叫的記憶。覆核仍沿用既有次數上限，篇幅不足可短並留稽核；不捏造價位或展望湊字數。這次沒有提高預設 thinking level，兩端維持 `medium`。

現有進度「價位校對」說明已修正為原句及公司歸屬核對；不再聲稱此時完成了日 K 驗證。正式行情驗證與績效仍依背景資料就緒狀況處理。

## 三、哪些檔案放進 Apps Script

**`apps-script` 中目前 27 個檔案全部需要，放入同一個原 Apps Script 專案。** 不需要另建試算表。這版沒有新增第28個檔案；若較舊雲端版本缺少 `Presentationquality.gs` 或 `Transcriptstore.gs`，必須補上。

| 類型 | 檔案 |
| --- | --- |
| 指令碼，19個 | Adminpipeline.gs、Adminservice.gs、Aiservice.gs、API.gs、Articlequality.gs、Cachebuilder.gs、Cmoney.gs、Code.gs、Config.gs、DB.gs、Evidencequality.gs、Logic.gs、MailService.gs、Presentationquality.gs、Quoteservice.gs、Refreshrunner.gs、Setup.gs、SheetService.gs、Transcriptstore.gs |
| HTML，8個 | Admin.html、Changelog.html、Index.html、JavaScript.html、Settings.html、Stylesheet.html、Tech.html、Unsubscribed.html |

不要把 Python、requirements、README、AGENTS、tests、docs、scripts、backups 或 ZIP 上傳為 GAS 程式碼。雲端既有 `appsscript.json` 保留；不要另存帶有相同全域函式的備份 `.gs`。

相對於目前 v9，GAS 實際修改7個：Adminpipeline、Adminservice、Articlequality、Config、Evidencequality、JavaScript、Presentationquality。為避免先前版本缺檔或混版，部署時仍建議核對全部27個。

## 四、詳細部署順序

1. 等正在執行的投稿工單結束。備份雲端程式與試算表，保留原專案、試算表 ID、訂閱者與部署網址。解壓 `release/zhangzhen-quality-v10.zip`；不要拿舊版 ZIP 覆蓋本版。
2. 開啟原 Google Apps Script 專案，按名稱更新上述19個指令碼。缺檔時選左側「＋→指令碼」，輸入不含 `.gs` 的名称，例如 `Presentationquality`，再貼完整內容。原有 `Code.gs` 也用目前短版更新，避免保留舊版內嵌函式。
3. 八個 `.html` 選「＋→HTML」建立或更新。例如 `JavaScript.html` 要用 HTML 類型，內容雖是 JavaScript 仍不能建成 `.gs`；`Stylesheet.html` 同理。儲存所有檔案。
4. 上方函式下拉選 `checkSetup`，按執行、完成授權、閱讀執行紀錄。這支是設定與分頁筆數檢查，不是完整 API 測試；不會呼叫 Gemini 或寄信。若缺分頁，執行 `addMissingSheets` 後再檢查。既有分頁缺少尾端欄位會在正式程式的 `getSheet_` 首次讀取時補上；不要手動清掉表頭或重建資料。
5. 「專案設定→指令碼屬性」保留 `SPREADSHEET_ID`、`ADMIN_KEY`、既有 Gemini／Fugle 金鑰及 `GITHUB_REPO`、`GITHUB_TOKEN`、`GITHUB_WORKFLOW`、`GITHUB_REF`。GAS 模型由 `Aiservice.gs` 的 `DEFAULT_MODEL` 提供；不能只加一個程式沒有讀取的 `GEMINI_MODEL` 屬性。
6. 確認 `GEMINI_THINKING_LEVEL=medium`，沒有設定也會使用 medium。若自行測 high，GitHub Variables 和 GAS 指令碼屬性要分別設定；high 不增加免費配額，也不能代替本版主詞與語氣防護。
7. 左側「觸發條件」核對 `everyFiveMinJob` 每5分鐘、`backfillDailyKJob` 約14:35，時區 Asia/Taipei。缺少才新增，不重複安裝。保留 GitHub 13:45 只補日 K 排程；不要為了更新這版直接執行會重建既有觸發器的 `installTriggers`。
8. 右上「部署→管理部署作業→選原網頁應用程式→鉛筆」。版本選「新版本」，說明填 `2026-09-13-quality-v10`，執行身分與既有存取範圍沿用，再按部署。使用原部署更新可以保留 `/exec` URL；若另建部署導致 URL 改變，必須同步 GitHub `APPS_SCRIPT_URL`。
9. 打開原部署網址加 `?action=ping`，確認回應 `build` 是 `2026-09-13-quality-v10`。只在編輯器儲存並不會更新原 `/exec` 執行版本；`/dev` 也不是 GitHub 應使用的正式網址。
10. GitHub 專案按 ZIP 相對路徑更新：根目錄 `pipeline.py`、`pipeline/pipeline.py` 兩份都更新；`.github/workflows/daily.yml`、兩份 requirements 也與本版核對。不要只把 ZIP 當單一檔案上傳，Actions 不會自動解壓。維護時正本是 `pipeline/pipeline.py`，修改後執行 `python scripts/sync_quality.py` 同步。
11. GitHub「Settings→Secrets and variables→Actions」：API 金鑰在 Secrets；Variables 的 `GEMINI_MODEL=gemini-3.5-flash-lite`、`GEMINI_THINKING_LEVEL=medium`。檢查 `GEMINI_MODEL_2` 等是否仍有舊模型覆寫。確認 GAS 的 `GITHUB_REF` 指向剛更新的分支。
12. Actions 選 `daily-transcript-pipeline`，按「Run workflow」，選同一分支，將 `check_keys` 設 `true`，其餘維持預設。這項會實際生成短回覆並消耗少量 Gemini 配額；確認金鑰、模型及 thinking 請求格式正常。
13. 開啟後台、強制重新整理。投稿9/10本次原文，勾「解鎖補登」與「覆蓋既有資料」，送出後核對原文 SHA256 是 `60d5901a9e651190ff0b749bb6c2d75931a804a47711503a7b3ad7ed3d7e8227`（只有完全相同原稿才應相同）。看到本版分類結果並核對完，再處理9/11。
14. **要套用新 Prompt，必須重新投稿原文。** 單按「續跑卡住的工單」只繼續舊檢查點，不能重做新分類；只有日 K 尚未補完時才用續跑，不要反覆重新投稿消耗 Gemini。
