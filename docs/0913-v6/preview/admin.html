版本沿革

  
這裡記錄從最初能動的版本到今天，每一次比較關鍵的調整，以及為什麼要改。

  

    

      
半份清單不再拿來猜代號、候選名單不再被歸進「不要碰」、資料修正可以看進度也可以取消（2026/09/10）

      
當天的表格上，台積電變成泰金-KY、萬海變成萬在、辛耘變成星雲、世芯-KY 與四星各自被配到力新。六檔全錯，可是每一欄都填滿了——名稱、代號、股價、K 線一應俱全，看起來完全正常，這種錯比留白難發現得多。

原因在對照表。載入時上市那一邊的兩個來源在同一天一起失效，只剩下櫃買的 887 檔，程式印了一行「兩邊沒有都載到，代號查核這一輪放寬」然後照跑。放寬的方向剛好相反：對不到的那些名字，正確答案本來就在沒載到的那一半裡，拿剩下的半份表去做拼音比對，只會在裡面挑一個最像的填進去。而拼音比對在這種情況下特別危險——辛耘與星雲兩個字完全同音，再怎麼調門檻都分不開，唯一能分開它們的是「表裡有沒有辛耘」。

現在改成三件事。一是表殘缺時不比、不猜、也不剔除：只留精確命中與去後綴命中，其餘一律留成代號待確認，「跟表裡每一檔都不像」這句話在半份表上不成立，不能用它刪東西。二是把來源補厚：上市多了證交所每日收盤行情、本益比殖利率表與 ISIN 公告，上櫃多了每日收盤行情與 ISIN，ISIN 是一張從沒改版過的 Big5 表格，留著當最後一道防線。三是每次成功載入就把清單存進「代號對照快取」分頁，來源全掛時拿昨天的頂著——名稱與代號一年也改不了幾檔，昨天的清單幾乎不會錯，拿半份清單硬猜則必定出事。

留白也要能自己好。收尾補代號那一步原本只掃「這次寫了哪幾天」，於是某天來源掛掉留下的待確認，隔天清單恢復了也不會被回頭處理，除非有人記得到後台按「重跑代號比對」。現在收尾一律掃全部歷史，而且發現手上的表是殘缺的就重新載入一次再比——擷取與收尾之間隔了好幾分鐘，來源多半已經恢復。掃全部只是多讀兩張分頁、在本機多算幾次相似度，不呼叫任何 API。

分類那邊修的是一個把意思弄反的錯。他有一個固定段落會把「我以後要買的」一次列出來：「這一支列在我的候選名單」「辛耘你們也可以抄起來」「我連後面要什麼聖暉、信紘科、家登還有牧德，通通列出來給你看了」。這一批被整批歸進「觀望不碰，語氣偏空，暫不進場」，字面上不算說錯（他確實說了現在還不買），意思卻整個反了——讀的人會把他當天最想買的名單當成地雷。現在「現在不要買」與「現在還沒買」分開判斷：前者是他叫你別碰（不准碰、追高、還沒跌完、一定會殺破），後者是他自己想買、只是在等時機。候選名單一律歸觀望注意，「等洗完再買」是條件不是否定。順帶補上兩條：拿來示範「外資一天買一天賣」「ETF 追高殺低」的那幾檔（華邦電、群創、聯電、廣達）不收，那一段的主詞是行情不是個股；回顧「上禮拜一我叫你 597 賣國巨」時，597 是那一天的指示，不可以填進今天的價位說明。

刷新鏈上還有一個與程式無關的坑。Apps Script 的網頁應用程式會先轉到 googleusercontent 再吐內容，那一層偶爾回 404 加一頁 Google 的錯誤頁，隔十秒再打就好了。先前只有補日K那一步會重試，其他步驟收到就當失敗，而且一失敗整條鏈收工——那天第一步「清除產業列」中了，於是代號、基本面、日K、持股追蹤、績效全部沒跑，網站停在前一天，成功 0 步失敗 1 步。現在每一步都會重試三次（真正的 doGet 例外除外，那種重試只是白等），而且單一步驟失敗不再整條收工，只有連續三步都失敗才停——那才代表下游是真的壞了。

最新會員操作通知也修掉一個會誤導的退讓。它原本一律對齊每日總覽那一天，總覽已經是今天、但今天還沒有簡訊時，它會安靜地退回顯示昨天那一則，畫面上沒有任何地方寫著那是昨天的。現在永遠顯示最新的一則，日期寫在標題上，並且講清楚它與總覽的關係——早一天、晚一天還是同一天。講清楚永遠比對齊安全，因為退讓出來的那一筆看起來與正常內容一模一樣。

四、HTTP 503 的原文寫著 high demand … usually temporary，是「這一刻服務忙」，不是「這把金鑰不能用」。先前把它算成失敗，那把金鑰就被標記成不可用、整輪跳過——明明只是那一秒鐘塞車，卻讓一把好金鑰整天不能用。現在 5xx 一律視為暫時性，保留該金鑰。

壞掉的金鑰不再中斷流程、沒有個股操作的日子不再算失敗（2026/09/09）

      
上一版加了多把金鑰輪替，但只處理了「額度用完」這一種換手理由，於是換到第二把之後，只要那一把設定有問題就整個工單當場結束：日誌上是「Gemini 呼叫失敗（polish 2/3）：HTTP 404」，退出碼 1，而第 1 段已經潤飾好的結果也一起丟掉，下一輪要從抓逐字稿重來。404 的意思其實很具體——那一把金鑰所屬的 Google 專案看不到 gemini-2.5-flash，多半是沒有啟用 Generative Language API，或那個專案還沒有這個模型的存取權；403 是沒權限或 API 被停用，400 是金鑰貼錯。這三種都是「這一把的問題」，換一把就能繼續，跟額度用完該做的事完全一樣，先前卻走了截然不同的路。現在 400、403、404 會先判斷是不是金鑰層級的問題，是的話把那一把標記為不可用並換下一把，全部都不能用時才失敗，而且訊息會指名是第幾把、哪一個環境變數、要去修什麼，不再只有一句 HTTP 404。金鑰內容本身不會出現在訊息裡。另外每一輪開跑前會先用「列出模型」問一次每一把金鑰能不能用（只查詢不生成，不算生成配額），設定錯的那一把在第一步就被標出來並跳過，不必等到流程跑到一半、第一把額度用完之後才爆——那是最不希望出事的時間點。潤飾那一段也補上：先前只有配額不足會降級成原文，呼叫失敗仍會往外拋，現在金鑰層級的失敗一樣降級，整份逐字稿不會因為第二段失敗就全部丟掉；但 MAX_TOKENS 這種「該去調切塊大小」的錯誤照舊往外拋，不會被降級藏起來。金鑰全部不可用之後的呼叫改成秒回，不再讓每一段都把六輪退避重跑一次。金鑰的解析也放寬了：GEMINI_API_KEYS 現在同時吃逗號與換行，一行一把是最自然的貼法，先前只切逗號，整段連同換行會被當成一把很長的金鑰送出去，換來一個看不懂的 404；不像金鑰的內容會被擋下並示警。

另一件是後台投稿逐字稿停在「撰稿（10/14）：找不到 2026/09/09 的結構化紀錄」。撰稿要讀回操作紀錄與會員持股裡那一天的列，一列都沒有時就拋錯，但零筆其實有三種完全不同的成因，只有一種是真的壞掉。第一種是買賣被改記到前一個交易日——他很常在今天的直播回頭講「昨天收盤後我做了什麼」，那幾筆本來就該記在昨天，整份逐字稿都在回顧昨天時，今天這一天就真的一列都沒有，但資料完好。第二種是那天本來就沒有指名任何一檔個股，只有大盤看法與心理喊話；擷取端的規則是「不指名就不要生」，所以零筆是正確結果，上游 pipeline.py 這種日子照樣會產生文章。第三種才是資料真的沒寫進去。現在三種分開處理：前兩種寫一篇說明並繼續往重算走，第一種還會順便把被改記的那幾天的文章一起重寫（不然那天的信與網站會永久對不起來），只有連逐字稿都找不到時才拋錯。這件事的代價不只是那一則錯誤訊息：工單停在撰稿，後面的重算A／B／C 全部不做，即使前面六步都成功了，那天的資料也永遠進不了持股追蹤與績效。順帶把「該怎麼修」補上這一條，先前它落到「沒有對應的已知處理方式」，等於沒講。

    

    

      
會員簡訊：解析版本戳記、範圍分流與配額熔斷（2026/09/09）

      
兩件事同時壞掉，而且互相餵養。第一件：抓文章的時候會先在解析明細欄塞一個 '[]' 佔位字串，於是「還沒判定過」與「判定過、真的沒有個股」在資料上長得一模一樣。併入過去資料那一步把佔位的 '[]' 讀成有效的空結果，一次 Gemini 都沒呼叫就把該列標成「已解析（無可收錄，稽核通過）」——9/7 那篇「手中持有1519華城，請於775元以上全數獲利賣出」就是這樣被判成無可收錄的，收錄個股欄一片空白，而狀態卻寫著稽核通過，看起來像是已經檢查過沒東西。第二件：挑選待處理列的條件把「無可收錄」也算成未解決，所以每一次執行都會把整個歷史裡所有沒有個股的純盤勢文章重新丟給模型判一次；每日排程一天有十幾個觸發點，Apps Script 那邊還有一個每十分鐘看一次待解析列的自動派工，而待解析列因為每次撞到 429 就整批回滾、狀態永遠停在待解析，於是自動派工每十幾分鐘就再發一個工單，工作清單上排滿「會員簡訊 SMS-…」，每一個都跑十四分鐘、每一個都在同一篇文章上撞牆、一列都沒寫進去。免費層的每日請求數在中午前就見底，接著當天的逐字稿擷取就會拿到「Gemini 配額用盡（extract）：HTTP 429」——那句錯誤的來源其實在這裡，不在逐字稿那條線。

處理方式是把「判定過了沒有」變成一件可以確定回答的事：新增解析版本欄，只有模型真的判定過才寫值。空白代表從未判定，等於現行版本代表判定過（收錄零筆也算判定過，不再重跑），不等於代表舊提示詞判定過、只有明確按重新解析才會重來。抓取與排回待解析時一律寫空白而不是 '[]'，文章被修訂時連版本一起清掉。工作也照範圍拆開：只更新當天（新簡訊進來時用，配額用量最小，每日排程與自動派工都改用這一種）、併入過去資料（掃全歷史但只補收錄個股仍空白的，已判定過的一次模型都不呼叫）、重新解析（強制重判，最耗配額）。寫入改成邊做邊落地，不需要模型的列先做完先寫進試算表，撞到配額時已完成的部分留著不回滾。429 分成每分鐘與每日兩種：每分鐘退避有意義，每日則立刻熔斷，同一輪之後所有呼叫直接拋例外連請求都不發，並算出太平洋時間午夜換算的重置時刻回報給後台，後台在那之前擋下派工並告訴使用者什麼時候可以再按。自動派工另外加了每日次數上限，真的壞掉時會安靜下來等人處理，而不是用整天的額度重複同一個失敗。pipeline 也補上多把金鑰輪替（GEMINI_API_KEY_2 到 _5，或逗號寫在 GEMINI_API_KEYS），與 Apps Script 那邊同一套命名——先前只有後台支援，同樣是額度問題，後台還能跑而 GitHub 這條整天停擺。

另外兩件：併入過去資料整段從一格擴成十三格，全部排在逐日稽核之後，先把哪一天有幾篇、幾篇還沒收錄個股盤點清楚再動資料，卡住時看得出卡在哪一段；以及把全站重算從這條鏈上拿掉。清產業列、代號比對、更新基本面、補齊日K、重算持股追蹤、記錄績效與這一篇簡訊收錄到哪些個股是兩件事，綁在一起會讓更新一筆簡訊要等一次全站重算，補齊日K一次就能跑十幾分鐘，而且中間任一步失敗會把已經寫好的簡訊資料一起判成失敗。需要讓網站跟著更新時，資料寫完後到網站內容按一次刷新即可。解析提示詞也依實際簡訊補強：換股句（賣出A、資金轉為買進B）要開兩筆、除權息金額與會員歷史成本與大盤點數都不可以當價位、耐心等待某價再找賣點屬於觀望注意而不是賣出。

補回會員持股聲明這條開倉路徑

      
前一版把開倉條件收緊成「只認明講買入」，解決了觀望不碰混進會員持股的問題，但也連帶擋掉一種真實情況：張震有時不會重述當初的買入動作，只在盤中複述一次會員手上有什麼。這類標的會出現在每日推播的「影片中明講之會員目前持有股票」那一段，網站卻看不到，兩邊對不起來。現在把它補成第二條開倉路徑，並加上一道防呆：同一天若同時出現持有聲明與觀望不碰或賣出，該筆聲明不予採信，避免舊問題重演。由持有聲明開倉的回合，進場價一律取當日收盤而非明講價，因為那天並沒有成交，介面上會用一個橘色的「持」字標記，個股面板另有一列「進場依據」寫明這件事。持股追蹤分頁新增首次進場方式與本回合進場方式兩欄。

    

    

      
持有聲明加上三個交易日的確認

      
用持有聲明開倉有一個先天弱點：只需要一句話就能成立，而逐字稿是語音辨識的產物，偶爾會把某個詞誤判成股票名稱。這種雜訊一旦出現，就會在追蹤表裡留下一個永久的假部位。現在由持有聲明開倉的部位要多過一關：開倉後三個交易日內必須至少再被提到一次，任何形式都算，期限內完全沒有後續的整個回合直接移除，當作沒發生過而不是標記為已出場。移除只針對未經確認的持有回合，同一檔若後來真的講了買入，那一段仍會保留。實作上特別區分了「確認期還沒過完」與「確認期過了但沒有後續」兩種狀態：昨天才講的持股會標為待確認並暫時保留，否則最新的持股會在隔天的重算裡被誤刪，這條路徑等於永遠留不住東西。交易日曆是從日K快取推出來的，快取落後時可用交易日不足，所有持有聲明會停在待確認而不會被誤刪。另外新增乾跑函式，可在套用前先列出會被移除的名單。

    

    

      
條件價改以觸價日成交

      
修正一個會讓報酬算錯的定價錯誤。張震很常講的不是當下成交價，而是「漲到某價位以上就賣」「跌到某價位以下才買」這類條件價，而條件價在發話當天必然還沒到價。先前系統一律拿發話當天的最高與最低去驗證，落在區間外就判定不合理、退回當日收盤，等於把他明確講過的價位丟掉，換成一個他從沒提過的數字。現在會先分辨那個數字是成交價還是條件價，是條件價就往後找第一個真正觸價的交易日，那天才是成交日，成交價就用他講的那個價位；六十個交易日內都沒觸價才退回收盤並註明條件未成立。往後找之前仍會先確認該數字對這一檔而言合不合理，離歷史區間超過三成的直接捨棄，避免被誤抓的營收金額在未來某天剛好等於股價而被誤採。成交日與發話日不同時，回合明細與進場價來源都會標出觸價日期。價位解析同時擴及說明重點欄，因為他常常不在價位欄講價而是在說明裡帶過一句；並補上方向一致性檢查，方向是買入而內容只描述賣出時，那個數字不會被當成這一筆的成本。

    

    

      
後台接回上游的完整流程

      
後台第一版只做潤飾、擷取、寫入、重算四步，把上游最重要的三道把關全跳過了：完整性稽核、代號比對、價位校對。同一份逐字稿走兩條路進來品質差很多，分類會亂、名稱對不到代號、價位說明與操作方向互相矛盾。現在補齊成十個步驟與上游一致，三段提示語逐字元搬過來完全相同。過程中發現一個容易忽略的坑：系統提示語搬對了，但送進去的使用者輸入是另外寫的，產出還是不一樣——上游在撰稿輸入的開頭有一句「唯一資料來源、禁止列入清單以外的股票、禁止改動代號」的框限，那是防幻覺的主要機制，少了它模型會自己補股票或改代號，於是信件與網站對不起來。現在連輸入格式一起對齊。另補上輸出被截斷時自動用精簡指示重生一次的容錯，否則個股多的那幾天信會缺一大段而且毫無徵兆。代號比對的同音修正在此環境沒有拼音函式庫可用，改以候選清單加語言模型判定，候選一律來自真實股票清單，模型只能選或回答沒有，回傳的代號還要真的存在於對照表才採用。

    

    

      
配額上限與批次呼叫

      
工單常在擷取或撰稿失敗，訊息只有一行 HTTP 429。查出兩個原因疊在一起，而第二個才是主因。其一是退避太短：重試只等 0、1.5、4 秒共約五秒半就放棄，但那是每分鐘配額用盡，額度要到下一分鐘才回補，等五秒必然還是滿的；現在拉長到最多約兩分鐘，跨過重置邊界，伺服器若指定了建議等待秒數則以它為準。其二是把請求發成了散彈：同音判定與價位校對原本逐檔各發一次，一天二三十檔就是二三十次連續呼叫，自己把配額打爆；現在兩者都改成一次批次請求，並在連續呼叫之間強制留間隔。錯誤訊息也重寫，原本只回一行狀態碼，看不出是每分鐘請求數爆掉、當日額度用完還是金鑰失效，而這三種處理方式完全不同；現在會帶出伺服器講的原因（並先遮掉可能夾帶的金鑰片段）並附上對應步驟。

    

    

      
價位改為雙向搜尋

      
修正一個會讓報酬算錯且從表面看不出來的缺陷。講者講價位有兩種時態：未來式是條件價要往後等觸發，過去式是回述成本要往前找。先前只往後找，於是所有回述成本的講法必然找不到，被當成條件沒成立而退回當日收盤，等於把明確講過的價格丟掉換成他從沒提過的數字。實際發生過某檔講的是舊成本、系統卻用了當天高出許多的收盤價。現在兩邊都找，取離發話日較近的那一天；往後保留六十個交易日上限因為條件價等太久失去意義，往前不設限因為既成事實沒有過期問題。若整段快取都沒碰到但數字仍在該檔歷史區間的合理範圍內，改為採用明講價並註明查無觸價紀錄，因為那多半是日K快取沒涵蓋到那一段，用收盤取代只會把錯誤藏起來。另外持有聲明開倉的回合，若後續講到價位會改用那個價位，先前一律取當日收盤。

    

    

      
分段執行與進度呈現

      
解決重算走到一半卡住不動的問題。執行環境對單次執行有時間上限，超過時不是拋出例外而是整個執行被直接中斷——這個差別很關鍵：拋例外還能被接住、記錄、排下一棒，被中斷則什麼都來不及做，於是進度沒寫回、下一棒沒排，工作停在原地且沒有任何錯誤訊息。全站重算要做六件事，其中更新基本面與補日K是對外抓資料，整包遠超過上限。現在每一小段開始前記下截止時間，做完一件事就檢查剩餘額度，不足就把進度寫回並交棒，下次接著做，不論外部服務多慢都會持續前進。同一套機制用在投稿工單、整理過去資料與立即刷新三個作業上，三者共用同一套進度呈現，都可以關掉頁面回來再看。立即刷新原本是同步跑完，前端要乾等一到兩分鐘且常常超過網頁等待上限而顯示連線失敗，實際上後端還在跑，改成分段後這個誤判就消失了。失敗時另外顯示處理指引，把常見失敗形態翻成具體下一步，其中配額上限特別區分每分鐘與每日兩種，因為前者等兩分鐘就好而後者要等到隔天。

    

    

      
題材剔除、累積報酬與整理舊資料

      
名稱判定補上題材與族群的剔除規則。先前出現過把一整串盤面題材當成一檔股票寫進表裡的情況，那類字串通常用頓號或「加」把兩三個主題串在一起，而台股沒有任何官方簡稱含這些符號；另外也擋掉常見的族群用詞。同一檔買了又賣、賣了又買時，各回合報酬改以連乘計算累積報酬並顯示在表格與個股面板——用連乘而不是相加，因為那才是同一筆錢滾過每一回合的真實結果，相加會把漲五成再跌五成算成打平，實際上是虧了四分之一。另新增整理過去資料的工具：規則更新只會套用在之後新進的資料上，先前寫進去的不會自己變好，這支拿新規則回頭把舊資料掃一遍，並提供只讀不寫的預覽讓人先確認要刪的確實都不是個股。逐列處理時由後往前掃並把刪除集中在最後執行，避免中途列號位移刪錯列。投稿的影片網址也改為選填，偵測不到時不必先去找網址才能貼逐字稿。

    

    

      
新增後台手動投稿

      
上游依賴的登入憑證過期時，重新產生需要一台能開瀏覽器的電腦，人在外面只有手機就整條線卡住。新增後台作為第二條路：用手機把逐字稿從 App 複製出來貼進去送出，後面的潤飾、擷取、分類、代號比對、股價更新全部照原流程跑完，兩條路產出的資料格式一致、寫進同樣的分頁、收斂到同一次全站重算。入口是網址加上參數，開啟後只有登入框，內容都要通過管理密鑰驗證才拿得到，用的是與立即刷新同一組密鑰。為了不必自己找網址，系統從台灣時間 11:30 起每 10 分鐘偵測一次當天影片，抓到就列在後台按一下帶入。送出後採非同步處理：先存原文與建立工單就回覆，真正的工作由觸發器一步一步做，每次只做一小段，因為單次執行有時間上限而完整處理遠超過它；中途失敗會停在該步驟並記錄原因，可以續跑不必整份重來，原文在最開始就先落地所以不必重貼。日期預設今天且鎖住，需要補登才解鎖並二次確認；同一支影片重複送出需另外勾選覆蓋。另外評估了用雲端執行環境代替本機取得憑證的可行性，結論是機房位址會觸發風險檢查、需要互動式圖形介面、環境是暫時的、且自動化登入有合規疑慮，因此不採用。

    

    

      
登入憑證續命與執行前探測

      
解決登入狀態時好時壞的結構性問題。這類憑證會被伺服器輪換，用戶端本來應該把新的存起來下次接續使用，但在自動化環境裡憑證每次都從設定值還原成暫存檔、工作結束就消失，輪換後的新憑證從未被保存，於是每次都拿著同一份越來越舊的憑證去敲門，落在伺服器的寬限期內就時好時壞。現在改成執行開始時先取出上次保存的最新憑證，結束時若偵測到輪換就存回試算表，設定值裡那份從此只是第一次用的種子。存放位置選試算表而非設定值，是為了不必額外申請可寫入設定的存取權杖；代價是該試算表必須維持私有，程式會在自動建立的分頁裡寫上這段提醒。另外新增執行前探測：每個觸發點先只用影片清單與試算表判斷有沒有事情要做，不碰逐字稿服務、不呼叫語言模型、不需要憑證，幾秒就有結果。直播進行中或當日已處理完成的觸發點直接結束，不再空轉二十幾分鐘。但只跳過確定不可能有影片的時段，等待窗一開始仍照常進去輪詢，以免把內部輪詢的設計廢掉。

    

    

      
外國股票不再寫入，登入到期改為事前預警

      
講者常拿美股當台股的風向球講，先前這些公司會被擷取進操作紀錄，因為對不到台股代號而留成代號待確認，並顯示在網站上。現在分三層擋掉：擷取提示明確要求不收外國公司並說明那只是行情背景；比對代號之前先查一份外國股票名單，命中就整列剔除，而且這一步必須排在相似度比對之前，否則這些正常的中文詞會被硬湊到拼音相近的台股上，那比留成待確認更糟；完整性稽核的提示也註明外國公司不算漏抓，避免剛擋掉又被補回來。名單設計上避開了與台股撞名的寫法，比對時還會再確認官方清單，名稱能精確對上台股就以台股為準，不會誤刪。同時剔除單字名稱，台股沒有單字簡稱，那是語音辨識切錯的碎片，而單字比拼音很容易湊出虛假高分。另外新增登入憑證的到期預警：流程開始前先讀憑證裡的到期時間，剩不到三天就發出警告，過期則直接標成錯誤，不必再等排程失敗才發現。

    

    

      
英文名稱個股與登入失效的處理

      
代號比對修正一個會誤刪個股的規則。原本有一條「名稱不含中文就剔除」，用意是擋掉 HBM、CoWoS 這類產業縮寫，但它會連帶殺掉官方簡稱本來就是英文的那幾檔 KY 股，實際發生過逐字稿寫成某個英文縮寫、比對階段整列被剔除的情形。現在在剔除規則之前先跑一次英文名稱比對，候選只取官方簡稱同樣不含中文的個股，並同時比對完整字母骨架與去掉 KY 後的字根，比不中才走原本的剔除邏輯，所以真正的產業縮寫仍然會被擋下來。另外，上游偵測登入失效的判斷式補上了實際會出現的錯誤形狀。先前這類錯誤沒被認出來，被當成一般失敗，於是輪詢迴圈每三分鐘重敲一次、一路敲到時間預算用完，而每一次都必然失敗。現在認出來就立刻停止並標記為認證過期；另外加了一道保險，同一個錯誤連續數次就中止輪詢，不再空轉。

    

    

      
買了又賣、賣了又買的呈現

      
同一檔股票賣掉後再買回來，舊版用一組固定的首次買入日與最近賣出日描述，會同時錯三個地方：進場價停留在第一次買入的價格、持有天數把中間沒有持有的空窗期也算進去、狀態欄在持有中與已出場之間互相蓋掉。現在改用回合模型，把每一檔的紀錄依時間切成數個回合，表格與首頁顯示最新那一個回合，進場價、持有天數與報酬全部從本回合進場日起算，過去的回合保留在回合明細裡逐條列出。狀態欄在回合數大於一時會標出目前是第幾回合，個股面板也會多出一塊持有回合的區塊。

    

    

      
價位說明校對與參考價位

      
針對價位說明的三類系統性錯誤新增校對流程：方向欄與價位內容互相矛盾、把營收或成交量這類非股價數字誤當價位、以及把概數當成精確成本。流程分兩層，第一層是純規則快篩不呼叫 AI，乾淨的列零成本通過；只有可疑的列才送 AI，並附上該檔當天的日K高低價當硬性驗證依據，AI 回傳的數字還要由程式再對一次區間才會採用，偏離超過三成一律清為未說明。原則是留未說明永遠好過填一個編出來的數字。另外，若首次買入沒有說明價位、但後續以觀望注意的語氣提到價格，會抓出來以參考價位的身分標註在表格與個股面板，與明講成交價的標記在顏色與意義上分開，且不列入報酬計算。

    

    

      
版面修正、日曆共用與一次到底的手動流程

      
修正價位說明欄敘述一長就會壓過右邊說明重點、兩欄文字疊在一起的問題。成因有三個且缺一不可：該欄原本沿用不換行的價格欄樣式、固定版面下內容不會撐開欄位而是直接溢出、以及沒有溢位限制，因此三個都處理，改用可換行的專屬樣式並放寬欄寬，兩欄之間補上分隔線。日曆改為置中滿版並抽成共用元件，郵件查詢與每日總覽的「翻到某一天」使用同一份程式與樣式，後者原本的日期輸入框已改為日曆，且只有真的有紀錄的日期才點得下去，不必先點下去才發現那天沒東西。每日推播與郵件查詢不再附結構化對照表，該表與網站內容重複，只是讓信變得冗長。手動流程新增價位校對模式，以及跑完立刻刷新網站的開關，可與任一模式同勾或單獨使用，讓資料整理與畫面更新一次到底。

    

    

      
品質關卡：稽核補漏、內容複審、漏抓判定

      
擷取只回答「有沒有提到這一檔」，那不夠。實際跑下來有兩種系統性錯誤，都在寄信前補上一道關卡處理。一是多抓：講者一小時裡有大量內容是拿以前的單子講道理，例如漢唐「我跌停有賣嗎？沒有啊，是等上來到黑K棒上緣才賣的」、索羅門「這支我已經沒了，我都賺錢賣」，那是教學，是完結的舊事，進了表格會讓網站顯示他在操作一檔早就出清的股票，持股追蹤還會開一個不存在的回合。新增的內容複審逐筆拿逐字稿回頭核對，純粹回顧舊單的整列刪掉，買入賣出若看不到「今天、剛剛、這個盤中」實際執行就退回觀望兩類或會員持股；沒把握的一律不動，單日刪除超過七成整批不刪，每一筆刪除都寫進修正建議留痕。二是誤報漏抓：稽核那一段刻意設計成高召回，寧可多列也不要漏，它的輸出本來就不該直接給人看，卻被原樣寫進狀態信，於是每天列出一批像台塑、台化、陽明、大立光這種其實是講集團、講族群、拿來當對照時順帶點名的名字。現在改成先經過漏抓判定：把逐字稿前後文一起送進去，逐筆判定該不該進表格，並把不收的原因分成集團順帶點名、族群舉例、對照比喻、回顧舊單、只有報價、看不出在講什麼六類；信裡呈現的是判定後的結論，不再是候選清單。關卡跑完才寄信，所以訂閱者收到的就是複審後的版本，先前那封每天都來、卻要人自己到 GitHub 重跑的稽核信也一併取消。過去的資料由後台「全面重整」套用同一套規則，一天一天把稽核與複審整套跑過，一加一減都做——只跑複審的話當初漏掉的永遠漏著，只跑稽核的話當初誤收的永遠留著。被改動過的那幾天會連同郵件內容一起重寫，否則那天的信與網站會永久對不起來。

    

    

      
版本沿革移到後台

      
這一段的讀者只有維護的人。放在公開的技術說明頁，對來查「他今天講了什麼」的訪客是純粹的雜訊，而且它會隨著每次改版一直長，把那一頁越推越長。改成獨立的 include 檔掛在後台，技術說明頁只留一句指路。

    

    

      
觸發器額度、全面重整改由 GitHub 驅動、進度條顯示真實子步驟

      
後台按「全面重整」跳出「這個指令碼包含過多觸發條件」。原因是 Apps Script 每個指令碼的觸發器上限是 20 個，而 installTriggers() 剛好裝滿 20 個，一格都不剩，任何一次性觸發器都建不出來。同一個原因還埋著一顆更嚴重的雷：每日品質關卡的觸發器也建不出來，而它是在 dailyPushJob 裡面排的，例外往外拋就讓整封推播信寄不出去，畫面上完全看不到徵兆。處理方式有三層。第一層把十二個「只是在等某個時刻」的觸發器（推播三次、狀態信三次、報價、看門狗、認證守望、影片偵測、稽核收尾、失敗告警）併成一個每五分鐘的派工函式，由它依時間決定該做哪一件，觸發器從 20 個降到 9 個，空出 11 格；順帶把「綁死在某個時刻」改成「過了時間而且今天還沒做過就做」，漏掉一棒下一棒會補上，而推播也從等整點改成 13:00 起每五分鐘試一次，逐字稿一好就寄。第二層把全面重整改成由 GitHub Actions 逐棒驅動：GitHub 每隔幾分鐘打一次網頁請求，Apps Script 做一小段就回報進度，做不完再打一次，一個觸發器都不用，而且每一棒都留在 Actions 日誌裡；GitHub 沒設定時才退回觸發器接力。第三層讓建觸發器失敗不再能中止推播——排不出來就直接放行寄出，寧可寄一封沒複審過的信，也不要整天沒有信。另外「只刷新畫面」的進度條原本只有三格「派工／GitHub 執行中／完成」，因為 GitHub 的 API 只回報那三種狀態。但真正知道跑到哪一步的是 Apps Script：整條鏈是 GitHub 一步一步打進來的，它每次都清楚自己被要求做哪一件。現在它會把那件事記下來，後台問得到，七個子項目逐一亮起來。

    

    

      
配額用盡改成暫停、全面重整可取消與單步重跑

      
全面重整跑到一半吐 HTTP 429「Quota exceeded」。429 其實有兩種，處理方式完全相反：每分鐘請求數爆掉等一分鐘就好，當日額度用完則等到明天，這一輪再怎麼退避都沒有用。先前一律當成前者，於是額度用完時每一次呼叫都要把五段退避（約兩分鐘）全部等完才失敗，而全面重整一天要打三四次、要跑一百多天，整個工作就耗在等一個今天不會好的東西上。現在依錯誤訊息分辨兩者，當日額度用完直接往外拋一個可辨識的例外，一路穿過稽核、複審、每日關卡到最外層——中途每一個 catch 都特別放行它，因為在任何一層吞掉都會變成「這一天失敗、跳過、跑下一天」，然後下一天再失敗一次，一百多天就這樣白跑完。最外層把狀態標成「暫停」而不是「失敗」：兩者的後續動作不同，失敗要人去看哪裡壞了，額度用完只要明天再按一次，而且進度都還在。GitHub 那邊的驅動迴圈看到暫停也會跟著收工，並印出明天怎麼繼續。另外補上三顆按鈕：取消重整（已完成的步驟與游標都保留，GitHub 下一棒問到已取消就自己收工，不必去 Actions 按停止）、接著跑（從停住的那一步、那一天繼續，做到一半的步驟也是接著做而不是整步重來）、以及單獨重跑某一步（配步驟選單，用在某一步失敗、修好之後只想重跑它）。

    

    

      
個股面板移除月K

      
個股面板的 K 線週期只留日與週，移除月K。月線一根涵蓋二十幾個交易日，而這個網站的資料是以「哪一天他講了什麼」為單位，兩者的時間尺度差太遠——在月線上看不出任何一次進出的位置，那條線對這裡要回答的問題沒有幫助。後端 getCandles 的 month 分支保留著，因為它是公開 API；拿掉的話 period=month 會掉到最後一行回傳日K，那不是壞掉，是安靜地回錯資料，比直接不支援糟得多。

    

    

      
多把金鑰輪替、看門狗不再搶走 GitHub 的工作

      
全面重整跑到第 6/32 天就因為當日額度用完而停下來。免費層的每日額度對「一次跑一百多天」這種工作太小，所以改成支援多把金鑰：不同 Google 專案各有各的額度，一把用完自動換下一把，全部用完才真的暫停到明天。用完的那一把會記在指令碼屬性裡（換日自動清），同一天後續的呼叫直接從還能用的那一把開始——不記的話每次呼叫都要從第一把撞一次牆，一天下來白撞幾百次，而且每一次都要等完整的退避。設定方式是指令碼屬性加 GEMINI_API_KEY_2 到 _5，或把多把用逗號寫在 GEMINI_API_KEYS 裡。另外修掉一個上一版引入的 bug：看門狗每五分鐘檢查背景作業有沒有卡住，卡住就重新排程，但它不知道全面重整是由 GitHub 驅動的。GitHub 那邊因為部署沒更新而失敗之後，看門狗看到狀態沒動就默默接手，建了觸發器把整件事搬到 Apps Script 上跑——於是 Actions 日誌裡什麼都看不到，看起來像「怎麼跑到 script 去了」。現在狀態會記下是誰在驅動，GitHub 那一種看門狗只記錄不接手，斷掉時由人按一次「接著跑」從同一個游標接續。pipeline 那邊也補上版本檢查，部署沒更新時會直接說「下游版本過舊，不支援 full-fix」，而不是丟一句看不出原因的「不認得的步驟：fullfix」。後台則在按「開始全面重整」時偵測是否有未完成的進度，有的話先提醒那會從頭重跑，要接續請按「接著跑」。

    

    

      
名稱與代號打架的仲裁、價位現實檢查

      
網站上出現「毅嘉（2402）」，引用的原話卻是「隱藏版光訊叫做 2402 的錩新」。毅嘉這兩個字在整份逐字稿裡一次都沒出現過。原因在代號比對的第一條規則：代號格式合法就直接採用，不再往下比名稱。那條規則本身是對的（四位數代號是硬證據，先前殘缺的對照表害得美琪瑪被改成美利達），但它假設了代號與名稱指的是同一檔，而逐字稿是語音轉文字，數字和名字都會被聽錯。這種錯每一欄都有值、股價與 K 線也都畫得出來，只是整列都是別人的資料，比空白難發現得多。現在兩者對不上時不再默默挑一邊，而是數一件可以驗證的事：這兩個字串在整份逐字稿裡各出現幾次。講者真正在談的那一檔，名字會被反覆講；聽錯的那一個通常只出現一次。上面那個例子裡錩新出現三次、2402 出現一次，所以採用名稱。次數一樣多時不猜，留成待確認——兩個都有可能對的時候，猜一個填進去只是把不確定藏起來。第二種接錯檔是把甲的話接到乙頭上：「我要你去買統振……66.4 是我會員已經買了，鴻準了」，那句持有講的是鴻準，66.4 也是鴻準的價位，統振不在那個價位，系統卻把統振記成會員持有。這是最嚴重的一種錯，它會開一個不存在的持有回合，然後每天用真實股價幫一筆不存在的部位算報酬。除了在提示語裡要求把聲明歸給緊鄰的那一檔，另外加了一道可以驗證的：拿數字去對那一檔真實的日K區間。偏離三成就不採用那個價位；差到兩倍以上就連分類一起降到觀望，因為那個數字根本不屬於這一檔。門檻分兩層是因為兩件事的代價不一樣——清掉一個數字錯了損失很小，改掉持有狀態錯了損失很大。另外要求說明重點要用自己的話寫成 40 字以內的通順短句，不要把逐字稿整段剪貼過來。

    

    

      
觀望不碰改成暫定出場

      
鴻海的持有回合被切成四段，第四段從 9/2 重新開始。實際情形是：8/27 明講會員持有 238，8/31 說「238 搶過了，248 不會推薦」，9/2 又說「前幾天於 238 買進，目前已漲到 250 幾」。8/31 那句是在勸還沒進場的人不要追高，不是宣布出場，9/2 那句證明部位從頭到尾都在手上。舊規則把觀望不碰一律當成平倉，於是同一筆部位被切成兩段，第三回合結算出一個沒有發生過的報酬，第四回合的進場價又變成 9/2 的收盤。現在觀望不碰改成暫定平倉，會被後來的事實推翻：往後看第一個實質動作，是會員持股或賣出就代表部位還在手上（賣得掉就表示當時還有），這次不碰不算出場；是買入才算真的重新進場，照舊切成兩個回合。超過十個交易日或二十一個日曆日沒有下文，仍然照舊視為出場。兩個上限一起看，是因為交易日的數法依賴日K快取，而快取會殘缺——快取少了一段時，相隔三個月的兩天算起來可能只差三個交易日，日曆日不依賴任何快取，擋得住這種情形。被推翻的那幾次會記在回合上，出場原因欄看得到，不會無聲無息地消失。

    

    

      
自動補缺的日K

      
表格上常出現「取不到進場價。可到後台按補齊日K並重算」。進場價、現價、報酬三欄都是從日K算出來的，一檔沒有 K 線的股票在表格上就是三個空格加一句要人去按按鈕的話。而會踩到的幾乎都是今天第一次被講到的股票——它才剛寫進操作紀錄，分批補日K是照代號排序用游標往下走的，不一定輪得到它，那句話就會在網站上掛一整天。要人去按一個按鈕才會好的東西，本來就該自己好。現在每一次重算持股追蹤之前都會先掃一遍「一列都沒有」的代號並立刻補上，通常是零到三檔，幾秒鐘的事；已經有資料的一概不碰，不與分批補日K重複做工。補不到的（代號打錯、剛上市、已下市）會把原因記下來，網站上的說明改成講真正的理由，而不是叫人去按一個按不好的按鈕。

    

    

      
人工補登

      
有些內容機器再怎麼強也擷取不到，因為講者刻意不講：「這是一檔非電子股，20 幾塊錢，盤底八個月，每股淨值 60.5 元，月K線 MACD 兩年半來第一次翻揚，我下半週才公開名稱。」整段有型態、有價位、有結論，就是沒有名字。擷取端的規則是「不指名就不要生」——那條規則是對的，從漲跌幅去猜是哪一檔只會猜錯——所以這一段必然被丟掉，可是它往往是那天最重要的內容。後台新增「人工補登」分頁：選日期（日曆與前台同一套外觀，但每一天都點得下去，因為需要補的正是還沒有資料的那一天）、填名稱與代號、選分類、貼上那一段逐字稿，送出。AI 在這裡的角色刻意很小，分類由人決定，它只負責把口語濃縮成一句 40 字的重點、把價位挑出來——人工補登的前提就是人比較準，讓模型有權推翻人就沒有意義了。寫進去的就是一般的一列，後面的重寫郵件、重算追蹤、刷新網站全部沿用既有的按鈕與函式，一條新的資料路徑都沒有。名稱與代號對不上時會擋下來問一次，那正是 2402／錩新 那種錯的來源，人工補登更不該讓它悄悄發生。另外留一張「人工補登」分頁記下誰在什麼時候、根據哪一段話、補了什麼，因為操作紀錄那一列看起來與 AI 擷取的沒有兩樣，事後要查只能查這裡。全面重整的內容複審會跳過這些列——複審的依據是「這一檔在逐字稿裡怎麼被講」，而補登存在的理由正是那天他沒講股名，交給複審只會一直回報找不到節錄，每次都白花一次模型呼叫。

    

    

      
複審可以改名稱

      
名稱與代號的仲裁只對「之後新進來的資料」有效，過去已經寫成毅嘉的那些列改不到。能回頭修它的只有內容複審，因為只有那裡同時看得到「表格上寫什麼」與「逐字稿實際講什麼」。複審多了第四種判決「改名稱」，判定之後程式會拿模型回報的名稱去比對官方清單，名稱與代號一起改掉。動手的條件是一個可以用程式驗證的硬事實：目前這個名稱在整份逐字稿裡一次都沒出現過。模型說「掛錯公司了」是判斷，會錯；「毅嘉這兩個字在兩萬字裡出現零次」是事實，不會錯。只認事實，模型的判斷只用來提供候選名稱；名稱只要出現過一次就一定不改，即使它很有把握——那種情形多半是同一段話提到了兩檔而它挑了另一檔。每一次改名稱都會寫進「修正建議」分頁留痕。按一次全面重整就會套用到全部歷史。

    

    

      
逐日編輯：後台可以改一列、刪一列

      
前面所有的機制都是「讓機器判得更準」，但機器一定有判不準的時候，而管理者是唯一看過整支影片的人。少了直接改一列的能力，發現錯了只有兩條路：去 Google 試算表手動改（然後郵件內容不會跟著變，網站與信件永久對不起來），或是按一次全面重整賭它這次會判對。兩條都不好。現在選一天就會列出當天所有的股票，可以直接改分類、價位、理由，也可以刪掉；把分類改成「會員持股」會自動搬到會員持股分頁，改回來也一樣，因為兩張分頁的欄位不同，不搬家的話價位會沒有地方放。原本的「人工補登」併進同一頁成為「新增一筆」——同一天的看、改、刪、補是同一件事，分成兩頁只會讓人在兩個分頁之間來回。列號會位移，所以每一次寫入之前都先驗身分：那一列的日期、代號、名稱要與前端記得的一樣，對不上就整張表重找，再找不到就明白拒絕請對方重新整理。少了這一關，在讀完清單到按下儲存之間若有人刪了前面的列，寫下去就會改到不相干的股票，而且兩邊都以為成功了。刪除沒有復原鍵，所以每一次刪除都會寫進「修正建議」分頁留痕。

    

    

      
全面重整可以只跑近一周

      
全面重整一天要呼叫三到四次模型，一百多個交易日就是四五百次，免費層的每日額度撐不完，實際上要跨好幾天、按好幾次「接著跑」。但多數時候規則只改了一點，需要重跑的其實只有最近幾天——為了那幾天把一百多天全部重判一次，額度與時間都是白花的。現在多了範圍選單：近一周、近一個月、全部歷史，預設是近一周（按錯的代價最小）。範圍用「有紀錄的交易日」往回數，不是用日曆天往回推：連假、颱風假、他請假沒開播這些日子都沒有紀錄，用日曆天推七天遇到中秋連假就只剩三四天真的有東西，範圍會忽大忽小。範圍只限制「按日期逐天處理」的三步——稽核與複審、價位校對、重寫郵件；補齊日K與重算追蹤不受限制，而且不該受限制：持有回合是從第一天算到今天的，只算最近七天會把回合切斷，算出來的報酬是錯的。範圍也會派給 GitHub Actions 當輸入，它對執行結果沒有影響（真正決定範圍的是下游的狀態），送過去純粹是為了讓執行清單上看得出這一輪跑的是近一周還是全部歷史——兩者的耗時差十倍，事後回頭看分不出來很麻煩。順帶把 Actions 的逾時上限也綁上去：選近一周時 60 分鐘就夠，一律給六小時的話，卡住的工作也要等六小時才會被砍掉。

    

    

      
後台日曆被按鈕樣式塗黑

      
補登那一頁的日曆整片變成深色方塊，數字看不見，左右換月的箭頭變成兩個黑色按鈕，而且箭頭的位置直接顯示著「‹」這樣的字面文字。兩個原因。一是日曆的每一格與換月鍵都是 button，而後台為了讓表單按鈕好看，寫了一條 .panel button 把分頁內的按鈕全部塗成實心深色——它的權重贏過 Stylesheet 的 .cal-c，卻輸給 .cal-c.has，於是只有「有紀錄」的那幾天長得對，其餘全黑，看起來像整個壞掉。現在在日曆範圍內把按鈕樣式還原回去，用的選擇器只涵蓋日曆內部，不影響任何其他按鈕。二是產生 HTML 時把 ‹ 這種 JavaScript 的跳脫寫法直接寫進了 HTML，而 HTML 不認得那個語法，只會原樣印出來。另外「資料修正」那一頁的日期也從瀏覽器內建的 date 欄位換成同一個日曆——那個內建欄位在每個瀏覽器長得都不一樣，深色模式下常常整個看不見，而且與旁邊那一頁完全對不起來。日曆做成共用的工廠函式，兩頁用同一份程式，不會各自長歪。換掉之後「日期留空代表處理全部」這個用法沒有地方表達了，所以補了一個「不限日期」的勾選給重新分類用。

    

    

      
閱讀設定改成版面設定

      
逐字稿上方那塊設定原本沒有標題，夾在文章上面看起來像內容的一部分，很多人根本沒發現它是可以調的。現在加上齒輪圖示與「版面設定」標題。三軸也重新選過：內容欄寬從三檔改成四檔（窄、標準、寬、特寬）——原本 92ch 到滿版之間差距太大，在寬螢幕上那一跳是從一行約 45 字直接變成八十幾字，中間少了一個真正好讀的選項。字級換成字距（標準、寬、特寬）：長篇中文的可讀性瓶頸不在字大不大，一段密排的繁體字讀久了會黏在一起，而中文沒有詞間空白可以幫忙斷開；字級瀏覽器本來就能縮放，字距沒有別的地方調得到。行距的三檔改成緊湊、標準、寬鬆，講法更直白。

    

    

      
昨天的操作記到昨天、同一天的先後照序排

      
晶心科出現兩筆同日進出：9/2 賣出 270 幾、9/2 買入 250 幾。兩件事都不對。第一，那是昨天做的——他昨天的直播只播到 11 點，收盤前的操作只能在今天的直播裡回頭講：「我昨天早盤請會員賣出晶心科創新高，大概賣 270 幾……那我昨天快 12 點的時候去把它買回來。」記在今天的後果是 9/1 那一天在網站上完全看不到這件事，9/2 卻多出兩筆從沒發生過的當日進出。現在擷取時會標記這一筆算哪一天，買賣改記到前一個交易日（前一個交易日從日K快取取，不是日期減一——週一的前一天是上週五，遇到連假還要再往前，減一天會落在沒有開盤的日子）；觀望與會員持股不改派，那是「現在的看法」，屬於今天這支影片。第二，順序反了。原本同一天的先後是用固定優先級猜的，買一律排在賣前面，於是「早上賣 270、中午買回 250」變成「先買 250 再賣 270」——先買後賣是加碼之後獲利了結，先賣後買是賣掉再撿回來，兩者的回合、進場價、報酬完全不同。更糟的是後面還有一條「同日已有買入就忽略相反訊號」的防呆，於是那筆賣出直接消失，回合永遠不會結束。現在操作紀錄多了「序」欄，擷取時照他描述的先後填 1、2、3，排序改看序；同一天有明確的序時，那條忽略相反訊號的防呆會讓開。舊資料沒有這一欄，行為與加這一關之前完全相同。既有試算表不會自己長出新欄位，所以 getSheet_ 順手補：表頭比對過，只補尾巴少掉的那幾欄，中間對不上時不動。

    

    

      
說明改寫成研究報告的句子

      
表格裡的說明重點原本是逐字稿剪貼——「隱藏版光訊叫做2402的錩新，昨天漲3塊1，今天漲兩塊4，好，注意」。那是口語，充滿情緒用語與模糊形容詞（有鬼、沒用、出事），對讀報表的人來說缺乏實質資訊。現在擷取端會去除口語與情緒、保留季線、缺口、整理時間及價格區間等實質條件，並寫成一個自然完整句：先交代現象，再銜接操作結論。中括號、方括號、加號與欄位標籤都禁止出現在結果中；程式寫入前另有確定性正規化，即使模型偶爾違反格式也不會流進前台。禁止加入原文沒有的資訊，也禁止改變結論方向——原文說不要買就是不要買，不可以寫成「可留意」。過去舊資料可由全面重整的「重寫說明」回頭處理；它只改文字，不動分類、價位與日期。

    

    

      
版面設定移到頂列

      
版面設定原本夾在逐字稿的內文上方，只有翻到那一頁才看得到，而且很多人根本沒發現它是可以調的。現在移到頂列的齒輪，從任何一頁都按得到；設定值跟著改掛在 html 元素上，與深淺色、手機版用同一個做法——按鈕在哪個層級，設定值就要在那個層級才讀得到。作用範圍也講清楚了：內容欄寬只作用在逐字稿（郵件內容裡有表格，把容器縮窄會讓表格擠成一團），字距與行距兩個長文區塊都套用。

    

    

      
出場原因不再是一片文字牆、逐日與紀錄一對一

      
鴻海的出場原因欄變成一整段沒有斷點的文字：「期間曾轉觀望不碰（2026/08/31（2026/09/02 明講會員持有，證明部位並未在 2026/08/31 離開）、2026/09/01（……））因此不視為出場」。理由對每一次都一樣，卻每一次都附了一遍。現在只記日期、理由講一次，日期用月/日（年份在旁邊的欄位已經看得到），並且拆成兩行呈現：「期間轉觀望不碰 2 次（08/31、09/01），之後仍明講會員持有，故不計出場」。另外個股面板上「影片提及 32 次」與下面「每天講了什麼」列出來的筆數對不起來——一個從原始紀錄數、一個從去重後的逐日說明數，而使用者會去數，數完發現只有 28 條，那個 32 就變成一個沒人相信的數字。現在提及次數直接等於逐日說明的筆數。「影片中提到的每一次」那張表也補上會員持股：先前它只讀操作紀錄，而逐日說明讀的是兩張分頁，少掉的正好是他明講會員持有的那幾天。兩邊都是「他提到這一檔」的紀錄，本來就該是同一份。

    

    

      
技術說明加上情境圖

      
技術說明前面加一節「五種出過的錯，長什麼樣子」：名稱與代號指向不同檔、甲的價位接到乙頭上、觀望不碰把回合切斷、昨天的操作記在今天、同一天先賣後買被弄反。每一張卡片是一個真的發生過的錯，配一張小圖，加上三行——症狀、原因、現在怎麼處理。用圖是因為這幾種錯的共同點是「每一欄都有值、看起來完全正常」，光靠文字描述很難讓人意識到問題長什麼樣子。圖用 inline SVG 而不是圖檔：顏色吃 CSS 變數，深淺色切換不必準備兩份，也不會多一次網路請求。

    

    

      
版面設定改成全站共用

      
版面設定原本只作用在逐字稿那一頁，後台也沒有這個功能。現在三軸都作用在所有分頁，前台與後台共用同一個齒輪、同一組選項、同一個瀏覽器儲存鍵——在前台調過的欄寬與字距，進後台看到的是同一組設定。實作上把整塊做成獨立的 Settings.html，兩個頁面各 include 一次。手機／電腦切換與深淺色切換當初是兩邊各抄一份，那種東西改了一邊忘了另一邊就會慢慢長歪，而且沒有人會特地去比對，這一次不重蹈覆轍。欄寬的做法是把 --wrap 拆成「上限」與「左右留白」兩個變數：版面設定只動上限，手機版與窄螢幕只動留白，兩者互不干擾；合成一條寫死的 min() 的話，任何一邊改了另一邊就整個被蓋掉。而 .wrap 是每一個分頁的外層容器、後台的內容欄也收在裡面，所以一改就是全站生效。手機版的欄寬是固定的，所以那幾條規則寫成與手機版互斥，不依賴檔案裡的先後順序——同權重時後面的贏，而相對位置會隨著改版飄移，寫成互斥就永遠不會冒出「選了手機版卻被欄寬設定蓋掉」這種找不到兇手的問題。字距與行距只套在「讀的文字」上，不套整個 body：套 body 的話按鈕、分頁列、輸入框、圖表座標都會跟著跑，把導覽列的字距拉開只會讓它擠不下。另外設定值改成記憶體與 localStorage 各存一份——這個網站跑在 Apps Script 的沙箱 iframe 裡，瀏覽器擋第三方儲存時 localStorage 會直接拋錯，只讀它的話會變成「按了選項畫面完全沒反應」，使用者會以為按鈕壞了。

    

    

      
幻覺檢查：名稱必須真的在逐字稿裡

      
表格出現一列「位速（3508）判斷為隔日沖券商拉高出貨，先行獲利了結」，但位速這兩個字在整份逐字稿裡出現零次。他那一段講的是「這個禮拜的第三個動作……我請我的會員買 250 的，賣 275 左右賣掉……那我又告訴我的會員 250 幾 26 買回來，收盤收 262.5」——有價位、有動作、有日期，唯獨沒有股票名稱。提示語早就寫了「不指名就不要生」，但那是「請它不要」，不是保證。現在加一道不靠提示語的防線：擷取完之後逐一確認，名稱或代號至少有一個要能在逐字稿裡原字找到，兩個都找不到就整筆丟掉。「這個字串有沒有出現在這兩萬字裡」是事實不是判斷，模型再有把握也推翻不了。比對前把空白拿掉，所以語音轉文字把「台 積 電」拆開也對得上；名稱短於兩個字不算數，那太容易誤中。這一關排在代號比對之前——比對會把名稱換成官方簡稱（加哲→嘉澤），換過之後就對不到逐字稿了。逐字稿拿不到時整關略過，因為那時全部丟掉會讓整天沒有資料，比放行糟得多。上游與後台兩條路都加了同一道。提示語也一起補強，把這個案例整段寫進去當反例。

    

    

      
信沒寄出去的時候要看得出原因

      
推播沒寄出，而信箱只是安靜地沒有東西，執行紀錄裡也什麼都沒有。原因是 dailyPushJob 有六個「直接 return」的出口，每一個都是靜默的——週末、今天那一列還沒有、文章還沒產生、已經寄過、關卡沒過、被別的執行搶先，看起來全都一樣。現在每一個出口都把原因記下來，新增 whyNoMail() 一次印出完整狀態（今天那一列在不在、文章多長、寄送狀態、關卡跑到哪、有幾個訂閱者、剩多少寄信額度、上一次退出的原因），forceSendToday() 可以跳過關卡強制補寄，resetTodayPush() 清掉卡住的狀態。另外修掉兩個會造成「整天沒有信」的真問題。一是卡在「寄送中」：那個狀態是搶鎖之後、真正寄出之前設的，用來防止三個時段各寄一封，但如果那次執行在中間被中斷，狀態就永遠留著，之後每一棒都被它擋掉。現在超過十五分鐘還在寄送中就判定該次已死，清掉重來——重複寄的風險遠小於整天沒有信。二是時間窗太窄：推播只在 13:00 到 15:40 之間每五分鐘試一次，上游跑得晚一點（重跑、配額退避、GitHub 排隊），文章在 15:40 之後才落地的話就再也沒有任何一棒會呼叫它。現在拉到 22:00，成本接近零，因為已寄送或還沒好都是立刻返回。再加一棒 18:00 的收尾巡檢，到那時還沒寄就把原因寫進系統狀態分頁。

    

    

      
處理進度拆成逐項、後台頂列對齊

      
投稿逐字稿的進度條原本六格，中間那格叫「擷取與比對」——它裡面有八件事在跑，會亮五到十分鐘不動，看起來像當掉，卡住時也分不出卡在哪一件。現在拆成十三格：排程中、讀取原文、潤飾、擷取、稽核補漏、查驗幻覺、代號比對、價位校對、日期歸屬、撰稿、寫入、刷新網站、完成，每一格還帶一句說明（例如「目前 18 檔，用日K驗證每一個數字是不是這一檔的」）。維護工具那邊補上子進度：補日K有三十幾檔、稽核與複審有一百多天、重寫說明一批 30 筆，這些步驟一格會亮好幾分鐘，先前畫面上只有一句「執行中」，與真的卡住完全分不出來，現在看得到「第幾批／共幾批」。步驟格的寬度也從等分改成依內容決定，否則換行之後最後一排的三格會各撐成三分之一寬，看起來像兩種不同的東西。後台頂列拿掉「回網站首頁」（瀏覽器的上一頁就回得去，而它是右邊那排唯一有文字的元素，讓整排看起來歪掉），並把版面切換、版面設定、深淺色三顆的高度、圓角、圖示大小全部對齊——它們是同一組東西，先前卻是 28／34／28 三種高度、圖示 15／17／13 三種大小，排在一起像三個不同時期硬塞進去的按鈕。

步驟列每一排格數一樣多

      
十四步的進度條會排成 9+5：下面那一排只有五格、右邊空著一半，看起來像沒排完。這個問題換過三種寫法。flex:1 會讓最後一排的格子各撐成該排的等分，上排小格下排大格；flex:0 1 auto 每格一樣寬了，但整排只佔左邊一半，右邊空著；格線加 auto-fill 解決了前兩個，但排出來就是 9+5。現在欄數改成算出來的：先看一排最多放得下幾格（每格至少 84px，字放大就跟著放大），據此算出需要幾排，再把格子平均分到每一排——十四格兩排就是 7+7，十格就是 5+5，九格一排剛好放得下就一排。只有一排放得下的時候用「最多幾格」而不是「實際幾格」，否則補登那條只有三步的鏈會變成三個超大格。每格的最小寬度與間距只寫在 CSS 一份，JS 讀那兩個值去算，不會兩邊各寫一個數字然後長歪。視窗變寬變窄、字體大小或欄寬改過、切到別的分頁（藏著的面板量不到寬度）都會重算。

有人用無頭瀏覽器對線上站台做了一份體檢報告。逐條對照程式碼之後，其中屬實的都修了：產業別直接顯示證交所的數字代碼（22），現在對照成「生技醫療業」；上市櫃日顯示未格式化的 20191007，現在是 2019/10/07——兩個轉換都放在讀出的那一刻，所以已經落地的舊快取也跟著變乾淨，不必等下一次重抓。績效走勢切到「正報酬比例」時線條永遠是紅的，因為顏色規則寫成 last >= 0 就用漲色，而比例永遠大於零：勝率只有三成也畫一條代表上漲的紅線，那是反過來誤導；現在改用中性色，並在五成拉一條基準線。觀望股點進去，抽屜最上方用最大的篇幅寫著「影片中沒有明講買入過這一檔」，而會點進來的人多半就是因為今天他講了這一檔——現在改成把最近一次的立場與那句話擺到最上面。沒有日K快取時，三個圖表容器加起來 600px 的白方塊也收起來了（順帶修掉一個潛在問題：瀏覽器內建的 [hidden] 權重極低，任何作者寫的 display 都蓋得過它，對 flex 元素設 hidden 是沒有反應的）。日曆上沒有紀錄的日期用 opacity .35 壓在 --muted 上，算出來的對比只有 1.6:1，在反光的螢幕上幾乎看不見，現在改成實際顏色，淺色 4.54:1、深色 4.84:1，過 WCAG AA。每日總覽四張表同時是空的很常見（他沒有買賣、只講觀望的日子），四塊完整的空區塊會佔掉 360px 把有內容的表推到很下面，改成一行之後是 176px。訊號帶原本 46 秒無限左捲，讀下面的表格時周邊視覺永遠有東西在動；改成預設不動、可以自己橫向滑，滑鼠移進去才慢慢捲。提示語補一條：他很常拿舊單當教材（「這檔我以前賺錢賣掉，現在不要碰」），那是觀望不碰，不是今天的賣出。報告裡「台積電成本被錄成 2135」那一條沒有改：它自己引用的站上現價是 2410，2135 到 2410 剛好就是它算出的 +12.88%，兩個數字是一致的；而真正的離譜值早就有一道防線（priceOnDate_ 會把偏離歷史區間的數字判定為不是股價，退回當日收盤並在來源欄註明）。結構性的建議（刪分頁、藏後台、聚合 API）也沒有動，那幾項會推翻先前明確做過的決定，留給人自己判斷。

    

    

      
後台與 AI 助手離開分頁列、內容欄加寬

      
分頁列少了兩格。後台移到頂列的鎖頭圖示——它跟其他分頁不是同一種東西，其他分頁是同一個網站的不同區塊，後台是另一個網址、另一群使用者，排在分頁列最後面看起來像「這個網站的第九個功能」。AI 助手則做成右下角的浮動面板：問問題通常是在看資料的過程中冒出來的，做成分頁的話想問就得離開現在這一頁，問完又要自己走回來；現在看到一半想問就開，問完關掉，原本那一頁還在。技術上它刻意不再掛 .panel——切分頁的程式會把所有 .panel 藏起來，助手若還是 .panel，切一下分頁就被關掉，等於沒解決問題。頂上不再擠之後，前台的內容上限從 1440px 拉到 1600px，欄寬四段也一起往上移（1100 / 1400 / 1700 / 2000）。後台的欄寬完全沒動：那邊是表單，一行輸入框拉寬只會讓眼睛從左跑到右。跑馬燈也改回一直捲。中間試過「預設不動、滑鼠移上去才捲」，實際用起來不對——那條帶子是當天點名的所有個股，會動才知道後面還有東西，停著只看得到前幾檔。

    

    

      
轉場、抽屜與載入回饋

抽屜整片打開、助手加寬、逐日說明只留一份

四張空白分頁與匿名使用紀錄

      
「盤中快照」與「小時K」一直是空的。原因不是連不上，是從來沒有人寫進去——Setup 建了表、前端也寫了「60 分 K 由本站自行累積的盤中快照聚合而成」，但寫入的那一支與收盤聚合的那一支都不存在。現在補上：盤中每五分鐘記一次現價與累計量，13:45 聚合成小時K 再清掉暫存。量是用差值算的不是相加——累計量直接相加會把同一批成交算好幾次，那是這種資料最容易踩到的坑。「今日影片候選」是因為 YOUTUBE_CHANNEL_ID 這個指令碼屬性沒設；「資料索引」空白是正常的，它只在跨年封存時才會有內容。另外新增「使用紀錄」：哪一個訪客、在哪一頁、做了什麼、停留多久，前後台都記。識別碼是瀏覽器本地產生的隨機字串，不是 Email 也不是 IP，清掉瀏覽器資料就換一個新的；只留 90 天。前端是批次送的——每切一次分頁就打一次後端會在 Apps Script 上排隊，而排隊排的是同一條線，使用者真正在等的那幾支請求會被它拖慢。

    

    

      
回顧往事不是今天的立場、同一檔不能一多一空

      
兩個實際判錯的案例。富邦金 2881：他花了好幾分鐘講「九根半漲停，賣在460到450，我在除權息前一天賣掉，現在腰斬了」——那是一段完整的成功故事，在建立信任，不是在給今天的指示；結果被收成今天的觀望不碰，價位還填了 460到450。那一天他對富邦金沒有任何當下的立場，正確答案是一列都不生。聯電 2303：他先說「獲利比連接好太多，要去衝季線、補這個缺口，好好留意這一塊」，接著自問自答「聯電可不可以買？聯電線還壓著，我根本連動都不會想動」。兩段分開讀會得到相反的結論，於是同一天同一檔出現了觀望注意與觀望不碰兩列，一多一空互相矛盾。提示語兩邊都補了這兩個例子；除此之外還加一道不靠提示語的收斂：同一天同一檔同時出現在兩類觀望時併成一列，留觀望不碰。不是因為它比較可能對，是兩種錯的代價不對稱——把「不要碰」顯示成「留意」，讀的人可能照著進場；反過來只是錯過一個想法。兩邊的理由都留著，看好的那一段通常正是條件（過季線補缺口再說）。上游與後台都有，所以過去的資料重跑一次全面重整也會被收乾淨。

    

    

      
績效走勢排除重複與非交易日

      
同一天出現兩筆時，畫在折線圖上是同一個 x 有兩個 y，圖表函式庫會把後面那一段畫成一條垂直線。重複來自回補與手動補跑——那兩條路都是直接 appendRow，不像每日排程會覆蓋同一天。非交易日也一樣：回補是按日曆天推的，週六日突然多一個轉折，而那一天根本沒有收盤價。兩者都在讀出時處理，所以已經寫進試算表的舊資料不必動就會變乾淨。交易日曆取自日K快取；快取整個讀不到時不過濾——那時全部都會被當成非交易日剔掉，圖會整片空白，比多幾個點糟得多。

    

    

      
技術說明：五個問題，五張圖

      
上一版把工程細節收進折疊區、前面補了對話，方向對了，但對話本身還是一坨包在氣泡裡的文字磚——風控隊長一顆泡泡一百八十字，讀起來跟原本的段落沒有差別。這一版每一段配一張圖，而且是「這一段的邏輯關係決定用哪一種圖」：沒講就是未說明是兩邊的交集，用維恩圖（左圈他實際講的、右圈外界的解讀，只收中間那一塊）；數字聽錯怎麼辦是條件分支，用決策流程圖（在當天高低價之內就採用、超出三成清成未說明、差到兩倍以上整筆降級）；不碰算不算出場是時間與狀態，用雙軌時間軸（十天內又明講持有就繼續，十天沒再提才結算）；為什麼規則這麼多是根因分析，用魚骨圖（語音聽錯、時態混淆、張冠李戴、日期歸屬四根刺指向數字失真）；一天在做什麼是步驟推進，用三格故事板。文字砍到只剩一兩句，對話區最長的一段從一百八十字降到三十八字——細節在圖上，不必再用字講一遍。全部是內嵌 SVG，顏色吃 CSS 變數，深淺色不必準備兩份，也不多一次網路請求；每張圖都有 aria-label。版面上圖比字寬：泡泡放到 94ch 給圖用，段落自己收在 58ch——一行字超過六十個字就開始難讀，但維恩圖擠在 520px 裡兩個圈的交集會小到看不出來。

    

    

      
跑馬燈點得中了

      
訊號帶改回無限捲之後出現一個新問題：那一排一直在動，滑鼠有 hover 可以停，手機沒有——點下去的當下位置已經跑掉了，點不中，或者更糟，點到隔壁那一檔。現在 pointerdown 立刻暫停，放開或離開再繼續。捲動維持原樣。順帶補一個缺口：K 線載入失敗時也會把圖表區收起來。先前只在「後端回傳空陣列」那條路收，連線斷掉時那 600px 的白方塊照樣留著。

    

    

      
技術說明：一題一圖一故事，深究跟著問題走

      
結構重排。五個問題各自成一塊：一句話回答、一張圖、幾步故事線，最後跟著一個只屬於這個問題的「想深究」。工程細節不再堆在頁尾同一坨——會想看排程表的人，通常正是剛讀完「你們一天在做什麼」的那一個。圖的選法照邏輯關係決定，不是照好看決定：關係網用概念圖、交集用維恩圖、條件分支用流程圖、層級用金字塔圖、時間與狀態用雙軌時間軸、根因用魚骨圖、分類發散用心智圖、步驟用故事板，八種。新加的三張裡，概念圖直接取代了原本那張系統架構 SVG——架構圖畫的是「有哪些方塊」，概念圖畫的是「它們之間是什麼關係」，線上有字才看得出為什麼要這樣接；金字塔圖講進場價的採信順序（明講且成交得了 → 明講但要往後找觸價日 → 當日收盤）；心智圖把十四道檢查歸成四個問句（聽對了嗎、是今天嗎、是這一檔嗎、算對了嗎）。被圖講完的段落全部刪掉：舊架構圖、「先看這裡」那張六列摘要表、「五種出過的錯」那一長段，共少了八千多字。留著只是佔篇幅。對話也再砍一輪，泡泡裡最長的一句剩十九個字——細節在圖上，不必用字再講一遍。

    

    

      
逐句浮現

      
一次把五段對話全部攤在眼前，讀者會直接往下滑過去，因為它看起來就是一大片字。改成捲到哪一段，那一段的句子才依序出現，每句間隔半秒，節奏跟真的在對話一樣，人就會停下來讀完。故事線與故事板同樣處理。三件事守住：隱藏用的 class 是 JS 自己加上去的，不是寫在 HTML 裡——JS 沒跑、出錯、被擋掉，內容都必須完整顯示，這是說明文件不是動畫；使用者關掉動畫效果就整段不做；還有一個保底，切到這一頁六秒之後若一塊都沒演過，代表位置根本算不出來，那就一律全部顯示。用捲動事件而不是 IntersectionObserver：IO 在面板一開始是 display:none 的情況下不一定會送出初次回呼，那時整段內容會停在透明狀態——這件事在測試環境實際重現過，換成 getBoundingClientRect 才量得到。過程中還抓到一個更嚴重的：判定條件原本要求「而且還在畫面上」，捲快一點時一整塊會在兩次畫格之間整個掠過去，那一塊的字就永遠是透明的，往上捲回去也看不到。改成「越過畫面下緣那條線就算數」，單向判定。

    

    

      
技術說明：一份文件一個欄寬

後台的「更新過去資料」，以及它做不到的事

      
先說做不到的，因為那決定了這件事只能長成什麼樣子：會員頁一次只給最新的十一篇，而且沒有分頁——?page=2、?p=2、?offset=10、?skip=10 全部試過，回來的永遠是同一批十一篇；真正的分頁走的是要授權權杖的內部 API。那個帳號同時轉貼好幾位分析師的簡訊，一天可能發五六篇，所以那十一篇大概只涵蓋一到兩天。所以維護工具裡分成三個動作，各自解決不同的問題：「補抓最近」重新掃一次會員頁把還沒收過的收下來，解決排程停過幾小時到一天的情況，走的判斷與平常那一棒完全一樣所以重按安全；「依編號補抓」貼文章網址或純數字進去、一行一個、一次最多二十篇，任意久以前的都補得到，前提是手上有那份清單；「重新解析」在提示詞改過之後用，只重跑模型與查證、不重抓網頁，已經寫進操作紀錄的列不會被寫第二次。三個動作都要管理密鑰，補抓一樣要通過「是不是張震的簡訊」那一關，貼錯連結不會生出雜訊。後台那一段把「做不到什麼」寫在最前面——工具做不到的事沒有寫清楚，使用者會以為是自己按錯。
