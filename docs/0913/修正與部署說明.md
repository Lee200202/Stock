# 2026/09/13 覆蓋與自動續跑修正

目前版本：`2026-09-13-overwrite-v5`。會員持股專區、四類操作、六章郵件及防重寄機制保留。

## 一、這次 GitHub 為何失敗

使用者提供的 J20260912221830 日誌顯示：資料、郵件查詢、代號、持股追蹤已完成；績效歷史需要交易日曆，但日K快取沒有資料。上一版能正確辨認 pending，卻沒有補齊依賴與排入續跑，所以最後 exit 1。這不表示先前寫入的11筆被撤回。

新版遇到這個情況會：

1. 保留已完成刷新步驟。
2. 自動明確呼叫 `dailyk`，不再被後台預設的跳過條件擋掉。
3. 每批寫回後台日K進度。每輪沿用25分鐘總預算，時間不足先保存游標，避免撞 GitHub 30分鐘上限。
4. 工單顯示橘色「等待日K」，而非完成或資料寫入失敗。這個狀態也涵蓋日K已補好、剩餘刷新步驟等待下一輪的情況，備註會明講。
5. 既有 `everyFiveMinJob` 檢查這個狀態，冷卻10分鐘後派回 GitHub。最多自動派6輪；GitHub排隊時間不保證。
6. 續跑只讀檢查點，不重跑 Gemini 健檢、潤飾或擷取。日K補齊後再算持股追蹤、績效歷史與績效快照。
7. 來源持續無資料或派工持續失敗，超過6輪會變成「待處理」。真正的網路/API錯誤仍報失敗，不把錯誤當成功。手動「續跑卡住的工單」會重設此輪自動重試次數。

13:45 GitHub只補日K排程及14:35 GAS備援保留。新流程針對後台工單缺資料自動修復，不要求每次投稿都先補滿所有歷史日K。

## 三、上櫃清單失效的額外原因

實際讀取官方公開來源確認：

- MOPS CSV回應含UTF-8 BOM，HTTP卻落到ISO-8859-1。舊程式直接用 `response.text`，中文欄名變亂碼，因此誤報「欄位可能改了」。新版從bytes按UTF-8 BOM解碼。
- ISIN清單目前先列上櫃權證，舊程式在第一個權證標題即截斷，造成零筆。新版逐列核對CFI普通股類別與四碼股票代號，不依區塊順序。
- 本機於9/13透過標準TLS驗證實測，兩個來源各解析891檔上櫃普通股，均含4966譜瑞-KY。
- 不關閉SSL憑證驗證。櫃買OpenAPI的憑證問題本身仍屬外部連線問題，這次是修好兩條獨立官方備援，既有試算表快取也保留。

官方資料：[MOPS上櫃公司CSV](https://mopsfin.twse.com.tw/opendata/t187ap03_O.csv)、[ISIN上櫃證券清單](https://isin.twse.com.tw/isin/C_public.jsp?strMode=4)。

## 四、Prompt 調整

擷取及覆核新增相同規則，並同步GAS鏡像：

- 修正原Prompt末段「非當日買賣，有看法就列觀望」與前段會員持股規則的衝突；昨日買且仍持有先列holdings，後文候選名單不能抹掉既有部位。這能解釋為何前面已舉世芯／嘉澤範例，覆核仍可能只留下觀望。
- 價位原句必須含該數字，且對應S段落列入evidence_refs；3850與四星KY分在相連句時要附兩段，不再只提醒模型填價格。
- 每次只以這次source原文為依據，舊文章、舊候選不可當成本輪事實。
- 洞見採「現象→講者明講原因→適用條件→觀察訊號」，缺少環節就省略；不得自創內幕、未被定價或已證實的預測。
- 昨日買入但今天仍持有，可列會員持股，不必硬要當日買入句；外資成本不當作會員成交價。

這些判定規則只用於模型輸入，不加入公開文章內文。既有JSON合併擷取＋一次語意覆核、較完整說明重點、會員持股表格保持不變。GAS模型仍由Aiservice.gs的DEFAULT_MODEL決定，thinkingLevel維持medium可調，不因流程錯誤盲目提升到high。

判讀資料格式仍是context-json-v4，為讓這次已寫入的v4工單接續，未強制作廢原刷新檢查點；網站部署build另更新為overwrite-v5。已完成舊日要使用新Prompt重新判讀，需主動投稿覆蓋；只續跑績效不會改寫已發布AI判讀。

## 六、部署與恢復目前失敗工單：依此順序

1. 確認沒有正在寫入的GitHub工單；保留同一個GAS專案及原SPREADSHEET_ID，先留存雲端現有版本與試算表備份。
2. 在GAS新增指令碼 `Transcriptstore`，整份貼上Transcriptstore.gs。既有各檔完整覆蓋為目前apps-script內容，不要保留Code_backup.gs等會重複定義函式的備份。
3. 儲存全部檔案；執行 `checkSetup()`。首次遇到影片清單與工單時，getSheet_會依Setup.gs在表尾補欄，不清舊資料。影片清單增加「原文更新時間／原文SHA256／來源別名」，後台工單增加「原文SHA256」。若表頭曾人工改序，投稿會拒絕並要求先核對。
4. 開啟「觸發條件」確認 `everyFiveMinJob` 每5分鐘執行、`backfillDailyKJob` 約14:35執行，時區Asia/Taipei。若每5分鐘觸發器缺少，從介面只新增這一個；不要直接執行會刪除既有觸發器的 `installTriggers()`。
5. 確認GAS屬性 `GITHUB_REPO`、`GITHUB_TOKEN`、`GITHUB_WORKFLOW`（通常daily.yml）、`GITHUB_REF`指向更新後GitHub分支，原有ADMIN_KEY與SPREADSHEET_ID保留。自動續跑沿用現有後台派工權限，不需新金鑰。
6. 「部署→管理部署作業→選原本網頁應用程式→鉛筆→版本選新版本→部署」。版本說明填 `2026-09-13-overwrite-v5`。執行身分為自己；存取設定沿用可讓GitHub呼叫的「所有人」。沿用原 `/exec` URL。
7. 瀏覽器開原網址加 `?action=ping`，確認build是 `2026-09-13-overwrite-v5`，features含 `transcript-job-hash`、`auto-dailyk-resume`、`transcript-merge-preview`。只存檔而沒更新部署，ping仍會顯示舊版。
8. GitHub同步更新根目錄 `pipeline.py` 與 `pipeline/pipeline.py`，其餘專案檔案可一起提交；既有daily.yml和requirements這次不需修改參數。請確認Workflow選到有本次修正的分支。若使用ZIP，依相對路徑更新，不能把整個ZIP上傳當程式。
9. **恢復J20260912221830：到後台按「續跑卡住的工單」**。這張日誌原文SHA256為 `60d5901a9e651190ff0b749bb6c2d75931a804a47711503a7b3ad7ed3d7e8227`。若期間未改原文且它仍是最新工單，應讀取原刷新檢查點，略過已完成步驟，自動補日K。不要再貼一次原文，以免清空修飾稿或重新開一張工單。
10. 若這張已不是最新工單，先確認後台目前顯示哪張；續跑按鈕針對最新工單，不要誤操作其他日期。可另用「網站內容」從補齊日K開始刷新指定日期，但這條手動刷新與工單狀態不是同一件事。
11. 若已改過原文、希望新Prompt重新擷取，則另走投稿覆蓋。新工單有原文指紋，不能拿舊稿通過；舊工單沒有指紋仍向後相容，但日誌會明示未綁定指紋。
12. 觀察GitHub及後台：日K補齊後應重算tracker→perfhist→perf，才顯示完成；等待日K時不應再次出現polish或assess-json呼叫。已寄出的郵件不會重寄，郵件查詢依最新試算表更新。

## 七、整併已存在的同日重複列

1. 等正在執行或等待日K的工單完成；工具會拒絕在工單進行中套用，避免列號移動。
2. 後台「投稿逐字稿」按「檢查同日重複逐字稿（乾跑）」。列出日期、保留列、原文來源列、刪除列、字數與選擇規則；這一步不合併資料。
3. 人工核對沒有時間戳的舊稿。篇幅較長不一定較新，若不合適先重新投稿正確原文後再乾跑。
4. 按「備份並套用上次整併計畫」。系統檢查影片清單快照未變，先複製完整分頁到「影片整併備份-時間」，再合併並由下往上刪除重複列。
5. 每批最多20日／40列，避免6分鐘上限；重複乾跑與套用直到顯示無重複。整併本身不重跑AI、不寄信、不改操作紀錄；保留別名供下一次覆蓋追溯跨日舊列。
