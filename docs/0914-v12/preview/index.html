想深究：哪些東西刻意不收

為什麼美股不會出現在紀錄裡

張震在盤中很常拿美股當台股的風向球講，例如某檔美國半導體股昨天大漲、今天台股的相關族群應該會強。這是行情背景，不是他要會員操作的標的，而且那些公司根本不在台股掛牌。它們一旦被擷取進操作紀錄，會造成兩種後果：一是在網站上被當成個股顯示，二是永遠對不到台股代號，只能留成「代號待確認」，長期累積成一批清不掉的雜訊。

處理方式分成三層，因為只靠任何一層都不夠。

層次做什麼為什麼需要這一層
擷取階段 提示裡明確列出常見的外國公司並要求不要收，同時說明「講者提到外國公司只是在講行情背景」 從源頭擋掉最省事。但語言模型不保證每次都遵守，也可能遇到名單以外的公司
比對階段 比對代號之前先查外國股票名單，命中就整列剔除 這是硬規則，不受模型狀態影響。位置很關鍵：必須排在相似度比對之前
稽核階段 完整性稽核的提示同樣註明外國公司不算漏抓，不要補回來 少了這層，前兩層剛擋掉的名字會被稽核當成「漏抓的個股」又補進去

為什麼不能靠相似度自然淘汰

外國公司的中文譯名都是正常的中文詞，跟某些台股簡稱的拼音很接近。實際跑出來的相似度落在 0.73 到 0.77 之間，剛好卡在門檻邊緣：門檻設高一點，它們會留成「代號待確認」而顯示在網站上；門檻設低一點，它們會被硬湊到完全不相干的台股上，那比留成待確認更糟——資料看起來完全正常，但整列都是錯的。所以必須用明確的名單擋掉，不能指望相似度自己處理。

想深究：價位是怎麼校對的

價位說明的校對

價位說明這一欄是從逐字稿擷取出來的，而口語轉文字再經過擷取，會產生三類系統性的錯誤。這三類都不是隨機出錯，而是有固定成因，所以可以用固定的規則抓出來。

錯誤類型實際發生過的例子成因與後果
方向與內容矛盾 方向欄是買入，價位說明卻寫著某個價位以上全部賣掉 方向與價位是分開判定的，兩者可能各自對應到逐字稿的不同段落。結果是一筆買入紀錄掛著賣出的價位，下游會把它當成進場價，報酬直接算錯。
數字根本不是股價 某檔的價位說明寫著幾百億以下，但那檔的股價是三位數 逐字稿裡談營收、市值、成交量的段落與談股價的段落相鄰，擷取時把金額誤當成價位。這種數字若被當成進場價，會算出離譜到看不懂的報酬率。
概數被當成精確價 價位說明只寫著一千四百多 那是概數不是成交價。取整數或取中間值都是程式自己編的，會產生一個看起來很精確、實際上沒有依據的成本。

兩層過濾，先便宜的再貴的

校對流程刻意設計成兩層。第一層是純規則的快篩，完全不呼叫 AI：檢查價位說明裡有沒有出現與方向相反的動作字眼、有沒有出現億元或張數這類不可能是股價的單位、有沒有出現概數用語、以及整句是不是長到不像一個價位說明。乾淨的列在這一層就通過了，成本是零。

只有被快篩挑出來的可疑列，才會進入第二層送 AI 校對，並且會一併把該檔當天的日K最高與最低價交給它當硬性驗證依據。AI 回來之後程式還會自己再對一次 K 線：如果它給的價位偏離當日區間超過三成，一律不採用、清成未說明。AI 說通過不算數，數字要自己對過才算。

整個流程的原則是：留「未說明」永遠好過填一個編出來的數字。找不到符合該方向的價位時，寧可空著，也不會把賣出的價位寫進買入那一列。

條件價與觸價日

張震講價位時，很常講的不是「我剛才用這個價格成交」，而是「漲到某個價位以上就全部賣掉」「跌到某個價位以下才進場」。這種是條件價：講的當天股價通常還沒到那裡，要等後面某一天市場真的走到，這筆操作才成立。

先前的處理有個明顯的錯誤。系統一律拿發話當天的最高與最低價去驗證他講的數字，落在區間外就判定不合理、退回當日收盤。可是條件價本來就必然落在當日區間之外，不然它就不叫條件了。結果是他明確講過的出場價被丟掉，換成一個他從來沒提過的收盤價，報酬自然算錯。表格上看起來就是「明明講過那個價，系統卻說不在當日區間內」。

現在改成先分辨這個數字是哪一種，再決定怎麼定價。

講法判定定價方式
某價位以上、站上某價位、漲到某價位 向上突破的條件價 從發話那天往後找，第一個最高價碰到該價位的交易日就是成交日，成交價就是那個價位
某價位以下、跌破某價位、拉回到某價位 向下觸及的條件價 同上，改找第一個最低價跌到該價位的交易日
在某價位買進、成本是某價位 明確成交價 落在當日高低之間就直接採用；當天碰不到就往後找第一個涵蓋該價位的交易日
期限內始終沒有觸價 條件沒成立 退回當日收盤，並在來源欄註明那個價位一直沒觸價。這是市場沒配合，不是資料錯誤

往後找有兩道限制。一是上限六十個交易日，超過就當作沒成交，避免一個很久以前的條件價在半年後被硬湊上去。二是往後找之前會先確認這個數字對這一檔而言合不合理：若它離這檔股票的歷史高低超過三成，直接判定不是股價、整個捨棄，不會拿去往後比對。少了第二道，被誤抓成價位的營收金額有機會在未來某天剛好等於股價而被誤採。

成交日與發話日不同時，回合明細會在價格後面標出觸價日期，個股面板的進場價來源也會寫成類似「張震說漲到某價位賣出，某月某日觸價」的形式，讓兩個日期的差別看得出來。

價位不只從價位說明欄取

張震常常不在價位欄講價，而是在說明重點裡順帶帶過一句，例如提到會員當初在某個價位買進。那同樣是明確的成本，只是位置不同。所以解析時兩欄都會看，價位說明優先，找不到才往說明重點裡撈。

兩欄都套用同一組排除規則：財報與技術線術語（每股盈餘、本益比、均線、季線等）整句不取；數量與金額單位只有在緊接著數字時才排除，這樣「張震」的張字與「說明重點」的點字不會被誤判成成交量與指數點位；概數（某數字加上多、出頭）保留敘述但不給數值，因為拿概數去算報酬等於自己編一個成本。

另外還有一道方向一致性檢查：若某一列的方向是買入，價位說明描述的卻只有賣出動作，那個數字講的是另一件事，不會被拿來當這一筆的成交價。這是為了擋掉擷取階段把兩段不同的話歸到同一列的情況。

技術指標的數字不是價位

說明重點裡最常出現的數字其實不是股價，而是看盤工具的參數：六十分K線、二十日均線、五分鐘線、九週KD。這些數字混在敘述句裡，長得跟價位一模一樣。

先前有一條規則是「整句只有一個數字，就當作它是價位」。那條規則在價位說明欄是對的——那一欄本來就是放價位的，出現一個孤零零的數字，它是價位的機率很高。但套到說明重點就會出事：「股價拉回至低檔區，且六十分K線顯示收斂末端翻揚」這句話裡，六十是唯一的數字，於是它被當成成交價，一路變成某一回合的出場價，算出負十五點多的報酬——而那一天的收盤其實比進場價還高，那一回合是小賺的。

現在分兩層擋。第一層是把技術指標的寫法整段拿掉再判斷：數字後面緊接著分K、分鐘、均線、K線、MA、KD 的，一律不是價位；拿掉之後那句話一個數字都不剩，才是正確答案。第二層是「整句只有一個數字」這條規則只適用於價位說明欄，說明重點不適用——敘述句裡真正的價位一定會帶著動詞或門檻詞（在某價位買進、跌破某價位），那些在前面的規則就已經抓到了；剩下那些孤零零的數字，是天數、季度、名次、技術參數的機率遠高於股價。

參考價位

另外處理一個常見情況：張震第一次講買入時沒有說價位，但後來在某一天以「觀望注意」的語氣提到了這一檔的價格。這個價格有參考價值，但它不是成交價，因為那天並沒有買賣動作。

所以程式會把它抓出來，一樣要通過當日高低驗證，然後以「參考價位」的身分標註在表格與個股面板上，進場價欄位會出現一個灰色的「參」字標記，與明講成交價的「明」字標記在顏色與意義上都分開。參考價位不會被用來計算報酬，它純粹是讓讀者知道張震後來講過這一檔大概在什麼價位。

條件價與回述成本

講者講價位有兩種時態，而且都很常見。先前只處理了其中一種，另一種全部算錯。

時態講法該往哪找
未來式 漲到某價位以上就賣、跌到某價位以下才買 往後找第一個真正觸價的交易日
過去式 會員是在某價位買的、那天某價位連買都買不到 往前找那個價位真正成交過的日子

先前只往後找。於是所有回述成本的講法必然找不到，然後被當成「條件沒成立」退回當日收盤——把講者明確講過的價格丟掉，換成一個他從沒提過的數字，報酬跟著錯，而且從表面完全看不出來。實際發生過某檔講的是一千多元的舊成本、系統卻用了當天兩千多的收盤價。

往前找必須有下限

雙向搜尋修好了一種錯，但也開了另一種。往前找原本一路找到快取的最開頭，而只要範圍夠長，任何價位都能在歷史上找到某一天「曾經成交於此」。

實際出現過這樣一列：某一回合九月四日買入、九月九日賣出，而系統標註的出場成交日是八月四日——比買進早了一個月。賣出不可能發生在買進之前，那筆報酬是憑空生出來的。

所以往前找要帶下限。算出場價時，下限是這一回合實際成交的那一天；算進場價時，下限是上一回合的出場日。回述成本仍然找得到（那本來就是這一回合開始之後、或上一回合結束之後的事），但跨不回不可能的區間。

連帶要改的是「找不到觸價日」時的處理。原本一律採用講者明講的價位，並在來源欄註明查無K線佐證——那個判斷是為「日K快取沒涵蓋到那一段」設計的。但有下限時，搜尋範圍就是這一回合實際存在的那幾天，而那幾天的K線就在快取裡，「沒碰到」不是快取缺漏，是這個價位在這段期間真的沒有成交過。這種情況再採用明講價就是編造，所以改成退回當日收盤，並在來源欄寫明那個數字為什麼沒被採用。

報價這一段最容易出問題的地方

證交所的即時報價介面有速率限制，而且是以來源服務判斷、不是以個別使用者判斷。網站上同時有五個人各查一檔，這五個請求全部從同一個 Apps Script 後端發出，一秒內就疊加超過限制。所以報價做了兩層保護：共用快取把每一檔結果存 25 秒（全站共用，非每人一份），以及一個用 LockService 加鎖的權杖桶，記錄最近數秒的請求，超量就先睡再送。歷史日K快取 6 小時，代號對照表 6 小時並由每週排程實質更新。日K與小時K讀取都改成整張表只讀一次、建索引後重用，避免逐檔查詢時反覆全表掃描拖垮圖表載入。

想深究：持有回合是怎麼算的

會員持股是怎麼判定的

這一段是整套系統最容易被誤解、也最常被回報有問題的地方，所以獨立出來完整說明。先講結論：一檔股票要進入會員持股，必須有一個明確的持有聲明，而這樣的聲明有兩種形式。

開倉方式來源進場價怎麼取
明講買入 影片中說了買進、承接、進場之類的動作 當日收盤；若明講了價格且通過當日高低驗證，改用明講價
會員持股聲明 影片中明講「會員目前持有 X」，也就是信件裡「影片中明講之會員目前持有股票」那一段列出的標的 一律取當日收盤。那天並沒有成交，不存在成交價

第二種是後來補上的。張震有時候不會重述當初的買入動作，只在盤中複述一次會員手上有什麼，那句話本身就是一個明確的持有聲明。少了這條路，這些標的會出現在信件裡卻不在網站上，兩邊對不起來。

反過來說，只被順口點名、只被討論過、或只出現在觀望類的標的，都不算持有。

為什麼以前會出現「觀望不碰」跑進會員持股

舊版有一個看似合理、實際上會出事的設計。當時的想法是：張震有時候只在盤中口述「會員目前手上有 X」，卻沒有對應的當日買入紀錄，這種股票在首頁看得到、持股追蹤卻沒有，兩邊對不起來。為了補這個洞，舊版把「會員持股」分頁裡每一檔第一次被列出的那一天，補成一筆假的買入紀錄，讓它能進入追蹤表。

問題出在首頁的「會員持股」區塊讀的並不是「會員持股」分頁，而是持股追蹤裡狀態為持有中的那些標的。兩件事湊在一起就變成：一檔股票只要在「會員持股」分頁出現過一次，即使它從頭到尾只被講過「這檔不要碰」，也會被補一筆假買入、進入追蹤表、被判定為持有中，最後出現在首頁的會員持股裡，而且方向欄還寫著觀望不碰。資料本身沒有錯，是判定規則把「被提到」誤當成「有持有」。

現在的規則沒有取消這條路，而是替它加上一道防呆：同一天若同時出現持有聲明與觀望不碰（或賣出），這筆持有聲明就不予採信。真正說得通的資料不會在同一天既說會員持有、又說這檔不要碰；會同時出現，幾乎都是擷取階段把兩段不同的話歸到同一檔股票上。寧可少收一檔，也不要讓一檔「不要碰」的股票因為被順口列進清單就變成持有中。

另外，由持有聲明開倉的回合，介面上會用一個橘色的「持」字標記在進場價旁邊，個股面板也會多一列「進場依據」寫明那不是當日成交。這是必要的區隔：那個價格是當天的收盤價，不是張震買進的價格，混為一談會讓人誤判成本。

判定流程

持有聲明的三日確認

用持有聲明開倉有一個先天的弱點：它只需要一句話就能成立。而逐字稿是語音辨識的產物，偶爾會把某個詞誤判成股票名稱，或把一段話歸到錯誤的標的上。這種雜訊只要出現一次，就會在追蹤表裡留下一個永久的假部位，而且因為之後再也沒有它的消息，還會一路撐到逾期規則才被關掉，中間那段時間都在污染統計。

所以由持有聲明開倉的部位要多過一關：開倉之後的三個交易日內，這一檔必須至少再被提到一次，任何形式都算——再次列入持股清單、被討論、被賣出、被歸到觀望，都算數。三個交易日內完全沒有任何後續的，判定為擷取錯誤，整個回合直接移除，不是標記為已出場，是當作它從來沒發生過。

門檻訂在三個交易日，是因為張震每個交易日都在講盤。一檔真的在會員手上的股票，不可能連續三個交易日完全不被提起；反過來說，只孤零零出現一次、之後就徹底消失的，幾乎都是雜訊。

最後那一段是這條規則最容易寫錯的地方。如果不分辨「確認期還沒過完」與「確認期過了但沒有後續」，昨天才講的持股會在今天的重算裡被當成沒有後續而立刻刪掉，等於這條路徑永遠留不住任何東西。所以判定之前會先確認交易日曆上真的已經有三個交易日過去；還沒滿的一律暫時保留，並在出場原因欄標示為待確認，等期限過完，下一次重算才會做出最終判定。

順帶一提，這也讓系統在日K快取落後時自動變得保守：交易日曆是從日K快取推出來的，快取還沒補到最新，可用的交易日就不足三個，所有持有聲明都會停在待確認而不會被誤刪。

要在套用之前先看會刪掉哪些，可以執行 auditUnconfirmedHoldings()。它只讀資料、不寫任何東西，會把每一筆持有聲明分成會被移除、暫時保留、會保留三類列出來，並附上各自最近一次被提及的日期。名單確認沒問題再執行重算。

買了又賣、賣了又買怎麼呈現

同一檔股票被賣掉之後再買回來，是很常見的操作。舊版用一組固定的「首次買入日」與「最近賣出日」來描述一檔股票，遇到這種情況會同時錯三個地方：進場價還停在第一次買入時的價格，於是第二段的報酬完全算錯；持有天數從第一次買入算起，把中間根本沒有持有的空窗期也算了進去；狀態欄則在持有中與已出場之間互相蓋掉，看不出現在到底在不在手上。

現在改用回合模型。程式把每一檔的所有紀錄依時間排序後走一遍，切成數個回合，一個回合就是一次進場到一次出場（或還沒出場）。表格與首頁顯示的一律是最新那一個回合，進場價、持有天數、報酬全部從本回合的進場日起算，過去的回合則另外保留在回合明細裡。

介面上的呈現方式是：狀態欄在回合數大於一時會多一個「第 N 回合」的標記，滑鼠移上去可以看到完整的回合明細；個股面板則會多出一塊「持有回合」，把每一段的進場日、出場日、出場方式與該段的已實現報酬逐條列出。只有一個回合的標的不顯示這些，避免佔版面講一件本來就看得到的事。

除了下午那幾支重活各自佔一個獨立觸發器，其餘全部由一支每五分鐘的排程依時間派工——Apps Script 每個指令碼最多 20 個觸發器，原本剛好裝滿，連全面重整那種一次性觸發器都建不出來。推播不綁固定時刻，而是 12:00 到 22:00 之間每一棒都問一次「今天的內容備妥了嗎」，備妥就寄，寄過就跳過，所以同一天不會重複寄。起點放在 12:00 是因為直播約 12:30 到 13:00 結束，收得早的那幾天影片十二點多就上架，內容可能十二點半就好了；終點拉到 22:00 是因為上游重跑或排隊時文章會落地得很晚，窗口太窄那一天就整天沒有信。告警排在 15:45 是因為輪詢期間狀態本來就是等待中，太早檢查會每天誤報。

探測：先確認有沒有事情要做

排程一天有十幾個觸發點，但盤中直播要到台灣時間下午一點過後才會生成隨選影片。也就是說，中午之前的那幾個觸發點不管敲幾次都不會有東西，卻照樣還原憑證、啟動用戶端、進到輪詢迴圈空轉二十幾分鐘。憑證失效時，這些空跑還會一路報錯洗版——先前看到的兩次失敗，就發生在這種必然空手而回的時段。

所以每個觸發點進來的第一件事改成「探測」：只用影片清單與試算表判斷現在有沒有事情要做，不碰逐字稿服務、不呼叫語言模型、不需要登入憑證，幾秒鐘就有結果。判斷結果決定後面所有步驟要不要執行。

情況判斷理由
週末跳過不開盤，沒有盤中直播
今日影片已處理完成跳過當天工作已經做完，剩下的觸發點都是多餘的
台灣中午之前，影片還沒出現跳過直播還在進行，隨選影片不可能存在，敲門必定空手
已進入等待窗，影片還沒出現執行要進去輪詢，等影片一出現就立刻接手
影片已出現但還沒處理完執行正事
已到收工時間仍無影片執行要跑最後一輪，標記今日無影片

這裡有一個容易做錯的地方：不能一律「沒有影片就跳過」。內部輪詢是這套系統的核心設計，一個工作進來之後每三分鐘敲一次門，敲到影片出現為止；若影片還沒出現就直接跳過，等於把輪詢廢掉，又退回去依賴排程準點觸發，而那正是當初要解決的問題。所以只跳過「確定不可能有影片」的時段，等待窗一開始就照常進去輪詢。

為什麼會撞到配額上限

後台上線初期，工單常在「擷取」或「撰稿」失敗，訊息只有一行 HTTP 429。查下去發現是兩個問題疊在一起，而且第二個才是主因。

錯誤訊息也重寫了。原本只回一行 HTTP 429，看不出是每分鐘請求數爆掉、當日額度用完、還是金鑰失效——而這三種的處理方式完全不同：等一下重跑、等到明天、換金鑰。現在會把伺服器講的原因帶出來（會先遮掉可能夾帶的金鑰片段），並附上對應的處理步驟。

為什麼每一步都要自己看時間

執行環境對單次執行有時間上限。超過時不是拋出例外，是整個執行被直接中斷——這個差別很關鍵：拋例外還能被接住、記錄、排下一棒，被中斷則什麼都來不及做。於是進度沒寫回、下一棒沒排，工作就停在原地，而且完全沒有錯誤訊息可看。

實際症狀就是重算走到一半不動了，介面顯示「處理中」但永遠不會前進。原因是全站重算要做六件事，其中更新基本面與補日K是對外抓資料，檔數多的時候特別慢，整包遠超過上限。

做法結果
一次跑完六件事 超時被中斷，工單卡死，無錯誤訊息，只能人工介入
拆成三段，每段固定做兩件 大部分情況可行，但外部服務特別慢時，單段仍可能超時
拆成三段，且每件事之前先看剩餘時間 不論外部多慢都會持續前進，做不完就交棒，下次接著做

現在採用第三種：每一小段開始前記下截止時間，做完一件事就檢查一次，剩餘不足一分鐘就把進度寫回、排下一棒、結束本次執行。同一套機制也用在整理過去資料與立即刷新上，所以那兩個作業同樣可以關掉頁面、回來再看進度。

為什麼上游不放在 Apps Script

Apps Script 單次執行上限約 6 分鐘，一天總觸發執行時間上限約 90 分鐘。等待 NotebookLM 完成索引這種事情，時間長度不受我們控制，撞上限的機率很高。GitHub Actions 提供原生 cron 排程，公開儲存庫免費且無時數上限，單次工作最長可跑 6 小時，也不需要另外開通付費帳單。所以上游放 GitHub Actions，下游放 Apps Script，各自做自己擅長的事。

登入狀態到期的預警

上游依賴一份 Google 的 session cookie 才能取得逐字稿，而 Google 會定期輪換它，所以過期是遲早會發生、且無法避免的事。真正的問題不是它會過期，而是過去只有在「已經失效」時才會知道，那時候當天的排程都已經白跑了，得等人工發現、重新產生憑證、再手動補跑。

現在在流程開始之前會先看一眼憑證裡的到期時間。每一個 cookie 都帶有到期的時間戳記，取最早到期的那一個來判斷：剩不到三天就在工作紀錄裡發出警告，已經過期則直接標成錯誤並說明本次必定失敗。這樣可以在還能正常運作的時候就先更新，而不是等失敗了才處理。

另外，認證失效的判斷式也已經涵蓋實際會出現的錯誤形狀。這類錯誤重試永遠沒有用，所以一旦認出來就立刻中止並標記為認證過期，不會再留在輪詢迴圈裡每三分鐘重敲一次直到時間預算耗盡。

為什麼登入狀態會時好時壞

這個現象值得說清楚，因為它看起來很像隨機故障：同一份憑證，上午兩次執行失敗並要求重新登入，下午卻在沒有更動任何設定的情況下正常跑完。

原因在於這類登入狀態是會被伺服器輪換的。每用一次，伺服器就可能發一組新的憑證回來，用戶端把新的存起來，下次用新的。在自己的電腦上這個循環是完整的，所以平常用瀏覽器不會突然被登出。

但在自動化環境裡這個循環是斷的。憑證每次都從設定值還原成一個暫存檔，工作結束後連同整台機器一起消失，輪換後的新憑證從來沒有被保存下來。於是每一次執行都拿著同一份、而且越來越舊的憑證去敲門。伺服器對舊憑證通常留有一段寬限期，寬限期內就會時好時壞——這正是上午失敗、下午又成功的原因。等寬限期真的過完，才會轉為穩定失敗。

長久之道：把輪換後的憑證存回去

治本的做法是讓那個循環在自動化環境裡也能閉合。現在的流程是：執行開始時，先從試算表取出上次保存的最新憑證覆蓋掉暫存檔；執行結束時，比對憑證有沒有被輪換過，有變動就存回試算表。設定值裡的那一份從此只是「種子」，第一次執行或試算表還沒有紀錄時才會用到，之後真正在用的一直是最新的版本。

選擇存在試算表而不是設定值，是為了不必額外申請一組可以寫入設定的存取權杖——這支程式本來就有試算表的寫入權限，不引入新的憑證就少一個要保管的東西。代價是這份資料等同於帳號的登入狀態，所以存放的試算表必須維持私有，只分享給本人與服務帳號，絕對不要開成知道連結就能檢視。程式會自動建立這張分頁並在裡面寫上這段提醒。

加上這個機制之後，正常情況下不需要再手動更新憑證。只有在長期完全沒有執行、輪換鏈整個斷掉，或帳號在其他地方被登出時，才需要重新登入一次。搭配前面提到的到期預警，也能在還能運作時就先發現。

其他常被問的

為什麼有些欄位寫著「本支影片未說明」
因為那支影片裡真的沒講。整個專案最重要的一條原則就是只呈現影片中明確講述的內容，沒講到的一律標示未說明，不會用其他日期的資料回補，也不會由模型推測一個看起來合理的答案填進去。看到未說明，代表的是資訊本身不存在，不是網站壞了。
為什麼有些股票顯示「代號待確認」
語音辨識出來的股票名稱有時會有同音字或簡稱，程式會先拿去比對證交所與櫃買中心的代號名稱清單，比對不到就先試近似名稱。仍然無法確定的時候，保留原始的語音文字並標示代號待確認，不會自行猜一個代號填進去。這種情況需要人工看一眼影片確認。
報價是即時的嗎
來自證交所的即時報價介面，但為了保護整個網站不被封鎖，同一檔股票的查詢結果會快取 25 秒。所以你看到的價格最舊是 25 秒前的。歷史 K 線來自證交所與櫃買中心的每日收盤資料，快取 6 小時。
為什麼沒有小時線
日線與週線都是從證交所公開的每日收盤資料算出來的，週線由日線聚合而成。小時線需要盤中逐筆成交資料，證交所的公開介面不提供歷史盤中資料，所以做不出來。如果之後接了付費資料源，這一項可以補上。
平均報酬是怎麼算的
取每一檔被明確講到買入的股票，以買入當日的收盤價為基準，計算到最近一個交易日收盤價的漲跌幅，再取算術平均。正報酬比例是這些標的中報酬為正的檔數佔比。這兩個數字只是歷史紀錄的統計描述，不含任何未來的預期，也沒有計入交易成本、實際成交價與部位大小。
訂閱之後想退訂怎麼辦
每一封信的底部都有取消訂閱連結。訂閱建立時系統會產生一組隨機權杖存在試算表裡，點擊連結後由後端驗證權杖是否相符，相符就把那筆訂閱標記為已取消，之後不再寄出任何信件。連結不需要登入。
問答小幫手會給投資建議嗎
不會。它只能讀取資料庫裡已經整理好的操作紀錄與會員持股，被明確禁止推測、補完、引用資料以外的內容，也被明確禁止提供任何買賣建議、目標價或看多看空的判斷。查不到就會直接說查不到。
如果某天 GitHub Actions 沒跑成功會怎樣
工作會顯示為失敗，試算表的影片清單會寫入明確的失敗原因，當天 15:45 系統會寄一封通知信到站方信箱，內容包含失敗原因與影片網址。網站上當日的資料就會停在最近一個成功的交易日，不會顯示任何猜測的內容。
這個網站能當作投資依據嗎
不能。這裡呈現的是一位分析師在公開直播中講過什麼的整理紀錄，性質接近會議紀錄，不是投資建議，也不構成任何買賣的邀約。實際的投資決策與盈虧，由使用者自行判斷與承擔。
想深究：後台怎麼用

後台：手動投稿逐字稿

上游那條路依賴一份會過期的登入憑證，而重新產生那份憑證需要一台能開瀏覽器的電腦。人在外面只有手機時，整條線就卡住，當天的資料補不回來。後台是為了這種情況準備的第二條路：用手機開逐字稿 App，把內容複製出來貼進後台送出，後面的潤飾、擷取、分類、代號比對、股價更新全部照原本的流程跑完。

兩條路產出的資料格式完全一樣，寫進同樣的分頁，最後都收斂到同一次全站重算。所以網站不知道、也不在意某一天的資料是哪條路進來的。

怎麼進去

網址是網站後面加上 ?page=admin。開啟後只會看到一個登入框，所有內容都要通過密鑰驗證才拿得到，所以這一頁本身可以直接開啟不必隱藏。頁面有標記不讓搜尋引擎收錄。

密鑰就是管理密鑰，與本頁最下方「立即刷新網站內容」用的是同一組，存在指令碼屬性的 ADMIN_KEY。忘記或沒設過時，在編輯器執行 showDeployInfo()，執行紀錄會印出來；沒設過的話它會自動產生一組安全的隨機字串並存好。

今日影片自動偵測

為了不必自己去翻頻道找網址，系統從台灣時間 11:30 起每 10 分鐘查一次頻道的發布清單，找到當天的盤中家教班影片就記下來，後台一開就看得到，按一下直接帶入。只在平日的 11:30 到 17:00 之間動作，這個區間之外查也不會有結果。若當天偵測不到，自己貼網址一樣可以送出。

送出之後發生什麼事

送出只做兩件事就回覆：把原文存起來、建立一張工單。真正的處理由觸發器一步一步做，每次只做一小段，做完把進度寫回工單並排下一棒。前端輪詢工單狀態畫出進度條。

會這樣設計是因為執行環境對單次執行有時間上限。一份兩萬多字的逐字稿要切成好幾段送去潤飾，加上擷取與全站重算，遠遠超過那個上限。切成小步之後每一步都在自己的額度裡跑完，而且中途某一步失敗時，工單會停在那一步並記下原因，可以從那裡續跑不必整份重來。原文在最開始就先落地，所以就算後面每一步都失敗，也不必請人重貼一次兩萬字。

步驟做什麼約略耗時
潤飾逐段整理成書面中文，刪語助詞、補標點、改同音錯字。每次只做一段每段 60 到 90 秒
擷取找出個股的操作與立場，分成買入、賣出、觀望不碰、觀望注意、會員持股約 30 秒
寫入先清掉當天既有的列再寫新的，避免重跑produce重複資料數秒
重算清產業列、代號比對、基本面、日K、持股追蹤、績效1 到 2 分鐘

整份跑完約三到八分鐘，視逐字稿長度而定。處理在伺服器端進行，可以關掉頁面，回來再看進度。完成後網站已經刷新過，不必再按「立即刷新」，也會寄一封通知信。

為什麼不用雲端筆記本環境自動取得憑證

曾經考慮過用雲端執行環境代替本機來重新產生登入憑證，讓手機也能完成。評估後判斷不可行，原因不在技術難度，而在對方的風險控制。

問題說明
機房位址會觸發風險檢查 雲端執行環境的對外位址屬於資料中心，從那裡登入個人帳號會被判定為異常，跳出裝置驗證或二階段驗證。而那些驗證流程本身又需要在受信任的裝置上完成，等於繞回原點。
需要互動式的圖形介面 登入流程要在真實瀏覽器裡完成。要在無螢幕的環境做這件事，得額外架設遠端桌面通道再從手機連進去，環節多、每次都要重來，比直接在後台貼逐字稿麻煩得多。
環境是暫時的 執行階段結束後環境就消失，取得的憑證還是得靠手動搬運，並沒有真正省事。
自動化登入的合規疑慮 以程式代為完成帳號登入流程，本身就處在服務條款的灰色地帶，可能導致帳號被限制。為了省一次手動操作而承擔這個風險並不划算。

所以結論是：手邊只有手機時，正確的做法不是想辦法讓機器代替你登入，而是換一條不需要登入的路。後台就是那條路。至於憑證本身，前面提到的輪換保存機制已經能讓它在正常運作下自動續命，加上到期預警，需要手動重新登入的情況會少很多。

後台走的是同一套流程

後台第一版只做「潤飾、擷取、寫入、重算」四步就結束，看起來合理，實際上把上游最重要的三道把關全跳過了。同一份逐字稿走兩條路進來，品質差很多：分類會亂、名稱對不到代號、價位說明和操作方向互相矛盾。

問題在於那三道才是資料品質的來源。擷取只是把逐字稿裡的東西撈出來，撈得不完整、聽錯的名稱、講錯的價位，都要靠後面的關卡處理。現在後台補齊成十個步驟，與上游一致。

後台的四類作業與進度呈現

後台有四類會跑比較久的作業，全部改成背景分段執行，共用同一套進度呈現：步驟膠囊標出目前走到哪一步、進度條顯示整體百分比、下方是詳細備註。都可以關掉頁面，登入時會自動把既有進度撈回來。

作業做什麼什麼時候用
投稿工單 十個步驟，從潤飾到重算 貼上逐字稿送出後自動開始
整理過去資料 拿新規則回頭掃既有資料：剔除題材與族群、補正同音錯字的代號、修正價位說明、重算持股追蹤 規則更新後想套用到舊資料時。建議先按預覽確認名單
立即刷新網站 六個步驟，重算全站顯示 手動改過試算表之後
會員簡訊補抓與重新解析 Apps Script 驗證管理權限後派送 GitHub Actions；GitHub 自動翻完來源文章，先辨識張震、再篩日期、解析、寫入並逐日稽核；日期不明者獨立隔離 補最近七天、補全部歷史、依文章編號補抓，或提示詞更新後重跑解析

立即刷新原本是一次同步跑完，前端要乾等一到兩分鐘，常常超過網頁請求的等待上限而顯示連線失敗——但後端其實還在跑，很容易誤判成壞掉。改成分段之後這個問題就消失了。

錯誤訊息要說「該怎麼修」

只講「發生什麼」對現場的人沒有幫助。失敗時進度區塊下方會多一段處理指引，把常見的失敗形態翻成具體的下一步。同一份說法後台與通知信共用，免得兩邊講得不一樣。

失敗形態指引內容
每分鐘請求數上限等一到兩分鐘按續跑，前面完成的不必重做
每日額度用完今天無法再呼叫，明天續跑或升級金鑰方案
金鑰無效到指令碼屬性檢查，說明在哪一頁、注意前後空白
輸出被截斷會自動用精簡指示重生一次，仍失敗就分兩次投稿
暫存逾時重新送出同一份逐字稿即可
對照表是空的先執行重建對照表的函式，再回來續跑
單步逾時按續跑會從中斷處接著做，不會從頭來過

其中配額上限特別區分成「每分鐘」與「每日」兩種，因為處理方式完全不同：前者等兩分鐘就好，後者要等到隔天。先前混在一起講，反而把人引導到錯誤的方向。

我現在就想更新網站，不等下個交易日

這裡有一件常被搞混的事，先講清楚會省下很多困惑：整理資料與更新網站是兩件事，發生在兩個不同的地方。

上游的 GitHub Actions 改的是試算表。它把資料整理好、寫進去，工作就結束了。下游的 Apps Script 才是把試算表算成網站看到的樣子，包括重算持股追蹤、補日K、更新基本面、記錄績效。所以只在 GitHub 按 Run workflow，試算表確實會變，但網站畫面不會立刻跟著變，要等下游排程（平日 14:50 那一輪）跑過才會。這就是「我明明改完了，網站怎麼還是舊的」的原因。

要立刻看到更新，有三個入口，擇一即可。

方式怎麼做適合什麼情況
網站管理入口 本頁最下方輸入管理密鑰，按「立即刷新網站內容」 資料本身沒問題，只是想讓畫面重算一次。不需要開 GitHub 也不需要開 Apps Script。
GitHub 一次到底 Actions → Run workflow，勾選要跑的模式，並把 refresh_site 也設為 true 要先整理資料再更新畫面。整理完會自動通知下游重算，不必再手動按一次。
Apps Script 編輯器 直接執行 refreshSiteNow() 前兩種都失效時的備援，或想看完整的執行紀錄。

如果只想刷新畫面、資料完全不要動，在 GitHub 就只勾 refresh_site、其他都不勾。程式偵測到沒有選任何模式時，會跳過抓影片的整個流程，只送出刷新指令就結束。

refresh_site 需要兩個 Secret 才會動作：APPS_SCRIPT_URL 是網頁應用程式的部署網址，ADMIN_KEY 必須與 Apps Script 指令碼屬性裡的那一組完全相同。少了任一個，程式會印出提示並安靜略過，不會影響已經寫進試算表的資料。刷新本身要一到兩分鐘，失敗也不會讓整個工作亮紅燈，因為資料已經存好了，晚一點由排程刷新一樣會正確。

運作方式是 pipeline 在流程結束後，對下游的網頁應用程式發一個帶密鑰的請求，下游驗證密鑰後才執行重算並回傳結果。密鑰不正確時只會拿到一個拒絕的回應，不會觸發任何運算，也不會洩漏任何內容。

那兩個 Secret 要去哪裡拿

第一次勾 refresh_site 時，執行紀錄多半會出現「缺少 APPS_SCRIPT_URL 或 ADMIN_KEY，本次略過刷新」。這不是壞掉，是這兩個值還沒設定。它們分別藏在兩個不同的地方，所以分開說明。

最快的做法：到 Apps Script 編輯器，在函式下拉選單選 showDeployInfo 按執行，然後看「執行紀錄」。這支函式會把兩個值一次印出來，還會順便檢查網址型態對不對、幫你產生還沒設定的密鑰、並給你一個可以直接貼到瀏覽器測試的網址。不想手動翻的話看這一支就夠了，下面兩小節是說明它印出來的東西是什麼。

APPS_SCRIPT_URL　網頁應用程式的部署網址

這是這個 Apps Script 專案對外的入口網址，也就是平常打開網站時看到的那一串。取得方式：Apps Script 編輯器右上角的部署按鈕 → 管理部署作業 → 選中間那個「網頁應用程式」區塊 → 複製底下的網址。

格式長這樣，中間那串英數字每個專案都不同：

正確與否網址結尾說明
要用這個 /exec 正式部署的網址，任何人都能存取，GitHub 打得進來。
不能用 /dev 開發測試網址，只有你本人登入 Google 帳號時才開得起來。GitHub Actions 沒有帳號可以登入，會被導到登入頁。

還有一個容易漏掉的設定：部署對話框裡的「誰可以存取」必須選「所有人」。這個專案本來就是公開網站，通常已經是這個設定；但如果曾經改成「僅限自己」，GitHub 過來的請求會被 Google 攔在登入頁，拿回去的是一頁 HTML 而不是預期的結果。

另外要注意版本。貼上新的程式碼之後，部署中的版本不會自動跟著更新，必須到管理部署作業 → 編輯（鉛筆圖示）→ 版本選「新版本」→ 部署。沒有做這一步的話，遠端刷新入口雖然寫在程式碼裡，但線上跑的還是舊版，請求會落到一般的網頁路由上，回傳網站首頁的 HTML。程式偵測到這種情況時會直接告訴你要重新部署。

ADMIN_KEY　管理密鑰

這個常被誤會，所以先講清楚：ADMIN_KEY 是你自己訂的一串字，不是 Google 或任何人發給你的。它的作用是一道門鎖，讓只有知道這串字的人才能觸發重算，避免任何人打開網址就能讓伺服器跑一輪運算。

查看或設定的位置：Apps Script 編輯器左側的專案設定（齒輪圖示）→ 捲到最下面的指令碼屬性 → 找 ADMIN_KEY 那一列。

情況怎麼做
已經有 ADMIN_KEY 直接複製那一列的值。這也是網站管理入口在用的同一組密鑰。
沒有這一列 執行 showDeployInfo()，它會自動產生一組夠長夠亂的隨機字串並存進去，同時印出來給你。也可以自己按「新增指令碼屬性」，名稱填 ADMIN_KEY，值自己取一組別人猜不到的字串。

複製時要留意，GitHub Secret 裡填的必須與指令碼屬性裡的一模一樣：大小寫相同、前後不能多出空格或換行。從執行紀錄複製時很容易連尾端的換行一起帶走，貼上後檢查一下。兩邊對不上時，端點會回一個明確的拒絕訊息，程式會提示你去比對這兩處。

填到 GitHub 的哪裡

到儲存庫的 Settings → Secrets and variables → Actions，按 New repository secret，建兩筆。名稱要完全照下表打，全部大寫、用底線，打錯一個字元程式就讀不到。

Secret 名稱值長什麼樣從哪裡來
APPS_SCRIPT_URL 一串 https 網址，/exec 結尾 Apps Script → 部署 → 管理部署作業
ADMIN_KEY 一串你自己訂的英數字 Apps Script → 專案設定 → 指令碼屬性

Secret 存進去之後就看不到內容了，只能覆蓋不能查看，這是 GitHub 的設計。所以 ADMIN_KEY 建議自己另外留一份，網站的管理入口也要用到同一組。

怎麼確認設好了

不必真的跑一次工作流程。showDeployInfo() 的執行紀錄最後會給你一串完整的測試網址，把它貼到瀏覽器網址列就能直接驗證：

出現 {"ok":false 並說密鑰不正確 端點通了，但密鑰對不上 回頭比對指令碼屬性與網址裡的那一段是否相同
出現網站首頁 部署中的版本還是舊程式碼 管理部署作業 → 編輯 → 版本選新版本 → 部署
跳到 Google 登入頁 部署的存取權限不是「所有人」 管理部署作業 → 編輯 → 誰可以存取改成「所有人」

刷新本身要跑一到兩分鐘，因為它會依序補日K、更新基本面、重算持股追蹤與績效。瀏覽器在這段時間看起來像是卡住，那是正常的，等它跑完就會回傳結果。

最後補一句：這兩個 Secret 只影響「跑完自動刷新」這個便利功能。沒有設定的話，資料整理完全不受影響，照樣會正確寫進試算表，只是要自己用網站管理入口或 refreshSiteNow() 刷新一次而已。

另外在 Apps Script 端可手動執行的常用函式：refreshSiteNow() 一鍵重算全站；purgeIndustryRows() 立刻移除記憶體、台塑集團這類產業列；auditUnconfirmedHoldings() 乾跑列出持有聲明的確認狀態、看看重算會移除哪些（不寫資料）；rebuildHoldingsTrackerJob() 重算持股追蹤、持有回合與逐日說明；backfillDailyKJob() 補日K快取；installTriggers() 重裝所有排程；statusReportJob() 立即寄一封爬取狀態信；auditDigest("YYYY/MM/DD") 稽核某天推播與網站是否一致；reviewDay("YYYY/MM/DD") 只複審某一天，列出改分類與刪除了哪幾筆；runGateNow("YYYY/MM/DD") 立刻把某一天的品質關卡（稽核、複審、重寫每日整理）跑完。

管理功能在哪裡

管理相關的操作全部收在後台，包括手動投稿逐字稿與立即刷新網站內容。這樣公開頁面上就不會出現任何需要密鑰的輸入框，管理入口也只有一個，不必記哪個功能在哪一頁。

從導覽列最右邊的後台進去，用管理密鑰登入。密鑰存在 Apps Script 指令碼屬性的 ADMIN_KEY；忘記或沒設過時，在編輯器執行 showDeployInfo()，執行紀錄會印出來，沒設過的話它會自動產生一組。登入時可以選擇在這台裝置記住密鑰，下次自動填入。也可以完全不透過網頁，直接在編輯器執行 refreshSiteNow()，效果與後台的刷新按鈕相同。

郵件與網站看到的是同一份

每日整理只產生一次，寫進同一張分頁的同一個欄位。網站的郵件查詢與寄出的推播信都從那裡讀，而且用同一支函式轉成網頁格式。所以兩邊的內容必然一致，不會出現信裡有、網站上沒有的情況。

唯一的差別是推播信會額外附上每位訂閱者專屬的取消訂閱連結，網站查詢頁不會有——那是必要的差異。

資料長期會怎麼樣

Google 試算表的儲存格數有上限，操作紀錄、每日推播內容、影片清單這三張表每天都在長。所以每年 1 月會有一個排程醒來，把上一年度的資料整列搬到獨立的封存分頁，例如 操作紀錄_2026，主要工作表只留當年度資料，另外在資料索引分頁記下每個封存分頁涵蓋的期間。所有寫入都經過 LockService，因為 GitHub Actions 和網站有機會同時對同一份試算表動手。

版本沿革

每一次比較關鍵的調整與原因，已經移到後台的「版本沿革」分頁。 那份紀錄的讀者只有維護的人，放在這裡對來查內容的訪客是雜訊，而且它會一直變長。

為什麼做這個

做過一套 Multi-Agent 股票分析系統，用五個 LLM 角色產出買賣建議。那個專案讓我看清楚一件事：模型很會寫出讀起來很有道理、但底下什麼都沒有的分析。它不會告訴你哪一句有根據、哪一句是它自己補的。
