## 兩輪結果為何差這麼多

兩份日誌的原文都是 24438 字、SHA256 05bd4602b379812d4e2dafe27cae87b64fda61287d7c3b6c8c876683b7aa4bd8，不是讀到不同原文。第一輪覆核 JSON 失敗，缺口未完整記錄；第二輪擷取因缺九類欄位／JSON 語法重試兩次，每次生成可能產生不同候選。全文覆核仍會受初稿影響，再加上本機語氣改判與 M31 被誤刪，導致發布 10 筆與 20 筆的落差。筆數更多不能證明較正確。這次對話提供的是日誌，未取得 9/14 原始 txt，無法逐句確認裕隆、鴻準是否真的明講持有。

## 本次修正

1. 判讀前先載入原本就需要的官方名稱表，建立 source_inventory（原字、官方代號、來源段落）。全文擷取與既有覆核共用盤點，兩轮都遺漏的名字也會產生明確缺口；不自動把名稱命中變成持股／買入，不強制湊相同筆數。純舊推薦仍依原文排除，不從前版復活。
2. 擷取與全文覆核請求使用 responseJsonSchema，要求完整九類陣列，空陣列合法；市場欄不硬套個股欄位。schema 只約束結構，不保證語意正確，原句與數字校驗仍保留。短名稱釐清、教學補問、其他 Gemini 用途維持各自格式。Gemini API 官方格式：https://ai.google.dev/api/generate-content#v1beta.GenerationConfig 。
3. 覆核漏回類別時拒絕整份回應，不再把漏回欄位默認成空陣列；擷取只有解析錯誤才走格式重試，Timeout 等由既有傳輸層處理，不套三次全文重試。原有 503 換鑰匙與暫時性刷新續跑不變。
4. 官方清單中的 M31、AES-KY 等英文簡稱不再被無中文字規則誤刪；HBM 等無官方命中的縮寫仍排除。不加入未核對的固定代號。
5. 保留 v15 的 Fugle 分段取完整區間、每 25 檔落地、代號游標與自動續跑、持股回合及弱正面語氣修正。逾期出場取最後提及日收盤，當天缺 K 只往前找。本次補擋非正數收盤、未來交易日，並更正前台「同日觀望不碰會作廢持股」的過時文字。
6. 保留先前已完成：會員持股專區、20 字內內容標題、盤勢與教學至少三點的合併補問（不足留稽核不補造）、誤字括注與主詞清理、ETF 與個股價位歸屬、漲跌金額不作股價、短價位不換行、非同步過期回應與誠實進度。

## 效率與穩定性邊界

盤點在本機完成，沒有新增模型呼叫；官方清單提前載入後同輪重用。仍保留一次全文覆核、有缺口才再覆核一次、③⑤不足合併補問一次。現有 UTF-8 保守預算與完整來源分批保留，schema 落在既有 4096 預留開銷內；24396 字基本長稿單批回歸通過，實際附帶候選變多時仍可能依預算分批。沒有為了表面一致而快取未驗證結果，也沒有強制把新版改成前版分類。模型仍可能產生語意差異，需以原文證據確認；不能承諾每次逐字相同。

## 詳細部署步驟

1. 先備份現有 GAS 專案、試算表與 GitHub 分支。這份套件是完整交付，不要只貼本次改動的兩三個檔案而遺漏前面尚未部署的版本。
2. 解壓 release/zhangzhen-quality-v16.zip。GitHub 更新 pipeline/pipeline.py（正本）、根目錄 pipeline.py、兩份 requirements.txt 與 .github/workflows/daily.yml；其餘 scripts、tests、docs 可一併提交方便追蹤。兩份 Python 必須一致。不要上傳金鑰或憑證。
3. 本機後續有修改時先執行 python -X utf8 scripts/sync_quality.py，再執行 python -X utf8 -m unittest discover -s tests -p "test_*.py"；本次已完成。
4. 開原試算表 → 擴充功能 → Apps Script。按上面清單逐檔整份替換；.gs 用指令碼檔、.html 用 HTML 檔。原有 Code.gs 也整份替換，不能把新模組貼在舊大檔後面。
5. 儲存；保留 appsscript.json、試算表 ID、GitHub repo/ref、Webhook/API Secret 等既有屬性。執行 checkSetup 檢查，只有缺分頁才執行 addMissingSheets，不重新初始化清空資料。
6. Python/GAS 保留 gemini-3.5-flash-lite、GEMINI_THINKING_LEVEL=medium；清查 GEMINI_MODEL_2 等是否仍指定舊模型。並非提高到 high 就能保證穩定，這次不增加思考層級。GAS GITHUB_REF 必須是剛更新分支。
7. Apps Script 右上「部署」→「管理部署作業」→編輯既有網頁應用程式部署→版本選「新版本」→部署。維持原有執行者／存取權限，網址不變。打開原 /exec?action=ping，build 應為 2026-09-14-quality-v16。
8. 保留既有 everyFiveMinJob、14:35 backfillDailyKJob 與 GitHub 13:45 補 K 排程。不要重複安裝觸發器。若剛升級 Fugle 修正而舊快取只有 46 天，先 auditDailyKCoverage()，確認無正在寫入，再 resetDailyKCursor() 一次、backfillDailyKJob() 一次；用 backfillDailyKStatus() 查看，不要不斷重按。已有新進度正常跑時不重設。
9. 補 K 完成後，再 auditDailyKCoverage() 確認涵蓋區間；依序執行 rebuildHoldingsTrackerJob()、rebuildPerformanceHistoryJob()。用 explainHoldingsTracker('9958') 檢查世紀鋼：最後提及 8/10 時，逾 10 交易日後以 8/10 收盤結算；若缺當日 K，明示採更早日期，不能用 9/14 現價。價格須依正式 K，不能用截圖中的 121 敘述或即時報價猜。
10. GitHub Actions 先跑 check_keys=true 確認模型／金鑰。這項會花少量額度，且僅是基本健檢；新九類 schema 的完整相容性須由下一步真實工單確認。
11. 後台重新投稿 9/14 原稿、勾補登（若已跨日）與覆蓋，只跑一次。先確認 SHA256 與日誌一致，再看「原文名稱盤點」「稽核補漏後」「語氣核對」「最終分類」、逐項待複核／篇幅提醒。檢查 M31、裕隆、鴻準等的實際原句；不要以 20 筆為必須達到的答案。不跑 reclassify 全歷史模式。
12. 本輪完成後再決定是否依序覆蓋 9/10、9/11。套新 Prompt 需重新投稿，單按舊工單續跑只續刷新。CMONEY-、MANUALENTRY- 與已寄送狀態保留；已寄出的信不自動重寄。後台「修改」舊逐字稿列仍可能被覆蓋，需永久保留者用人工新增。
13. 手機與桌面強制重新整理，核對會員持股、個股、郵件、進度；內容完成與日 K／績效背景未完成分開顯示。暫時性 404 等待續跑時不要反覆投稿。
