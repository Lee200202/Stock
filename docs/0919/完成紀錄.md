## 零、一句話總結

把「逐字稿」這一段從**需要人每天貼**，改成**排程自動取得並接進既有的潤飾稽核流程**，
過程中發現原本規劃的取稿方式對這個頻道根本走不通，整條路徑重做。

## 一、最重要的發現：NotebookLM 這條路走不通

起初的需求是「用 NotebookLM 抓逐字稿」。實際查證後發現：

| 項目 | 事實 |
| --- | --- |
| NotebookLM 匯入 YouTube 時讀什麼 | 影片的**字幕** |
| 這個頻道的影片有沒有字幕 | **沒有**，連 YouTube 自動產生的都沒有 |
| 結論 | 登入狀態再新也拿不到。**不是「會過期」，是走不通** |

在發現這件事之前，已經先做了一整套 NotebookLM 的憑證續命機制
（cookie 輪換寫回試算表、Secret Manager 版本化、Cloud Run 部署、Cloud Shell 登入腳本）。
那些全部作廢並刪除——方向錯了，修得再好也沒用。

**改用 Gemini API 直接讀公開的 YouTube 網址**，由模型自己「聽」聲音聽打。
做法取自使用者自己那份可運作的 `notebooklm_test` 專案。

連帶解決了原本最痛的問題：**再也沒有會過期的憑證**。
API key 不會過期、服務帳號金鑰也不會，整套沒有需要定期重新登入的環節。

### 順帶更正的一個誤導

曾經照 cookie 的 `expires` 欄位印出「登入憑證還有約 314.8 天」。
實測那份 `storage_state.json` 檔案停在 2026/07/30、早就失效了，
而 `SIDCC` 仍寫著 314 天，另外幾個 `expires` 是毫秒時間戳、換算出來是幾萬年後。

**Google 是在伺服器端讓 session 失效的，跟 cookie 上的到期日無關。**
任何「還剩幾天」的推算都是假的。那個訊息會把排查方向整個帶偏。

### 2-2　兩套機制，手動永遠優先

「影片清單」新增 `逐字稿來源` 欄：

| 值 | 誰寫的 | 自動抓取的行為 |
| --- | --- | --- |
| `手動` | 人貼的 | **完全停手**，不覆蓋、不重抓 |
| `手動保留` | 人宣告「今天我自己貼」，還沒貼 | **完全停手**，等人 |
| `自動` | `transcript.py` 抓的 | 已有稿就不重抓 |
| （空白）且已有原文 | 舊資料 | **視同手動**，停手 |

最後一列是刻意的。這一欄是後來才加的，在它之前試算表裡所有原文都是人貼的；
把「沒標來源」當成自動，就等於允許機器覆蓋人工成果——
**那是這支程式唯一真正不可逆的傷害。**

判斷順序上，手動優先排在 `tick()` 的**第一關**：在查 YouTube、呼叫 Gemini 之前就擋掉，
所以已經貼好稿的日子一毛額度都不會花。

### 2-3　國定假日不執行

原本只判斷星期幾，國定假日落在平日時市場休市、沒有直播，系統仍會照跑、
照判「今日無影片」、照寄狀態信。那些信是假的，看久了會把真正的異常一起忽略。

清單直接從證交所 API 取得（不憑記憶寫，寫錯一天會讓系統安靜跳過真正的交易日）。
2026 年共 **24 天**，並處理了一個陷阱：證交所把「春節前最後交易日」
「春節後開始交易日」與休市日混在同一份資料裡，**那三天是正常交易日**，沒濾掉會多關三天市。

三個判斷點全部接上：`transcript.py`、`pipeline.py`、`MailService.gs`。

> **沒收錄的年份一律當成交易日**，並在日誌印提醒。
> 反過來做會讓整年排程安靜停擺、毫無錯誤訊息；多跑一天只是一次空跑，兩者不對等。

最近會用到：**2026/09/25（中秋）、09/28（教師節）都休市**。

### 2-4　說明重點補上逐字稿依據

簡訊本文常常只有一句「晶心科連續大漲，務必抱牢」，寫進網站與郵件後讀的人看不出為什麼。
原本的提示語寫死「不得補入原簡訊沒有提供的」，它只能看那一句。

改成：**當天有逐字稿時，撈出提到同一批個股的句子當依據**。邊界守三道：

1. 只撈**簡訊真的點名、而且逐字稿真的講過**的那幾檔（實測「台積電」講稿有、簡訊沒點名 → 正確排除）
2. 摘錄標明「不得據此新增或刪除任何一檔」
3. 沒有逐字稿、或稿裡沒提到這檔 → **完全照舊**

另處理 KY 後綴：對照表寫「譜瑞-KY」但簡訊只說「譜瑞」，不脫後綴整檔會漏撈。

## 三、修掉的 bug

### 3-1　串流模式一個字都收不到（實測踩到）

`gemini-3.5-flash-lite` 不支援背景模式會改走串流，但事件解析寫錯了：

| 原本寫的 | 實際的形狀 |
| --- | --- |
| `event.delta` | `event.event_type == "step.delta"` → `event.delta.text` |
| `event.status` | `event.event_type == "interaction.completed"` → `event.interaction.status` |

結果 `parts` 永遠是空的，每一段都被判成「無輸出」而失敗，
訊息只說「狀態 in_progress」，**完全看不出是解析錯了**——三把金鑰輪完才放棄。

一併補上原本漏掉的：

- **串流中途斷線接續**（實測約 4 分半會斷一次）：用 interaction ID + last_event_id
  從中斷處續收，已收到的文字保留，不重送影片、不多花額度
- **背景模式逾時前先 `cancel`**：否則工作還在跑、還在計額度

### 3-2　模型負載過高時一直在換金鑰（2026/09/17 的失敗）

日誌顯示兩把金鑰輪流重送同一個 `high demand` 的模型，四次全敗、耗掉 11 分鐘、整集失敗。

**`high demand` 是模型層級的壅塞，所有金鑰共用同一份容量，換金鑰不可能有用。**
改成：

| 失敗類型 | 反應 |
| --- | --- |
| 負載過高（high demand / 503） | **立刻換模型**，不換金鑰 |
| 額度用完（429 / 每日額度） | 換金鑰；全用完再換模型 |
| 探測逾時 | 視為壅塞訊號（門檻 20→30 秒） |

配套三項：所有模型都忙 → 判「還沒好」交給輪詢重試（不亮紅燈）；
已完成的片段跨輪保留；探測通過不代表大請求會成功（小請求不佔容量）。

### 3-3　gspread 6 的例外型別

`open_sheets` 只接 `APIError`，但 gspread 6 把 **403 換成內建的 `PermissionError`**
（訊息還是空的）、404 換成 `SpreadsheetNotFound`。於是最常見的兩種狀況完全沒被接到，
使用者看到一長串 traceback，看不出「要去分享試算表給誰」。

現在會直接印出該分享的服務帳號信箱與操作步驟。

### 3-4　根目錄與 pipeline/ 的模組名衝突

根目錄的 `pipeline.py` 會以模組名 `pipeline` **蓋過** `pipeline/` 這個命名空間套件，
於是 `from pipeline.market_holidays import` 去載入了 `pipeline.py`，
直接爆「缺少環境變數 SPREADSHEET_ID」，而且看不出是名稱衝突。

改成只留 `pipeline/` 底下一份，順便消掉原本「兩份副本要靠人同步」的負擔。

## 四、我自己造成、後來修正的錯誤

記在這裡是因為它們都花了時間，而且模式值得記住。

| 錯誤 | 後果 | 修正 |
| --- | --- | --- |
| 端對端演練用「過去／未來日期」當標的 | 第 2、4 幕停在「日期還沒到」就返回，**根本沒走到 YouTube**，但退出碼 0 看起來全過 | 改用今天當標的；驗「它是為了什麼理由結束的」而不只是退出碼 |
| 備援模型預設填了沒驗證過的名字 | 模型不存在會回 404，而 404 是不重試的硬失敗，備援變成必定失敗的一步 | 預設留空；`check` 會列出金鑰實際可用的模型讓使用者挑 |
| `pipeline.py` 的 import 退路用 `sys.path.insert` | 把 `pipeline/` 永久插進搜尋路徑，同程序後面的 `from pipeline import ...` 全部找不到 | 改用 importlib 依路徑載入，不動全域狀態 |
| 刪 `pipeline.py` 死碼的腳本用「搜尋第一個」定位 | 多刪了 8 行無關程式碼 | 從備份還原，改成先列出每一行核對、確認無重疊才寫入 |
| 文件裡的範例專案 ID 寫得像真的 | 使用者直接複製貼上，卡在權限錯誤 | 改用角括號佔位，並在腳本加上「專案存取不了」的明確指引 |

## 六、排程現況

### 取稿（`transcript-gemini`）

| 觸發點（台北） | UTC cron |
| --- | --- |
| 11:05、11:30、11:55 | `5,30,55 3 * * 1-5` |
| 12:20、12:45 | `20,45 4 * * 1-5` |
| 13:10、13:35 | `10,35 5 * * 1-5` |

間隔固定 25 分鐘，接上內部輪詢的時間預算，一棒接一棒不留空隙。

**起點為什麼是 11:05。** 實測最近五集「進入頻道清單」的時間：

| 9/14 | 9/15 | 9/16 | 9/17 | 9/18 |
| --- | --- | --- | --- | --- |
| 11:15 | 11:07 | 11:04 | 11:24 | 11:18 |

影片在直播**結束時**才進清單，不是開播時。早收的日子 11:07 就抓得到，
用 11:20 起跑會白等十幾分鐘。

> cron 與程式的 `POLL_START` 必須一起改。只改 cron 的話那一輪會停在
> 「還沒到 11:20」而空轉——看起來有跑，其實什麼都沒做。有測試在驗這兩者一致。

### 交棒到潤飾稽核

兩支程式不互相呼叫，只透過試算表的「原始逐字稿內容」欄溝通。
`pipeline.py` 的 `stage_transcript` 只要看到原文 > 200 字就往下走，**沒有任何人工步驟**。

週一的預期時間軸：

```
10:00   直播開始（此時影片還沒進頻道清單）
11:0X   直播結束 → 影片進清單 → 回放處理中
+5 分   回放就緒 → Gemini 切 3 段聽打（10～15 分）
11:25   逐字稿寫進「影片清單」F 欄，來源=自動
11:26   daily.yml 輪詢敲到原文 → 自動進潤飾
11:30   擷取 → 稽核 → 代號 → 寫操作紀錄／會員持股 → 撰稿
12:00+  Apps Script 每 5 分鐘檢查，備妥就寄推播
```

最壞情況（11:24 才進清單 + Gemini 跑 20 分 → 11:49 落地）：
`daily.yml` 的 11:20 那輪跑到 11:45 沒接到，11:35 那輪排隊接手，11:50 接到，
仍在 12:00 寄信窗之前。
