# v60：取消卡住的更新工單並重建績效

這次錯誤不是 GitHub Actions 執行仍在跑。最新失敗執行已結束；Apps Script 的 `dayEditSyncV1` 工單仍標為「處理中」或「等待續跑」，因此新的 `performance` 請求被拒絕。只取消 GitHub Actions 執行無法清除此狀態。

## 本次修改

- 後台取消入口現在也接受「等待續跑」的工單。以前這個狀態會擋住績效重建，卻不能由取消按鈕解除。
- `day-sync` 的 `op=cancel` 必須帶讀取狀態時取得的工單 ID。若期間已換成另一筆工單，取消會拒絕，避免誤停新工作。
- GitHub `day-edit-sync` 新增 `cancel` 與 `cancel-performance` 兩個手動模式。後者先取消原工單，若原步驟仍活著，等它收尾後才建立新的績效工單。每次操作都核對取消結果。
- 單純選 `performance` 時，如有逐日更新工單，會給出明確處理方式，不再印 Python traceback；若已是同一筆 `PERF-` 工單，會接續既有進度。

## 部署檔案與順序

1. 本機 Apps Script 專案更新以下三檔，保留其餘最新修改：`apps-script/Evidencequality.gs`、`apps-script/Config.gs`、`apps-script/Setup.gs`。這些檔案**沒有放在 GitHub**，因為 GitHub 倉庫目前只保留 Actions 所需的 Python 與 workflow。
2. 在原 Apps Script 專案儲存，執行 `checkProjectFiles()`；確認 Config 與 Setup 均為 `2026-09-24-day-sync-cancel-v60`。以現有網頁應用程式部署建立**新版本**，沿用原部署 ID 和 `/exec` 網址；不要另建一個不同網址的部署。
3. 開啟正式 `/exec?action=ping`，確認 `build` 為 `2026-09-24-day-sync-cancel-v60`，`features` 含 `day-sync-cancel-v60`。若仍是 v59，GitHub 新模式尚不能執行。
4. GitHub Actions 程式檔為 `.github/workflows/day-sync.yml` 與 `scripts/day_sync.py`，推送 main 後才會出現新模式。進入 [day-edit-sync](https://github.com/Lee200202/Stock/actions/workflows/day-sync.yml) → **Run workflow** → 選 `cancel-performance`。這會放棄原工單尚未完成的步驟，然後從 2026/07/08 重算持股追蹤、歷史績效並記錄目前績效。已完成的原工單資料不回滾；不會重寄已寄郵件。
5. 如果只想先解除佔用、暫不重算，選 `cancel`。若今天的逐日編輯尚未同步郵件，取消後回後台重新安排該日同步；不要以績效重建成功當作郵件也已更新。
6. 在 Actions 日誌確認 `已取消 DAY-...`，隨後 `PERF-...` 到「完成」。再於後台查看工單進度與績效日期。`cancel-performance` 若遇到新工單插入會停止並報錯，不會再次取消別人的新工單。

目前正式站 ping 仍為 v59；本次沒有管理密鑰的登入狀態，所以沒有代替管理者取消正式 Apps Script 工單、部署 GAS，或重建正式績效。GitHub Actions 第 15 次失敗執行已終止，無需取消它本身。
