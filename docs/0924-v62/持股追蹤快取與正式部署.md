# v62：持股追蹤快取與正式網站版本

2026/09/24 的 `snapshotPerformanceJob()` 執行紀錄顯示「持股追蹤清單 106811 字元，超過快取上限，這一次不快取」及「已記錄 2026/09/24 的績效」。**這不是績效失敗**：每日績效已寫入；只是 `getHoldingsTracker()` 這次直接從試算表計算，未把整份清單暫存，後續讀取可能較慢。不必因此重跑 `snapshotPerformanceJob()`。

原因是同一批追蹤項目同時放在 `items`、`held`、`exited` 三個陣列，寫快取時序列化了重複資料；程式又以 JavaScript 字元數估算限制，中文在 CacheService 中實際佔用較多 UTF-8 位元組。v62 保持 API 回傳內容不變，快取只存一份項目清單，讀回時重建持有／已出場陣列。若單份仍大於安全位元組上限，會分段寫入快取，全部寫好後才寫索引；任一分段被清除或寫入失敗時會改讀試算表，不影響頁面與績效結果。

## 目前先做什麼

1. 確認試算表「每日績效」分頁已有 `2026/09/24` 一列，平均報酬 `-0.84%`、正報酬比例 `58.3%`。這兩個數字來自您剛執行的紀錄；不要只憑日誌推定網站也已更新。
2. **不用再執行** `snapshotPerformanceJob()`、`repairRecentTrackedDailyKNow()` 或整輪重算來消除這行快取提示。它是讀取速度問題，並非資料寫入錯誤。
3. 正式 `/exec?action=ping` 在 18:27 曾回報 v60；重試後於 18:30 已回報 `2026-09-24-recent-k-price-v61`，表示 v61 網頁部署已生效。Apps Script 編輯器執行函式會更新試算表，但**不會自動切換正式網頁的部署版本**；v62 的快取修正仍須完成下方部署。

## 部署 v62

部署包 `release/zhangzhen-tracker-cache-v62.zip` 包含完整的 v61 近期日 K 與計價修正，再加 v62 快取修正。內有五個 Apps Script 檔案：`Cachebuilder.gs`、`SheetService.gs`、`JavaScript.html`、`Config.gs`、`Setup.gs`。不需改 GitHub Actions 或 Python。

1. 在**原本的** Apps Script 專案替換上述五檔並儲存。不要用較舊的 v60／v61 壓縮包覆蓋其他新修改。
2. 在 Apps Script 編輯器執行 `checkProjectFiles()`，確認 `build` 與對應版本都是 `2026-09-24-tracker-cache-v62`，沒有缺檔或版本不一致。
3. 到「部署」→「管理部署」→目前正式網頁應用程式旁的鉛筆→「版本」選**新增版本**→部署。沿用原部署 ID 和 `/exec` 網址。
4. 開啟原網址加 `?action=ping`，確認 `build` 是 `2026-09-24-tracker-cache-v62`，`features` 含 `tracker-cache-v62` 與 `recent-k-gap-price-v61`。再重新整理網站「持股追蹤」與個股頁；第一次讀取會建立精簡快取，之後的讀取使用快取。若單份仍偏大，執行紀錄應看到「分成 N 段快取」，不再是 106811 字元整份略過。

v62 離線回歸已核對完整清單、持有／已出場分類、逐日說明及單檔回合資料在快取讀回後都保留，分段均低於單筆位元組限制；54 項 GAS 測試通過。**尚未代管理者在雲端部署 v62，也沒有權限直接讀取「每日績效」試算表核對實際列。**
