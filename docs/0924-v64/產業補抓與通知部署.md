# v64 部署與驗證：產業比重、監控通知與績效圖

這次修正三個具體問題：今日產業成交比重仍停在前一交易日；取稿狀態信可能在寄送失敗前就標記已回報；績效圖每次重畫都疊加一條「五成」基準線。GitHub 的推送只更新 GitHub Actions 所用程式，**不會自動更新 Apps Script 網站**。

## 這一版改了什麼

- `market_data.py` 先寫入證交所產業比重，再抓較慢的 Yahoo 行情；今天的證交所資料還沒公布時保留舊資料並讓本輪失敗，等下一次排程。新增只補產業的 `--mode sectors`。
- `market-data.yml` 增加台北時間 16:16、17:16、18:16 的產業專用排程。這次推送至 `main` 也會啟動一次產業補抓。GitHub 排程可能延遲，因此 Apps Script 另有 16:30 的獨立觸發器與 15:30–22:00 每 15 分鐘的缺口檢查。
- 監控頁顯示產業資料日期、最近補抓結果與錯誤。網站遇到過期資料明確標「今日資料補抓中」。
- 五分鐘總排程先派影片取稿、處理待寄郵件、每日總覽、簡訊補抓與解析派工，再做較重的行情工作。會員簡訊另有每分鐘輪詢觸發器；10 分鐘稽核補抓可接住輪詢漏文。
- 取稿狀態信改用盤中即時通知的深綠標題卡、白色內容卡；每 15 分鐘檢查，內容有變才寄。只有寄送成功才記已寄指紋，失敗留給下一棒重試。確認今日無直播後不寄「無影片」假告警。只有觀望紀錄的節目不再因為買賣與持股為零而誤報。
- 績效圖重畫前移除舊基準線，正報酬比例的「五成」只剩一條，切換到持有檔數時不留線。

## A. 先確認 GitHub 自動補抓

1. 打開 [Actions／market-data-cache](https://github.com/Lee200202/Stock/actions/workflows/market-data.yml)。這次程式推送應出現一筆 `push` 執行，`MODE=sectors`；查看最後是否顯示今日資料日期與產業數。排程時間為台北 16:16、17:16、18:16，平台可能延遲。
2. 若推送執行未出現或未成功，按 **Run workflow**，`mode` 選 **sectors**，不填 `codes`。失敗時先讀該次日誌；若證交所尚未發布，等下一個時段重試。不要拿昨天資料標成今天。
3. 這一步只更新試算表「市場總覽快取」的 `sectors` 列。可核對該列的 `資料JSON.date`、`更新時間`、`來源`、`狀態`。它不寄訂閱郵件，也不會改持股資料。

## B. 將 Apps Script 更新到正式網站

1. 在原 Apps Script 專案先建立版本或備份目前 8 個同名檔。從 [v64 部署包](../../release/zhangzhen-sector-monitor-v64.zip) 解壓，逐一替換 `Config.gs`、`Setup.gs`、`Marketservice.gs`、`Market.html`、`Adminservice.gs`、`Admin.html`、`MailService.gs`、`JavaScript.html` 的**內容**。不要建立重複檔名；其他檔案保留原有最新版本。
2. 在編輯器執行 `checkProjectFiles()`：結果須為通過，`GAS_BUILD` 與 `PROJECT_BUILD_` 均須是 `2026-09-24-sector-catchup-v64`。若它提示有檔案版本不一致，先核對上述八檔，不要直接部署混版。
3. 執行 `installTriggers()`。它會重建主排程和每分鐘簡訊輪詢，並安裝產業獨立補抓；**既有一次性觸發器會被重建**，因此只在沒有正在跑的後台工單時執行。接著執行 `installMarketDataJobs()` 補回 19:15 歷史分 K 排程。再執行 `checkAutomationReadiness()`，核對 `everyFiveMin`、`instantMail.pollTrigger`、`sectorCatchupScheduled`、`webapp` 等欄位。`hourlyHistory` 若為 false，重跑 `installMarketDataJobs()`；`marketSnapshots` 為 false 時，先在後台看最近採樣時間與當前是否為盤中，不把休市或非盤中當失敗。
4. 交易日 15:30 後可執行 `sectorCatchupNow()` 補當日資料，結果應顯示 `state=已更新`、`dataDate=今日`。再執行 `sectorCatchupStatus()`，核對試算表與回報日期一致。盤前或休市日不要要求今日產業資料。失敗若顯示來源尚未公布，稍後會由既有排程自動再試。
5. 到 **部署 → 管理部署 → 編輯既有網頁應用程式 → 建立新版本 → 部署**。不要建立另一條陌生網址。正式 `/exec?action=ping` 的 `build` 須變成 `2026-09-24-sector-catchup-v64`；重新整理網站「市場總覽」，查看「產業成交比重」日期。僅儲存程式碼不會讓 `/exec` 更新。

## C. 逐條核對其餘自動流程

1. **取稿／稽核**：平日從 11:05 起由 GitHub `transcript.yml`、`daily.yml` 多個時段嘗試；`everyFiveMinJob` 的 `transcriptAutomationTick_` 可補派。後台「自動化監控」應顯示主排程心跳、影片狀態、原文／修飾字數與當日失敗。已確認今日無直播時，顯示停播而非持續等待逐字稿。
2. **每日總覽**：到後台「自動化監控」設定最早寄送時間。`dailyPushJob` 於交易日 12:00–22:00 每五分鐘檢查；文章與品質關卡完成且到達設定時間才寄。看「每日推播內容」寄送狀態及後台寄送帳本的已交郵件服務、待續送、失敗數，不以「函式有啟動」代替已寄出的證據。18:00 的 `pushCheckJob` 會記錄仍未寄的原因。
3. **會員簡訊與盤中即時通知**：`cmoneyPollJob` 每分鐘觸發，盤中檢查會員文章；`cmAutoReconcileToday_` 再核對來源第一頁，漏文會補存並派 GitHub 解析。新文的即時郵件看後台寄送帳本；若來源有文章、試算表沒有，執行唯讀的 `diagnoseCmoneyToday(文章編號)`，再按診斷結果決定補抓。文章發布超過 60 分鐘才被補到，不假稱是「即時」寄送。
4. **取稿狀態信**：交易日 12:30–18:00 每 15 分鐘核對；有新進度才寄至 `statusEmails_()` 的管理者收件箱。要驗證樣式可看下一封自然產生的狀態信；不需為測試而寄給訂閱者。若信沒有來，先查 `statusEmails_()` 設定、MailApp 剩餘配額與 Apps Script 執行紀錄。

## 驗證界限

本機測試覆蓋 Python 市場資料、Apps Script 語法與檔案表、績效圖基準線，以及公開／後台 1440、1280、900、768、390、360 像素版面。正式站逐頁可讀性已查看；正式站的 v64 功能須完成上述 Apps Script 部署後再以 `/exec` 驗證。未在本機代替實際 MailApp 寄送、Gemini 判讀或 Apps Script 真實觸發器執行。
