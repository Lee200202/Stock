## 一、你的任務

你要改寫的是「張震股市盤中家教班」網站的「技術說明」分頁（`apps-script/Tech.html`，樣式在 `apps-script/Stylesheet.html`，共用的閱讀進度、右側子目錄、逐句浮現在 `apps-script/JavaScript.html`）。

管理者的原話：

> 「目前呈現方式仍有不直觀，敘述過於 AI，不像是一般文章敘述分享。還有增加 ERD 圖完整流程而非分散。敘述沒有字數限制。」

所以這次有三件事：

1. **換語氣**：從「產品說明書／系統規格」改成「作者本人寫的一篇分享文章」。讀起來要像一個人在講他為什麼做這個網站、踩過哪些坑、怎麼解決，而不是一份條列式規格。
2. **換結構**：目前是六段各自獨立的卡片式內容，每一段都用同一套模板（小標籤 → 大標 → 引言 → 對話框 → 圖 → 四格流程卡 → 灰色備註 → 表格），讀者必須在六段之間跳來跳去才拼得出全貌。改成一篇有起承轉合、可以從頭讀到尾的文章。
3. **補一張全貌圖**：一張完整的資料關聯圖（ERD）加上一條從資料進來到網站、郵件、績效的完整流程，放在文章前段，讓讀者先看到整張地圖，再讀細節。目前唯一的「資料關聯圖」只有 4 個方塊（影片清單 → 逐字稿判讀稽核 → 操作紀錄／會員持股 → 每日推播內容），藏在第 5 段裡，完全不是全貌。

字數沒有上限。寧可寫得完整、有例子、有故事，也不要為了精簡寫成口號。

## 二、我在正式站實際看到的問題

### 2.1 敘述像 AI 產生的說明書，而不是一個人在分享

逐段讀下來，最明顯的「AI 腔」特徵：

| 現象 | 原文例子 | 為什麼不好 |
|---|---|---|
| 口號式大標 | 「把不確定留下，不把錯誤藏起來」「數字正確，還要確定是誰的價格」「兩條排程，以試算表交棒」 | 像簡報標語，讀者看不出這一段要講什麼事 |
| 對仗、排比、「不是…而是…」 | 「省下的是『查找與核對』的時間，不是提高投資勝率」「不補、不猜」「不為了畫面完整而放行」 | 每段都在用同一種修辭，讀久了很像模型生成 |
| 假對話 | 「讀者會問／系統怎麼做」「讀者／系統」「管理者／覆蓋核對」「讀者／定價」 | 對話的另一方是「系統」，而且每一句都是完美回答，沒有真實感 |
| 「系統」當主詞 | 「系統怎麼做」「系統處理」「程式負責核對」 | 讀者讀不到「人」；作者本人應該出現 |
| 報告模板 | 第一段「動機／目的／痛點／解法／價值」五個色塊 | 像期末報告格式，不像文章 |
| 工程術語沒有解釋 | 下一棒、交棒、檢查點、刷新檢查點、原文指紋、SHA256、503、pipeline、稽核、背景追蹤、覆蓋核對、同步佇列、泳道 | 一般讀者看不懂；管理者需要的才留，而且要先解釋 |
| 同一模板重複六次 | 每段固定「四格流程卡（flow-map）＋一條灰色備註（flow-note）」，測試還強制剛好 6 組、24 格 | 形式大於內容，第 4 格常常是在湊數 |
| 螢光筆標記太多 | 每段都有 `<mark>` 黃底句、主體／行為／時間／條件四色筆 | 重點太多等於沒有重點 |
| 開頭先講「怎麼讀這一頁」 | 「每一段先用三、四行講重點，其餘用圖、對話與可以按的示範說明。」 | 文章不需要先說明自己的格式 |

### 2.2 結構與閱讀體驗

- **六段一次只顯示一段**，切段的步驟條不會黏在上方；看完一段要捲回最上面才能切下一段（段尾有「下一段」按鈕，但只能單向往下）。
- **沒有全貌**：流程散在第 1 段（取稿到發布）、第 4 段（持股回合）、第 5 段（資料關聯）、第 6 段（排程）。會員簡訊、寄信、行情、績效怎麼接在一起，沒有任何一張圖畫出來。
- **逐句浮現效果會讓畫面一大片空白**：往下捲比較快時，好幾個螢幕高度是空的，等一兩秒才出現（實測第一段中段到常見問題之間）。
- **讀者與管理者的內容混在一起**：「先看後台選定日期的取稿與 pipeline 稽核狀態，再開各自的 GitHub 日誌」「backfillDailyKJob／backfillDailyKStatus／explainHoldingsTracker」這種是管理者手冊，對一般讀者是雜訊。
- 第一段的即時數字（有紀錄的天數 60、收錄的個股紀錄 1,268、出現過的個股 240、會員簡訊 42、人工補登 1、每日整理 54，自 2025/12/04 起）是很好的素材，但被塞在「價值」色塊裡，沒有被好好講成故事。

### 2.3 互動示範的問題（實際按過）

| 位置 | 按了什麼 | 問題 |

## 三、必須修正的事實錯誤（正式站現在寫錯的）

這些是網站規則已經改過、但技術說明還寫舊版的地方。**改寫時一律以 `AGENTS.md` 與程式為準**，下面是我對到的：

1. **出場價**：第 4 段三處寫「以這一天收盤計算出場」「回溯以最後提及日收盤計算出場」「出場價回頭用 8/10（最後提及日）的收盤」。
   **現行規則（v68）**：出場一律取出場日「當日最高」——明講賣出、轉觀望不碰、逾期 10 個交易日未再提及都一樣；轉觀望、逾期只取當天或之前最近的交易日，不往後取。
2. **進場價**：第 4 段滑桿寫「成本依那天講的價位」。
   **現行規則（v58／v68）**：進場一律取成交日「當日最低」；首次明講「會員目前持有」也取聲明當日（或之前最近交易日）最低。張震講的價位（「73.5 以下買進」「成本 2250」）只當灰字附註，不當計算價；管理者在後台修正的成本優先。
3. **取稿時間與誰負責**：第 6 段四格泳道寫「GitHub · 取稿 11:05 起」「GitHub · 判讀 11:20 起」。
   **現況**：交易日 11:05 起由 Apps Script 每五分鐘的主排程派工給 GitHub Actions 取稿（`Adminservice.gs` 的 `TX_AUTO_START_HM_`），原稿落地後再派判讀；GitHub 自己的 cron（`transcript.yml` 11:05／11:30…、`daily.yml` 11:20／11:35…）常延遲，只當備援。
4. **年度休市日**：第 6 段備註寫「未收錄年份提醒後照常執行」。
   **現況（v66）**：隔年休市日尚未核實時，台股自動工作**暫停**並在日誌標明；會員簡訊照常。
5. **績效怎麼算**：目前頁面沒有講清楚。可以寫進文章：每日績效是「當天所有持有中回合的未實現報酬平均」；歷史績效用回合的進場價逐日對收盤重算；出場價只影響已出場那一回合的報酬。進場取最低、出場取最高是「跟著喊單能拿到的最好結果」，報酬是上限示意，不是實際成交紀錄，這一點一定要誠實寫出來。
6. 其他你改寫時碰到的規則，都要回頭對 `AGENTS.md` 對應版本的說明（v58、v61 已撤回、v66、v67、v68、v69），不確定就讀程式，不要憑印象寫。

注意：`tests/test_docs_v27.py` 的 `test_thresholds_match_the_code` 目前還要求頁面含「最後提及日收盤」，這是跟著舊規則寫的，改寫時要一併把測試改成新規則（例如改成要求「當日最高」「不能向後取價」「超過 10 個交易日」）。

## 四、改寫方向（建議，可以調整）

### 4.1 語氣：作者本人的分享文

- 用第一人稱「我」。作者是李世勛（臺北大學統計所，做機器學習、NLP 與大型語言模型，應用在量化金融），頁尾已有作者欄。
- 讀者設定：**訂閱這個網站的一般投資人**，以及**想了解這個專案怎麼做的人**（同學、面試官、工程師）。管理者操作手冊不是主角。
- 講「為什麼」與「遇到什麼問題」，用真實發生過的事當例子。這個專案有很多好故事，例如：
  - 語音辨識把「力積電」聽成「立即電」、「勤誠」聽成「秦城」，所以搜尋要能用聽錯的字找到。
  - 「鴻準最近散戶一直賣，大戶持股增加，會員要抱牢」——句子裡有「賣」，但會員其實是續抱。
  - 「ETF 賣出勤誠 168 張，勤誠 900 以下才看買點」——168 是張數，900 才是價格，而且是勤誠的、不是 ETF 的。
  - 「以前 1580 推薦，當時沒人買，漲上來才追」只是回顧，不能當成今天看多。
  - 2026/09/23 聖暉、力積電當天的會員簡訊「請於 73.5 元以下買進」，網站怎麼記、成本怎麼算。
  - 9/24 首頁「資料讀取失敗」：持股追蹤清單超過 Apps Script 快取 100KB 上限，一行沒防護就整頁掛掉。
  - 9/25 中秋節休市，還在寫「每日績效」，後來改成休市日排程自動略過。
  - 手機上「說明重點」往右滑不動，查出來是兩條 CSS 互相蓋掉。
  挑幾個最有代表性的講清楚，比每個主題都點到為止好。
- 可以承認限制與取捨：模型每次輸出可能不同、報酬是上限示意、GitHub 排程會延遲、免費帳號一天寄信額度只有 100 位。這些寫得坦白，反而最有說服力。
- 數字用第一段的即時數字（`apiGetTechStats`，每次打開從試算表讀），寫進句子裡，例如「到今天為止，網站整理了 60 天、1,268 筆個股紀錄」，而不是做成六格儀表板。

### 4.2 建議的文章架構

以下是建議，你可以合併或重排：

1. **開場：一個具體的查找情境**（約 2～4 段）。以前想找「力積電上次講的成本」要翻聊天紀錄、拖影片時間軸；現在搜一次就列出每一次提到。順帶講這個網站是什麼、不是什麼（不是投資建議、和頻道沒有隸屬關係）。
2. **先看全貌：一張圖**（新增，見 4.3）。一段文字帶讀者看圖：資料從哪裡來、經過哪些處理、最後出現在哪裡。
3. **跟著一天走一遍**：用一個真實交易日（建議 9/23）從早上會員簡訊、中午直播影片、下午發布整理與寄信、晚上補日 K 與記績效一路講下來。現在第 1 段的「情境演示」和第 6 段的「一天泳道」可以合併成這一節的互動。
4. **最難的幾件事**：每件事一個小標，用故事講問題、再講做法。建議四件：
   - 聽錯字與股名（名稱比對、別名、官方代號）
   - 一句話到底是誰做了什麼（當日買賣／會員持股／觀望注意／觀望不碰、舊推薦回顧）
   - 這個數字是誰的、是不是價格（張數、漲跌額、股利、條件價）
   - 持股什麼時候算開始、什麼時候算結束、價格怎麼取、績效怎麼算（第三節的新規則寫在這裡）
5. **出錯的時候怎麼辦**：模型忙碌、影片晚到、沒有直播、休市、快取爆掉、手動貼稿插隊。重點是「不假裝成功、進度保留、下一輪接著做」，用人話講。
6. **它做不到的事**：報酬是上限示意、不含交易成本、模型可能看錯、排程可能延遲、寄信額度。
7. **常見問題**（保留現在四題，可再加）。
8. **給管理者的附錄**（收合）：排查順序、函式名稱、日 K 與績效重算怎麼跑。現有「管理者速查」與「排查順序」等搬到這裡，或乾脆移到後台，讓主文乾淨。
9. **關於作者**（保留）。

呈現方式建議改成**一篇連續長文**，靠右側子目錄（`.subnav`，現有）與章節錨點導覽，不再一次只顯示一段；如果你認為保留分段比較好，至少讓步驟條在捲動時黏在上方，且段落數依內容決定，不必硬湊六段。這兩種做法都要同步修改 `tests/test_docs_v27.py` 與 `scripts/preview_v54.js` 裡鎖死「6 段、6 個 flow-map、24 格、每段 4 格重點」的斷言（那些是舊版版型的測試，不是需求）。

### 4.3 新增：完整的資料關聯圖（ERD）與流程全貌

管理者要的是「完整流程」，不是分散的小圖。建議做兩張，或一張可切換兩種看法的圖：

**A. 資料關聯圖（ERD）**：資料存在 Google 試算表，每個分頁當一個實體；關聯是程式邏輯上的，不是資料庫外鍵（圖上要註明）。依領域分色分區，實體至少包含下表。**畫之前請自己對過 `apps-script/Setup.gs` 的 `SHEET_SCHEMA` 與 `pipeline/pipeline.py`、`transcript.py`、`market_data.py` 用到的分頁，以程式為準，我的整理可能有漏。**

| 領域 | 分頁（主要欄位） |
|---|---|
| 來源 | 影片清單（影片ID、發布日期、原始／修飾後逐字稿、原文SHA256、逐字稿來源：手動／手動保留／自動）、今日影片候選、會員簡訊（文章ID、發文時間、原文、解析明細、通知狀態、內容指紋）、會員簡訊稽核、人工補登 |
| 判讀 | 逐字稿判讀稽核（來源影片ID、原文SHA256、判讀JSON）、逐字稿刷新檢查點、名稱判定紀錄、辨識日誌、代號對照快取、股票對照表（代號、名稱、市場、產業） |
| 紀錄 | 操作紀錄（日期、代號、方向、價位說明、來源影片ID、序）、會員持股（日期、代號、目前立場、來源影片ID）、修正建議 |
| 發布與寄送 | 每日推播內容（日期、文字稿、寄送狀態）、簡訊內容同步、使用者訂閱清單（Email、訂閱項目、取消訂閱權杖）、寄送帳本（訊息ID、種類、日期、收件者、狀態、服務接受時間） |

## 五、寫作規範（避免 AI 腔）

請遵守：

- 不要用口號式標題、四字對仗、三段排比。
- 「不是…而是…」「不…、不…」「與其…不如…」整篇各不超過兩次。
- 不要虛構對話；需要呈現問答時，用「常有人問我…」這種真實口吻，或直接寫成段落。
- 主詞用「我」「網站」「這一步」，少用「系統」。
- 工程術語第一次出現時用一句白話解釋，之後才可以用；「下一棒」「交棒」「檢查點」「稽核」「pipeline」「泳道」在主文盡量換成日常說法。
- 每一個觀點配一個具體例子（真實日期、真實個股、真實數字）。
- 句子長短交錯，允許口語（「後來我才發現」「這一步最容易出錯」）。
- 不誇大：沒有量測過的省時比例不要寫；報酬是上限示意要寫明；不宣稱模型每次輸出一致。
- 台灣繁體中文、全形標點。
- 網站的公開文字規則仍然適用：不寫「張震指出」「講者表示」這類以人名當主詞的句子（講節目時用「直播」「節目」「頻道」）；語音誤字「張正」不得出現。
- 不放內部提示詞、判斷規則原文、金鑰或任何個資（作者欄現有的 Email 與連結可以保留）。

改寫示範（只示範語氣，內容請依實際情況寫）：

> **原文**：「把不確定留下，不把錯誤藏起來。模型負責理解上下文；程式再核對名稱、原句、數字與分類衝突。」
>
> **改寫**：「模型很會讀上下文，但它講錯的時候也講得很有自信。所以我讓它先讀，程式再回頭對一次：這個股名在不在證交所的清單上？它引用的那句話，原稿裡找不找得到？那個數字真的是股價，還是張數？對不上的，我寧可在網站上寫『未說明』，也不要讓一個猜出來的價格安靜地混進去。」

> **原文**：「讀者會問：11:05 到了，為什麼網站還沒出現今天的分析？系統怎麼做：取稿、判讀、發布是三個不同進度。」
>
> **改寫**：「常有人在中午傳訊息問我：『今天怎麼還沒更新？』通常是影片回放還沒出來。直播結束後，頻道要一段時間才會放出回放，網站得等回放出現才能開始聽打；聽打完、整理完，才會發布。後台會分開顯示這三個進度，所以我看得出是卡在哪一步，而不是只看到一條還沒跑完的進度條。」

## 七、技術限制（一定要遵守）

- 網站是 Google Apps Script 網頁應用程式，整頁包在 googleusercontent 的沙箱 iframe 裡，而且帶 `<base target="_top">`：頁內連結不能用 `href="#x"` 跳轉（會導走外框），要攔 click 用程式捲動（現有 `__scrollToY`）。

- 常見問題與「關於作者」要在任何收合區塊之外（`tests/test_docs_v27.py` 會檢查 `<details>` 開關數）。
- 不新增外部函式庫或字型；圖用 inline SVG 或 HTML／CSS。
- 顏色一律用 CSS 變數，深色模式（`[data-theme="dark"]` 與 `prefers-color-scheme`）都要看得清楚。
- 手機（390px、360px）不得有橫向捲動，文字不小於 12px（乘 `--rd-fs`），按鈕觸控高度至少 44px。
- `prefers-reduced-motion: reduce` 時不自動播放、不做位移動畫。
- 字級、字距、行距要跟著版面設定走（`--rd-fs`、`--rd-ls`、`--rd-lh`）。
- 不要動與技術說明無關的程式與規則。
