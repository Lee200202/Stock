# GitHub Pages 原站介面部署與驗收

## 為什麼不是只複製一個 HTML

Apps Script 的 `Index.html` 會把 `Stylesheet.html`、`JavaScript.html`、`Market.html`、`MarketCharts.html`、`MarketDetail.html`、`Settings.html`、`Tech.html` 組成一頁；按鈕靠 `google.script.run` 呼叫 GAS 後端。GitHub Pages 不提供這個執行環境。單獨複製畫面會得到外觀相似、資料與訂閱卻不能用的壞站。

網站資料仍依原 GAS 的快取與排程更新；**GitHub Action 只在程式變更或手動啟動時發布版面**，不再每 15 分鐘整包讀試算表、重建一份內容。發布前 Action 會真實呼叫橋接 API；失敗就保留上一個已成功的 Pages 版本。

這一版在 `public-site/gas-source/` **逐檔保存目前 Apps Script 原檔**；檔案雜湊與本機 `apps-script/` 一致。建站腳本只展開 GAS 的 include、四個 `doGet` 模板值，並在原本 `JavaScript.html` 前加入 `original-bridge.js`。原有動畫、表格、圖表、版面設定、分頁、技術說明及原站的 JavaScript 原封不動。`site-api/worker.mjs` 是免費 Cloudflare Worker，將前台 API 轉給既有 GAS；GAS 的 `SiteBridge.gs` 限定只能呼叫原前台用的公開 API，**不能呼叫後台函式**。

目前已建立 GitHub Pages、部署 Worker 程式；**GAS v75 與橋接密鑰尚待管理者部署**。在完成下列步驟前，GitHub Pages 仍保留上一個已成功發布的舊頁，workflow 沒有 `SITE_API_URL` 就略過發布。不要把它誤認成這版原站介面。

## 依序部署（不要跳步）

1. 打開 Apps Script 編輯器，從本機 `C:\Users\user\Downloads\zhangzhen-stock-site-updated\apps-script\` 或 GitHub 的 `public-site/gas-source/` **整檔替換** `Code.gs`、`Config.gs`、`Setup.gs`，再新增 `SiteBridge.gs`。這四檔互相配套，不能只貼其中一檔。其餘 GAS 檔案不需因橋接重貼。存檔後先執行 `checkProjectFiles()`；應沒有缺檔，build 應是 `2026-09-28-pages-bridge-v75`。
2. 在 Apps Script 執行 `siteBridgeSetup()` 一次。它會建立並在**執行記錄**顯示一串 `SITE_BRIDGE_TOKEN`。這是密鑰，不要貼進 GitHub、Issue、網址或對話；只在下一步貼進 Cloudflare Secret。再次執行會顯示同一串，方便補設。
3. Apps Script 右上 **部署 → 管理部署作業 → 編輯現有網頁應用程式 → 版本選「新版本」→ 部署**。保持既有「執行身分：我」與「誰可以存取：所有人」。在無痕視窗開原 `/exec?action=ping`，確認 `build` 是 v75、`features` 有 `pages-original-ui-v75`。不要新增另一個部署 URL；新 URL 會讓原郵件／LINE 連結指向舊部署。
4. Cloudflare Worker 已部署為 `zhangzhen-site-api`。在 `C:\Users\user\Stock\site-api` 開終端，執行 `npx wrangler secret put SITE_BRIDGE_TOKEN`，貼上第 2 步的密鑰並按 Enter。或者 Cloudflare Dashboard → Workers & Pages → **zhangzhen-site-api** → Settings → Variables and Secrets → Add → 名稱 `SITE_BRIDGE_TOKEN`、類型 Secret，貼入並儲存。`GAS_WEBAPP_URL` 已在 `site-api/wrangler.jsonc` 指向現有正式 `/exec`；若 GAS 部署 ID 改變，要同步改這裡並 `npx wrangler deploy`。
5. 用瀏覽器開 [Worker 健康檢查](https://zhangzhen-site-api.rainforecast2026-6fb.workers.dev/healthz)。必須是 `{"ok":true,"ready":true}`。在本機執行 `python scripts/check_site_api.py`，應能透過 Worker 讀到每日總覽；此步只讀，不寄信、不改表。若 502，先看 GAS `/exec?action=ping` 與部署版本；若 503，看 Secret 是否已存。
6. GitHub 倉庫 **Settings → Secrets and variables → Actions → Variables → New repository variable**。名稱 `SITE_API_URL`，值 `https://zhangzhen-site-api.rainforecast2026-6fb.workers.dev/api`。這是公開 API 網址，不是密鑰。然後 **Actions → public-site-pages → Run workflow → main → Run workflow**。成功後開 [GitHub Pages 正式站](https://lee200202.github.io/Stock/)。
7. 驗收桌面和手機：首頁買賣／觀望／持股、會員通知、逐字稿、查個股、K 線、成交量與技術指標、市場總覽日內線、績效、郵件查詢、技術說明、深淺色與字級。按鈕觸發後要看到資料或明確錯誤；不能只有外觀。再用一般多帳號瀏覽器開 GitHub Pages，確認不經 Google 的網頁進入流程。

## 仍須區分的兩種網址

GitHub Pages 是公開前台。原 GAS `/exec` 仍負責後台、訂閱寫入、AI、資料庫及寄信。前台經 Worker 呼叫後端，因此 Worker 或 GAS 停止時，頁面本身還能開，但動態資料會失敗；這和完全離線網站不同。後台鎖頭目前仍連原 GAS `/exec?page=admin`，管理者遇到多帳號 Cookie 衝突應使用獨立 Chrome 使用者設定檔。**不要把後台或密鑰放進 GitHub Pages。**

退訂連結仍留原 GAS：它帶收件者專屬 token，不能寫進公開靜態檔。郵件與 LINE 既有「看整理」連結尚未自動改成 Pages；需先通過第 7 步驗收，再改連結來源，避免寄出指向尚未可用網站的信。這版沒有宣稱後台與退訂已遷出 GAS。

## 故障與回復

- Pages Action 顯示 skipped：第 6 步變數未設；上一版網站會保留。若設了卻報 `SITE_API_URL must be an HTTPS /api endpoint`，檢查網址是否以 `/api` 結尾。不要建立假的 URL 讓工作流變綠。
- Worker `/healthz` 顯示 `ready:false`：Cloudflare Secret 尚未設定。不要把 token 填成 GitHub Variable。
- Pages Action 的「後端橋接實測」失敗：不要強行略過此步；它是避免完整原站版面上線後所有按鈕都壞掉的防線。
- 前台顯示「資料讀取失敗」：看瀏覽器 Network 的 `/api` 狀態；503 是 Worker 設定，502 是 GAS 版本、執行權限或後端暫時錯誤。再跑 `checkProjectFiles()`、`ping`。
- 原版面改了：先在本機同步對應 HTML 到 `public-site/gas-source/`，核對 SHA-256，跑原站預覽測試，再推 GitHub。**不要另寫一份簡化的首頁。**
- 要回復前一次已成功的 GitHub Pages 部署：在 GitHub Actions 重新執行該版的 workflow／回退該版 commit；GAS、LINE、寄信流程不受 Pages 前台回退影響。
