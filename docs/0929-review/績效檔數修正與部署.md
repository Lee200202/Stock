# 績效表「追蹤檔數」修正

2026/09/29 的畫面顯示「追蹤檔數 34、持有檔數 12」。34 來自持股追蹤中 12 檔持有加 22 檔已出場；但同表先前的歷史重算只寫當日持有檔數。兩條寫入路徑使用不同定義，因此不能用 34 判讀當日績效。

現在第二欄統一叫「計入報酬檔數」：當日仍持有、且有進場價與可用價格、真正參與平均報酬計算的檔數。第三欄「持有檔數」包括暫時缺價的持倉。已出場檔不計入這兩欄。第二欄可能小於第三欄，不可自行補成相同。歷史重算從既有「日K快取」和「持股追蹤」回合計算，不因此額外呼叫行情 API。

## 部署次序

1. 把 GitHub 的 `public-site/gas-source/` 下列 **五個**檔案完整貼到同名 Apps Script 檔案：`Cachebuilder.gs`、`Setup.gs`、`Config.gs`、`Index.html`、`JavaScript.html`。不要只貼其中一份，也不要執行 `installTriggers()`。
2. 在 Apps Script 編輯器執行 `checkProjectFiles()`，確認沒有缺檔或舊版警示，並核對 build 為 `2026-09-29-performance-count-v82`。
3. 在「部署 → 管理部署作業」編輯現有網頁應用程式，版本選「新版本」，部署；不要新建另一個網址。重新開正式網址，確認版本已更新。
4. 在編輯器執行 **不帶參數** 的 `rebuildPerformanceHistoryJob()` 一次。它會重算「每日績效」整張表，並把第二欄改成新名稱；不用重抓日K。若日誌顯示「缺少回合JSON」，先執行 `rebuildHoldingsTrackerJob()`，待完成後再跑歷史重算。
5. 重新載入網站「績效走勢」，核對 9/29 的計入檔數不超過持有檔數，且沒有顯示 34。直接檢查試算表「每日績效」：B1 應為「計入報酬檔數」，同一列 B 值應 ≤ C 值。當天尚無日K或缺進場價時，B 可小於 C；不能硬指定一定是 12。

後續的 `snapshotPerformanceJob()` 也會寫同一口徑。若部署後仍看到舊欄位，先檢查正式網址部署版本與 `checkProjectFiles()`；只改 GitHub 或只存編輯器草稿不會更新正式站。

此版尚未由 Codex 部署到使用者的 Apps Script，也未直接修改正式試算表；正式畫面須依上述步驟驗收。
