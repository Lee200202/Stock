# 完整歷史日 K：關機後的 GitHub 接棒

## 已有流程與本次新增

`market-history.yml` 原本每次有兩輪探查與三個保存／組裝發布檢查點，但只在平日台北時間18:40定時執行，沒有完成後自動接棒。本機聊天的追蹤不能作為電腦關機後的執行依賴。

新增 `market-history-continue.yml`：

1. GitHub 收到 `market-history` 完成事件後核對最新執行；既有正在執行的舊版本也適用，不需要取消重跑。
2. 每小時第17分另有恢復核對；GitHub 排程可能延遲，不承諾準點。
3. 同目的工作只要仍有 active／pending 就保留，接棒控制器也用獨立 concurrency 防止同時派工。
4. 最新 main 補抓成功、兩個市場有結束進度，且有「預算到、未走訪範圍」才派出下一次完整範圍（years=0、minutes=150）的增量探查。
5. 沿用有效既有封存與原有空回應冷卻規則，不因接棒重新下載全部資料。每次兩輪之間仍保存並發布通過品質檢查的資料。

## 停止與等待邊界

- 人工取消、工作失敗或逾時：不自動復活，控制器標記待核；既有平日排程仍可在下個排程時機重試。
- 缺少兩市場結束進度：不把未知當成完成，也不直接無限重跑。
- 全部計畫範圍已走訪：停止立即接棒；待核空回應與來源失敗保留，平日排程依既有冷卻規則複核。
- 連續兩次沒有新增或更新封存：停止立即接棒，避免空轉。新增封存包含待核空回應，不等於新增有效交易日。
- `coverageVerified=false` 不直接作為派工條件；否則官方矛盾列與來源缺口可能造成永久迴圈。
- 未找到資料不是休市或掛牌起點的證明。正式完整驗收仍需核對官方範圍、轉板、缺日及公司行動；這項接棒功能不宣稱全部歷史已齊。
