# 2026/10/27 模型候選發布流程修正

管理者最新要求：分類與說明須經真實模型實跑，驗收後套用同一次結果；不得把人工答案灌進流程再稱模型正確。之前已授權的來源修復另列，不回溯冒稱模型驗收。

## 查實的舊流程問題

`regenerate_verified_day.py` 曾預設將 golden.must／must_not 放進人工裁決快取；預覽期間套用 reviewed_notes、按 note_must_not 刪句；正式寫入後再呼叫模型重寫通知說明及人工說明覆蓋。這讓預覽與發布不是同份結果，並使規則模式名稱與實際資料注入不一致。這些包裝已移除。

## 新流程

1. `preview` 凍結業務來源與部位；同日既有網站分類、人工裁決與人工說明不進推論。保留當日通知事件，清空既有改寫說明與解析明細；歷史部位截至目標日前。目標原稿直接用完整原字。
2. 真實模型經擷取、稽核、裁決、來源審閱及書面化，到寫入前攔下。人工與模型裁決快取均停用，不寫正式表。
3. 推論完成後才打開參考JSON比對。品質、隔離、待裁決與未完成審閱任一未過，候選標失敗。詞表語氣／漏收盤點只列待核提醒，不代表分類答案。
4. 保存含程式commit、run ID、原稿SHA、輸入快照摘要、參考政策SHA、精確signals與文章的artifact。
5. `apply` 必填成功preview的candidate_run。GitHub核對repo、workflow、event、commit、日期與成功結論，再下載該run artifact；再次核指紋、原稿、政策與業務快照。缺項或變動即停止，不重跑模型。
6. 獨立備份後再查漂移，單次Sheets batchUpdate原子套用精確候選，逐值讀回。通知／人工列、其他日期、寄送旗標與帳本保留；保留來源與模型若有身分差異則停止，不能拿舊列替模型補答。
7. 發布期間禁止模型呼叫；不做答案句刪除、不重寫通知說明、不寄Email／LINE。保留的既有通知說明不是本輪模型產出，需單獨標示。

## 驗收界線

來源參考仍可能是看過結果的代理草稿；相符率不是盲測準確率。失敗候選不發布，不因此填答案。未見日期、同版重複及內容歸屬驗收分開報告。一般每日自動流程與此受控重判入口不同，不能由單日測試宣稱所有排程已完成驗收。
