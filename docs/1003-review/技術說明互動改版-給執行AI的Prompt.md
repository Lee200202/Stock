## 建議的故事線

讓讀者能沿著「我想查什麼 → 資料怎麼來 → 哪句話可信 → 稽核過程如何防止舊稿覆蓋新稿 → 公開說明怎麼取捨 → 出錯時如何續跑 → 這些結果的限制」往下讀。若維持原有十二節，至少將「沒講名字」案例移到其他證據案例旁，再接原稿稽核與公開說明；合併與故障章節重複的排隊、續跑文字。更新開頭對章節的預告、右側子目錄、閱讀進度與章節跳轉；保留既有 section ID 或提供相容錨點，使舊連結仍能到正確內容。常見問題和作者仍在主文底部。每節先用一句讀者問題引入，再給可操作的例子，深入規則放在可展開的文字說明，不要把必要結論藏起來。

## 互動一：原稿版本與稽核狀態實驗室

把 `#tech-transcript-progress` 的四段文字轉成一個「選情境 → 看資料狀態 → 看下一步」的模組。畫面一側或上方是原稿版本、指紋、已完成片段、稽核結果、公開／寄送關卡的簡短流程；另一側是大顆可點的情境膠囊與結果卡。桌面可以並排；手機改直向，不要讓整頁橫向捲動。每次選擇要有清楚的視覺變化、事實原因與操作結果，至少覆蓋：

- 原稿內容相同又貼一次：哪些潤飾可沿用，哪些分類、證據與寄送核對仍要完成。
- 潤飾期間原稿真的更新：舊工單不能覆蓋新稿；顯示原稿指紋不一致、保留新稿與下一輪如何續跑。
- 取消單一取稿或稽核工單，與「今天暫停自動取稿」的作用範圍差別；已落地資料如何保留。
- 模型 503、回應截斷／JSON 無效、證據缺漏：明確區分暫時等待、有限重試、備援與待人工複核，不把「有心跳」畫成「已完成」。金鑰及額度說法必須跟程式一致。
- 報價等待或共用鎖忙碌：是否釋放鎖、何時交給下一輪，並展示「文章完成」與「背景績效完成」是兩種不同狀態。

這是教學用的靜態情境模擬，標明「示意，不是即時監控」。情境內容放在同一份資料表／陣列供按鈕與結果卡使用，避免同一規則散落在多處 DOM 和 JS。使用者切換情境時，不得呼叫真實後台 API、觸發工單或寫寄送帳本。核對現有程式後再定每個分支的文案；若本段舊敘述與目前流程不符，修正文案並記錄依據。

## 互動二：公開說明編輯檯

把 `#tech-public-notes` 改成「原句／來源 → 檢查 → 公開會看到什麼」的可選案例。不要只做 before/after 文字切換；每次點選應讓讀者看到哪個證據支持、哪個句子被刪或留待複核，以及最後公開文字的實際長度與語氣。用顏色加文字標籤表示「可公開」「保留部分」「待複核／不公開」，不能只靠顏色。至少有以下案例：

1. 技術位置、消息與風險都有原句支撐：留下具體事實和條件，移除「逐字稿補充的重點是」等製作過程語句。
2. 兩句意思相同而第二句只是換開頭：只留一次；若第二句含新數字或新條件，保留新資訊。顯示被保留的差異，與 v107 的去重規則一致。
3. 引句屬於甲公司，說明卻借用了乙公司的現金增資或其他事件：不支持的部分進內部稽核，其他有依據的句子仍可保留。不要把甲、乙案例寫成真實新增投資資訊。
4. 分類為「觀望不碰」但說明卻寫「找買點」：列待複核並展示矛盾，不自動改分類或擅自改作者說法。
5. 會員通知有交易方向和成交價：方向留在分類；公開網站、郵件與 LINE 的說明不要洩出通知的具體成交價或來源名稱。均線週期、成交張數、百分比、EPS 等非成交價數字仍應保留。示例若涉及私人通知，用虛構、明示為示意的內容，絕不讀出真實會員原文。
6. 管理者人工修正：同一原稿指紋、股票、來源與分類再處理時保留；任一關鍵條件改變則退回待複核。示範「保護」與「不自動套用」兩種結果。

結果卡要讓人直接讀懂「公開看見的是什麼」；詳細引用、數字與來源的核對可在展開區查看。不要把內部判定紀錄冒充已寄信內容。已寄出的郵件是快照，頁面示例只能解釋新規則，不得在部署時改寫或重寄舊信。若整頁目前的「公開不顯示價位」說法與技術示例中的實價相衝突，先查實際產品規則，讓示例和說明一致，並把取捨寫進交付說明。

## 視覺、動態與可及性

- 保留現有溫暖的深色／淺色、橢圓形大按鈕與有空間感的卡片；兩個新模組各有不同的主視覺：稽核用版本／狀態時間軸，公開說明用證據到成稿的編輯台。可用 inline SVG、CSS 線條與高亮連結呈現因果，不新增龐大的動畫框架或外部圖床。
- 互動只在使用者點選時以短暫的顏色、線條或 150–250ms 狀態轉場回饋；不恢復 v107 已移除的列表捲動淡入，也不做自動播放、視差或讓文字在捲到前透明。遵從 `prefers-reduced-motion`，減少動態時即時切換內容。這與 [W3C 對互動動畫的說明](https://www.w3.org/WAI/WCAG21/Understanding/animation-from-interactions) 一致。
- 用原生 `<button>`／`<details>`，明確的 `aria-pressed` 或合適的 tab／tabpanel 語意，焦點可見、Tab 順序合理、切換後結果可由輔助技術讀取。若採 tabs，依 [W3C APG tabs pattern](https://www.w3.org/WAI/ARIA/apg/patterns/tabs/) 實作方向鍵與焦點管理；若只是多個獨立情境按鈕，沿用現有 button group，避免假 tabs。按鈕觸控區至少 44×44px；文字與背景對比、非顏色提示、鍵盤和觸控都要驗。
- 沒有 JavaScript 或模組初始化失敗時，核心規則與預設案例仍可閱讀；每個動態圖都有文字等價內容。不要用大量 `aria-live` 一次朗讀整個長段落。首次載入不新增後端呼叫，切換情境不發網路請求，也不得拖慢首頁資料、個股面板或後台載入。

可參考 [The Pudding 對視覺故事的經驗](https://pudding.cool/process/how-to-make-dope-shit-part-3/)：讓圖像的每個狀態對應明確文字，快速捲動或倒著閱讀也能理解。不必照搬全屏滾動敘事；此站讀者會按目錄跳章，互動必須在單節內完整成立。
