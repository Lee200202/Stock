# 每日寄信前複核：雲端排程作業步驟

本檔是雲端排程每天照做的步驟（等同技能）。固定動作交給腳本，AI 只做兩件事：讀原稿判讀、判斷差異。不用截圖或點網頁。

- 複核範圍（管理者 2026/11/06 擴大）：個股分類與說明，加上郵件的 **①盤勢總覽重點整理** 與 **③分析師操作邏輯與教學重點** 兩章。兩章的品質標準見第 4-1 節。

- 試行期原訂到 11/14，管理者 2026/11/03 指示提前結束：明確錯誤當天照第 6 步修正並更新網站，`trial` 一律設 false。
- 改了什麼由 12:30 的「爬取狀態」信用卡片呈現，不另寄信。

## 0. 環境（雲端環境變數，由管理者設定）

| 變數 | 用途 |
|---|---|
| `GOOGLE_SHEETS_SERVICE_ACCOUNT` | 服務帳戶金鑰 JSON（與 GitHub 的同一把） |
| `SPREADSHEET_ID` | 主資料試算表 |
| `REVIEW_LOG_ID` | 複核紀錄試算表 |
| `GEMINI_API_KEY` | 填 `offline` 即可：複核不呼叫 Gemini，只為了讓主流程模組能載入 |

- 網路要允許：`sheets.googleapis.com`、`oauth2.googleapis.com`、`www.googleapis.com`。
- 第一步先安裝套件：`python -m pip install -q -r requirements.txt cryptography cffi`。雲端容器的 `pip` 指向另一個 Python 版本，一定要用 `python -m pip`。
- 金鑰可以填整份 JSON（壓成一行）或它的 Base64 一行字，腳本會自動還原。

## 1. 取輸入包（11:40 起）

```bash
python scripts/daily_review/fetch_day.py --hold
```

- **印出 `NO_TRADING_DAY`**：週末或休市日，直接結束，不寫任何東西。
- **印出 `NOT_READY`**：主流程還沒寫完。每 5 分鐘再跑一次，最多到 12:40。
  - 到了 12:40 仍未完成（包括當天沒有影片）：寫 `judged.json`，`diffs` 留空，`report` 寫「主流程 12:40 仍未完成，今天未複核」，然後跑第 5 步。
- **印出 `READY`**：已把今天設為「複核中」，郵件會等，最晚 13:00。

## 2. 讀裁示，再獨立判讀（這時不看網站）

1. 先讀以下三份，記在判讀檔的 `rulings_read`：
   - `docs/daily-review/裁示紀錄.md`
   - `docs/分類裁決基準.md`
   - `docs/stock-skills/skills/stock-content-audit/references/self-classification.md`
2. 讀 `.daily-review/<日期>/` 裡的檔案：
   - `raw.txt`：判讀唯一依據。
   - `polished.txt`：只用來辨認同音字。
   - `notices.txt`：只用來判斷部位。
   - `positions.json`：今天以前的部位。
3. 整篇讀完再寫 `reading.json`，格式見 `scripts/daily_review/freeze_reading.py`：
   - 每一檔原稿點名的股票都要有一列，附原句和可接受集合 `accept`。
   - 確定不該公開的放在 `must_not_public`。
   - 沒有股名的「這一支」不要猜。
   - `chapters.macro`／`chapters.lessons`：自己整理講者今天講到的每一個盤勢主題與教學主題（`topic` 主題、`detail` 具體內容與數字、`quote` 逐字原句）。
     - 盤勢依序找：指數漲跌與關鍵點位、位階與均線（年線、季線、60分K）、量能、法人或融資籌碼、族群資金輪動、匯率與重大事件、下一步的多空看法。
     - 教學找：講者教觀眾怎麼想、怎麼做、要避免什麼的段落，例如技術法則、選股依據、進出場與加碼紀律、風險控管。
     - 招生、電話、防詐提醒、私人理財以外的閒聊不列。`quote` 不在 raw.txt 時凍結會失敗。
4. 凍結：

```bash
python scripts/daily_review/freeze_reading.py .daily-review/<日期>/reading.json
```

凍結之後不得回頭改判讀。

## 3. 比對（凍結後才讀網站內容）

```bash
python scripts/daily_review/compare_site.py
```

產出 `diffs.json`、`diffs.md` 與 `chapters.md`。

- 個股差異類型：分類、漏收、複核未涵蓋、應排除卻公開、今日買賣、通知用語外洩、說明重複。
- 章節的機械疑點（代號欄是 ① 或 ③）：章節空白、章節點數不足、章節數字不在原稿、章節過短。
- `chapters.md` 把網站兩章的每一點和自己凍結的主題並排。語意上的問題由你自己加進 judged.json，類型用：
  - `章節幻覺`：原稿沒講的事、數字或因果；把個股或別段的話寫成盤勢；只出現在會員通知的用語。
  - `章節主詞錯置`：把 A 的看法寫成 B 的、把觀眾問句寫成講者主張。
  - `章節漏主題`：自己凍結的主題裡有具體技術內容（點位、均線、量能、籌碼、匯率、明講的操作方法），網站兩章都沒有。
  - `章節說明不清`：只寫「講解了季線」沒寫出操作邏輯、口語照抄、條件或對象寫反。

## 4. 判斷每一項差異，寫 judged.json

每一項差異給一個嚴重度：

| 嚴重度 | 什麼時候用 |
|---|---|
| 明確錯誤 | 違反裁示紀錄或分類基準，原句清楚 |
| 待確認 | 可能錯，但裁示沒有直接規定，或原句兩可 |
| 邊界 | 在可接受集合內的差異，或材料極少 |
| 複核錯 | 回頭看，是自己的判讀沒套用裁示；網站是對的 |

每一項差異再給一個處理 `action`：

| action | 什麼時候用 |
|---|---|
| 待套用 | 明確錯誤，而且第 6 步寫得出修正計畫（包括身分確定的股名聽錯） |
| 待管理者 | 待確認，或明確錯誤但屬於第 6 步「不得自行修正」 |
| 只記錄 | 邊界、複核錯 |

### 4-1 ①盤勢與③教學的判斷標準（管理者 2026/09–11 的要求彙整）

| 項目 | 標準 |
|---|---|
| 點數 | 原稿超過 5,000 字時各章以 3 點為目標；整章空白是最嚴重的錯（10/29）；少於 2 點是明確錯誤；材料真的少可以少，不湊數 |
| 每點長度 | 盤勢約 70～140 字，教學約 120～220 字；材料只有一句時可以短 |
| 內容 | 要有資訊與具體技術面說明（點位、均線、量能、籌碼、族群、匯率、事件），不寫評語、不照抄口語；教學寫出操作邏輯：做法 → 明講的原因 → 適用對象與條件 → 當天例子 → 要避免的錯誤（「突破季線後回測季線再上去才是買點」，不是「講解了季線」） |
| 依據 | 每一句、每一個數字都對得回原稿；不借鄰股或別段的話；不出現會員通知的存在與用詞；不寫招生與電話 |
| 去重 | 同章與跨章意思相近的點只留一點，換另一個有內容的主題 |

嚴重度與 action：

| 情況 | 嚴重度 | action |
|---|---|---|
| 章節空白；章節幻覺；數字不在原稿且確認是錯的；主詞錯置；通知用語 | 明確錯誤 | 待套用（第 6 步改寫兩章） |
| 章節漏主題，而且漏的是講者明講「第一個重點／最重要」的主題，或該章不到 3 點 | 明確錯誤 | 待套用 |
| 其他漏主題、過短、說明不清 | 待確認 | 待套用（寫得出有原句依據的改寫時）或只記錄；同類反覆出現時寫進提示詞候選，週五的每週檢討會處理 |
| 寫法差異、機械疑點核對後沒問題（例如數字只是格式不同） | 邊界 | 只記錄 |

`report` 是完整日報（純文字，存在紀錄表，郵件不全文照登），依序寫：
1. 一句總結：比對幾檔、各嚴重度幾項。
2. 每一項明確錯誤／待確認：網站寫什麼、原句、依據哪一條裁示、怎麼改（分類與說明全文）。
3. 主流程執行狀況：幾點寫完、郵件狀態。
4. 提示詞候選：同一類錯誤反覆出現時，寫要改哪一段規則或提示詞、附反例原句，並說明要加什麼離線測試。
5. 待管理者裁示的問題。

`diffs` 每一列的 `site`／`review`／`quote`／`reason`／`before`／`after` 要短：郵件卡片直接用這幾欄（網站：／判斷：／原句：／處理：）。

## 5. 寫紀錄、解除複核中

```bash
python scripts/daily_review/write_log.py .daily-review/<日期>/judged.json
```

- `trial` 一律設 `false`（管理者 2026/11/03 提前結束試行）。
- 有 `待套用` 的差異：每日摘要記「修正中」，郵件繼續等，直到第 6 步套用完成（最晚 13:00）。沒有就記「已完成」，郵件立刻放行。
- 不另寄信。Apps Script 在 12:30 起的「爬取狀態」信裡，用卡片列出今天網站改了什麼、各嚴重度數字、明確錯誤與待裁示。

## 6. 修正明確錯誤並更新網站（先跑完第 5 步再推分支）

只修「明確錯誤」，只走現有的修正工具，不碰後台網頁、不用管理密碼：

1. 寫計畫檔（引句要逐字出自 `raw.txt`）：
   - 個股分類與說明：`scripts/repairs/<日期>-source-review.json`，格式見 `scripts/apply_source_review.py`；`previous_note_sha256` 由 `site.json` 的說明算 SHA256。
   - 會員通知產生的買賣列理由（例如通知用語外洩）：`scripts/repairs/<日期>-notice-reason.json`，格式見 `scripts/apply_notice_reason_fix.py`。舊理由只寫 `previous_reason_sha256`、`previous_reason_chars`，**不得把舊句寫進計畫**。
   - 盤勢與教學章節：`scripts/repairs/<日期>-points-review.json`，格式見 `scripts/apply_reviewed_points.py` 與範例 `scripts/repairs/2026-11-06-points-review.json`。
     - 這份計畫會**整份取代 ① 與 ③ 兩章**：網站上原本正確的點要一起放進來（可改寫得更完整），再補上漏掉的主題、刪掉有錯的點。
     - 每一點：`kind`（盤勢用 level／volume／event／flow，教學用 view）、`text`（書面句，數字都要出現在自己的引句裡）、`quotes`（逐字出自 raw.txt，每句至少 6 字）。
     - `sha256` 用 `status.json` 的 `raw_sha256`；`headline` 沿用網站目前的標題，除非標題本身有錯。
     - 推送前一定先跑 `python scripts/daily_review/chapters.py check-plan scripts/repairs/<日期>-points-review.json .daily-review/<日期>/raw.txt`，印出「章節修正計畫核對通過」才推；它會印出郵件會呈現的兩章，逐點讀一次。
2. **股名聽錯（唸的名稱與實際公司不符）**：管理者 2026/11/03 授權直接修，不必先問。以下全部成立才算「身分確定」：
   - 唸的名稱和目標公司讀音相近（同音、近音、少一個字）。
   - 至少一項佐證：講者同時唸了代號；當天或之前的部位／通知紀錄就是這一檔；講到的價位或事件只符合這一檔；同一段落的族群脈絡只符合這一檔。
   - 候選只有一檔。
   成立時做三件事（股名學習，像讓流程從過去的經驗學習）：
   - **改當天網站**：在 `source-review` 計畫把錯的那一列刪掉（action delete），正確的那一檔照原稿重寫一段說明（action insert／update，引句要講的是這一檔），分類照當天原句判斷。
   - **寫進資料庫**：`scripts/repairs/<日期>-name-memo.json`，格式見 `scripts/daily_review/name_memo.py`（heard 唸的名稱、code、name 官方名稱、keys 情境關鍵詞、why、quotes 含唸的名稱的原句）。套用後寫進主資料「名稱判定紀錄」，來源「複核」；之後每天的比對直接套用，不再問模型。
   - 唸的名稱本身就是另一家公司（例：「力致」是 3483）時，**一定要填 keys**：只在這些詞出現時才換（例：「加澤、180」），否則以後真的講到那家公司會被換掉。找不出能分辨的情境詞，就只修當天、不寫資料庫，在日報寫明。
   - 在 `docs/daily-review/裁示紀錄.md` 的別名表加一列（日期、來源「複核」）。
   任何一項不成立：列「待確認」，action 寫「待管理者」，不修。
   - 同一天已推過修正分支時：在原分支上接著提交，只改這一輪要修的計畫檔。前一輪**真的套用成功**（主資料「修正建議」有收據）而這次沒改的計畫不會重套；前一輪失敗的計畫即使沒改也會再套（2026/11/10 起看收據，不再只看 git 差異）。
3. **推送前總檢查（管理者 2026/11/10：格式要在這裡確定，GitHub 只負責套用）**：
   - 跑 `python scripts/daily_review/preflight.py --date <YYYY/MM/DD>`，印出「推送前檢查通過」才推。它一次檢查所有計畫：欄位、指紋格式、原稿指紋、每句引句至少 6 字且逐字在原稿、新文字不含通知字眼、通知計畫一份只改一張表、章節品質。
   - 再對每份計畫跑一次套用工具的**預覽**（不加 `--apply`）：`apply_notice_reason_fix.py`、`apply_source_review.py`、`apply_notice_ruling.py`（有哪份跑哪份）。預覽會核對正式試算表上的唯一列與舊說明指紋；`apply_source_review.py` 若因代號表網路受限而停在「載入代號對照表」，在日報註明，其餘檢查仍要通過。
   - 雲端環境的金鑰是 Base64：只要先 `import common`（`scripts/daily_review/common.py`）就會自動還原，預覽工具都已處理，不必自己解碼。
   - 任一項不通過就改計畫、重跑，**不要先推到 GitHub 試**（11/10 推了五輪，三輪是計畫檔本身的錯）。
   - 指紋一律用 `site.json`／預覽印出的值計算：`update`／`delete` 都要 `previous_note_sha256`；同一則通知改多檔放在同一份 notice-reason 計畫即可（工具會累積寫入）。
4. 推到分支 `daily-review/apply-<日期YYYYMMDD>`（只放計畫檔與裁示紀錄的改動）；若推送被拒（雲端工作階段只能推 `claude/` 開頭的分支），改推 `claude/daily-review-apply-<日期YYYYMMDD>`，效果相同。工作流程 `daily-review-apply.yml` 會依序預覽、套用、讀回，成功後把複核紀錄改成「已修正」、把股名寫進「名稱判定紀錄」；套用失敗就標「修正失敗」，郵件照當時內容寄出。
5. 不得自行修正（改列「待管理者」）：
   - 新增或更動今日買賣（成交事實）。
   - 其他日期的資料。
   - 寄送帳本。
   - 分類規則本身的改變（新的邊界寫法）。

## 省用量的規則

- 只讀這裡列出的檔案，不要全庫搜尋，也不要讀 `pipeline/pipeline.py` 全文。
- 原稿只讀一次，判讀一次寫完。
- 不重跑主流程、不呼叫 Gemini、不開瀏覽器。
- 判斷差異時只看 `diffs.md`、`chapters.md` 與相關原句，不重讀整份原稿。
