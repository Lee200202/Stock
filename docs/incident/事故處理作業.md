# 盤勢有據：自主事故處理作業（2026/11/26 管理者核准）

管理者要求：GitHub 工作流程出錯時，系統自己讀錯誤、判斷該重跑、修 pipeline、更新網站，還是更新 Apps Script，並自己排下一次執行，人工不介入也能持續運作。有錯就回報；需要管理者決定的才找人。

## 一、整體流程

1. **正式工作失敗**
   - 觸發：`incident-triage.yml` 的 workflow_run 事件，不用模型。
   - 讀失敗步驟與錯誤紀錄後分類，用的規則是 `scripts/incident/rules.py`。
   - 結果寫進複核紀錄「事故紀錄」。
2. **依分類決定動作**

   | 分類 | 動作 |
   |---|---|
   | 暫時性錯誤（Sheets 429、Gemini 503、網路、GitHub 執行環境） | 當天後面還有排程就交給下一輪。當天最後一輪失敗，或同一工作連續 3 次失敗，就 20 分鐘後重跑一次。每個工作每天最多自動重跑 2 次，超過就通知管理者。 |
   | Gemini 每日額度用完 | 太平洋時間午夜後 5 分鐘重跑（台北 16:05，夏令 15:05），並通知。 |
   | 主表容量 | 換卷機制已處理時立刻重跑；沒換卷就通知。 |
   | 版本落後、設定缺漏 | 通知管理者。正式 /exec 只有擁有者能切，金鑰由管理者貼。 |
   | 程式錯誤 | 標「待雲端處理」，交給雲端排程「盤勢有據 事故處理」。 |

3. **每 30 分鐘掃一次**
   - 時段：`incident-triage.yml` 的 schedule，台北 08:07–22:37。
   - 執行到期的重跑：`rerun-failed-jobs`，用原本的排程事件重跑同一次執行。
   - 核對重跑結果：重跑由 GITHUB_TOKEN 發起，結束時不會再觸發 workflow_run，所以由掃描補判斷。
   - 把整點以前的通知推出去。
4. **雲端事故處理**（本作業第三節）
   - 讀錯誤、離線重現、修正。
   - 推到 `claude/incident-YYYYMMDD-INC…` 分支。
5. **`incident-fix.yml` 把關**
   - 依序做：守門（`scripts/incident/fix_gate.py`）、離線契約與網站檢查；改了 pipeline 再加真實模型重播，沿用每週檢討的重播與保留日規則。
   - 全部通過時：
     - **前兩週（從 2026/11/26 起）**：開 PR，由管理者核准合併。
     - **之後**：管理者把 repo 變數 `INCIDENT_AUTO_MERGE` 設成 `true`，才改成自動合併。
   - 結果寫回事故紀錄並推 LINE。

## 二、上限與界線

- 自動重跑：每個工作每天 2 次。
- 雲端修正：每天 1 件、每週 3 件。
- 同一個錯誤指紋修過一次仍失敗，就停下等管理者。
- 雲端不能做：
  - 直接推 main；
  - 改 `.github/`、`scripts/incident/`（自己的規則與上限）、`AGENTS.md`、技能文件、requirements；
  - 刪改既有答案檔；
  - 寄信或推播；
  - 動訂閱者資料或寄送帳本；
  - 切正式 /exec。
- 改到 Apps Script 原始碼時，合併後還要建立 Apps Script 新版本，再由擁有者切 /exec；通知會寫明。
- 每次判斷都寫進「事故紀錄」。需要通知的，同一小時合併成一則 LINE「事故處理」卡；需要管理者處理的會立刻推。

## 三、雲端排程「盤勢有據 事故處理」

- cron（UTC）：`0 5,8,12 * * 1-5`，即台北週一到週五 13:00、16:00、20:00。
- 模型與工具：claude-opus-5-5、high；工具 Bash、Read、Write、Edit、Glob、Grep。
- 環境：與另外兩個排程共用。
- 沒有待處理事故時，第一步就結束，只用掉很少的用量。

### 提示詞（照抄到雲端排程）

```text
你是「盤勢有據」的事故處理員。GitHub 正式工作流程失敗後，incident-triage.yml 已經分類，把「程式錯誤」寫進複核紀錄「事故紀錄」（處理狀態「待雲端處理」）。你的工作：讀錯誤、離線重現、判斷要修哪裡、做最小修正、推到分支交給 incident-fix.yml 把關。全程繁體中文。

0. 環境檢查：環境變數 GOOGLE_SHEETS_SERVICE_ACCOUNT、SPREADSHEET_ID、REVIEW_LOG_ID 任一缺少，立刻停止並回報「雲端環境變數未設定」。安裝套件一律用 `python -m pip install -q -r requirements.txt cryptography cffi pyyaml`，並 `export GEMINI_API_KEY=offline`。若腳本報「不是服務帳戶金鑰」，立刻停止並回報，不要自行檢查金鑰內容。不讀、不印、不搜尋任何金鑰。
1. `python scripts/incident/cloud_queue.py list`。印「沒有待處理事故」就結束。有的話只處理最早的一件：`python scripts/incident/cloud_queue.py claim --id <事故ID>`，claim 失敗（別的工作階段已接手）就結束。
2. 先讀 docs/incident/事故處理作業.md、AGENTS.md 指到的協作技能入口，再讀錯誤摘要與失敗步驟對應的程式。判斷這是不是程式問題：
   - 不是程式問題（資料、設定、金鑰、配額、Google 或 GitHub 服務故障、需要管理者定義的分類邊界）：`python scripts/incident/cloud_queue.py release --id <事故ID> --state 待管理者 --note "<兩三句：查了什麼、原因、建議管理者怎麼做>"`，然後結束。
   - 已經不再發生（例如之後的排程已成功、main 已有人修好）：release --state 不需修正，note 寫依據（哪一次執行成功、哪個提交），然後結束。
3. 是程式問題：在離線環境重現（用假的 Google／Gemini 回應或既有測試，不呼叫 Gemini、不寫正式試算表）。先寫一個會失敗的測試，再做最小修正讓它通過。修正對象只會是 pipeline/、transcript.py、market_data.py、scripts/（scripts/incident/ 除外）、public-site/（網站與 Apps Script 原始碼）、site-api/。新測試加到 scripts/run_offline_contracts.py 的 SUITES（只准加）。改到股票分類或說明規則時，依技能與裁示紀錄，不自己訂新的分類邊界；需要新定義就照第 2 步 release 待管理者。
4. 寫 docs/incident/<事故ID>/plan.json：{"incident_id","target"（pipeline／網站／Apps Script／腳本）,"cause","fix","repro"（重現指令與重現前後的結果）,"replay_days","holdout_days"}。改了 pipeline/pipeline.py 一定要有 replay_days（有答案檔的相關日期）與至少兩天 holdout_days（scripts/golden/ 有答案檔、與 replay_days 不同的日期），合計不超過每週檢討的上限。跑 `python scripts/run_offline_contracts.py`（SPREADSHEET_ID=offline）全部通過才推。
5. 從 origin/main 建分支 `claude/incident-<台北日期YYYYMMDD>-<事故ID>`，所有修改放進提交，推送。不推 main、不開 PR（工作流程會開）。然後 `python scripts/incident/cloud_queue.py release --id <事故ID> --state 已提交修正 --branch <分支名> --note "<一句話：修了什麼>"`。
6. 回報：事故ID、判斷、修改的檔案、分支名、還需要管理者做的事（例如改到 Apps Script 時要建立新版本並由擁有者切 /exec）。
```

## 四、擁有者要做的事

- 前兩週在 GitHub 核准事故修正的 PR。LINE 卡片的「看修正分支」會連過去。
- 穩定後，若要改成自動合併，就在 repo 變數設 `INCIDENT_AUTO_MERGE=true`。
- 版本落後與設定缺漏類的通知，照卡片說明處理：切 /exec，或補金鑰與分享權限。

## 五、驗收方式

- 離線：
  - `python -B scripts/test_incident_rules.py`：分類、決策、上限、守門、事故卡；
  - `python -B scripts/sim_failures_1126.py`：各種故障實際觸發。
- 正式唯讀試跑：Actions → incident-triage → Run workflow，mode 選 `triage`，填一個過去失敗的執行 ID，勾 dry_run。只印分類與決策，不寫紀錄、不重跑、不通知。
