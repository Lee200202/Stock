### 1.6 語氣強度

- 「務必」「嚴謹」「鄭重提醒」：管理者曾經被同一類錯誤影響過，這一輪要附證據。
- 「跟說好不一致，嚴懲之」（10/14）：做了沒被要求的改動。立刻完整恢復，只做被要求的那一件（第 7 節）。
- 「很嚴重結果請修正」（10/08 逐字稿優於簡訊分類）：優先處理，先停止會繼續擴散的路徑。

## 2. 授權帳本與擁有者步驟

### 2.1 已持續有效的授權（仍以最新訊息為準）

- 讀取任何公開頁面、公開 API、GitHub runs 與日誌。
- 唯讀重播（`raw`、`preview`、`titles`、`verdicts`）。注意它們會用模型額度，送出前先估算（`stock-rule-tuning` 第 9 節）。
- 本機修改程式、測試、文件；推送 main（管理者每一輪都要求「github 部分也請推送上去」）。
- clasp push 與 create-version。
- 觸發與取消 Actions（10/05）。

### 2.2 每次都要被點名的動作

| 動作 | 為什麼 |
|---|---|
| 單日 `apply`／`apply-rules` 寫正式資料 | 會改公開內容；管理者要在對話中說出日期，或說「更新今日網站內容」 |
| 刪除資料列 | 後台提示無法復原；在問題裡列出日期、代號、哪一列 |
| 加名稱別名（`CONFIRMED_NAMES`） | 10/15 管理者拒絕當輪直接加「成城→勤誠」 |
| 寄送 Email／LINE（含測試信、通知另一位好友） | 對外發送；10/05「請訊息通知另一位好友……就這一次而已」是單次授權 |
| Worker 部署 | 正式服務改動 |
| 重新套用其他工作階段正在手動整理的日期 | 會蓋掉人工修正 |

### 2.3 只有擁有者能做的事

- 把 Apps Script 正式部署 `/exec` 移到新版本：clasp 帳號推送與建版可以，但部署時會被拒（「Only users in the same domain as the script owner may deploy this script」）。回報時寫「已建立版本 N，請到 部署作業 → 管理部署作業 → 編輯 → 版本 N」。
- 登入後台、輸入管理金鑰與 Google 密碼。
- 在 LINE Official Account Manager 核對月用量、在 Google AI Studio 看額度（管理者會貼 RPM／TPM／RPD 給我）。
- 修改權限設定、指令許可規則（10/08 管理者曾要求「在設定裡替這個指令加一條 Bash 權限規則」——這是管理者自己的設定，可以說明怎麼加，不替他改）。

### 2.4 永遠不做

- 印出或寫入 GitHub token、橋接 token、Gemini／Claude 金鑰、管理金鑰。
- 在公開文字放電話、Email、訂閱名單。
- 把會員通知的存在寫進前台。
- 在 GitHub 公開 repo 放私人全文或金鑰。

## 3. 中途訊息、貼上紀錄與截圖

- 中途插入的訊息（畫面上以 `<!-- reply -->` 引用我上一句話開頭）是對那一句的回覆或追加要求。先判斷是修正方向（立刻採用）、追加項目（排進待辦），還是只是補資料（例如貼一段 GitHub 日誌）。
- 管理者常把另一個工作階段的進度整段貼上，後面接「請繼續完成上述任務」。做法：把貼上的內容當成進度紀錄，先查實際狀態（git log、run 結果、正式站），確認哪些真的完成、哪些只寫了「正在進行」，再接續。不要直接相信「已完成」。
- 貼上的日誌是證據：找出 ✗ 行、`品質錯誤`、`Error:`、`exit code`，從最早的失敗開始追。
- 截圖上有紅圈或箭頭時，以紅圈處為修改目標；「我指的是點選紅圈處要連結到」（10/06）表示上一輪理解錯了位置。看不清時用瀏覽器窗格打開同一頁核對。
- 管理者有時會把同一則訊息貼兩次，或在 Codex 與 Claude 兩邊各發一次；以最新、最完整的那一則為準。

## 4. 多個工作階段並行

- 管理者同時開 Claude Code 與 Codex，兩邊都會改 `C:\Users\user\Stock`。開始前 `git status --short`、`git log -5 --oneline`、`git fetch` 看有沒有別人推的 commit；未追蹤或已修改但不是我改的檔案不碰、不加進 commit。
- 推送前 `git pull --rebase`；衝突時保留對方的改動，只合入我的部分。
- 同一個 workflow concurrency group 同時只能有一個 pending；別的工作階段剛排了 run，就等它結束，不要取消。
- 另一個工作階段手動整理過的日期（後台人工修正、已核對說明）不要重新 apply；先問。
- 技能的版本化來源在 `docs/stock-skills/skills/`，Codex 讀的是 `~/.codex/skills/stock-*/`；兩邊都更新後用建置腳本 `--check-installed` 確認一致。

## 5. 交給其他 AI 的 prompt

管理者常說「我會拿給其他 ai 執行」。這類交付的格式：

1. **開頭三行**：要改的網址與頁面、要讀的正本檔案（`public-site/gas-source/*.html|gs`，不是未進版控的 `apps-script/` 鏡像）、不可以碰的東西（金鑰、寄送、`/exec`）。
2. **現況盤點**：實際操作正式站後的逐節表格（區域、現在的狀態、要求）。例：10/03 技術頁十四個一級標題的互動盤點。
3. **要做的模組**：每個模組寫出要回答的問題、互動方式、資料來源、文字上限、動畫與減少動態時的行為。
4. **設計變數與程式範本**：附實際的 CSS 變數、類別名稱、現有圖解的程式片段與檔案行號（管理者 10/13：「可提供相關程式碼供新 ai prompt 參考」）。
5. **限制**：已確認的規則（通道可見性、按鈕必須有互動、回頂在底部中央、不加說明性贅字……）逐條列，標日期。
6. **驗收**：可量測的條件與指令（寬度 1440／1280／768／390／360、深淺色、放大字級、鍵盤、無 JavaScript、減少動態；`scripts/` 裡的檢查腳本名稱）。
7. **部署順序與回退**：GitHub → Apps Script 版本 → 擁有者移 `/exec` → 正式讀回；回退到哪個版本。

不放金鑰、不放私人原文全文。交付時說清楚「這一輪只完成規格，正式網站尚未改版」。管理者也可能把對方 AI 的回覆貼回來要我審查——按第 3 節處理。

## 6. 進度與結案報告

- 開工第一句：要查什麼、用哪些技能、會在哪裡驗收。
- 進度訊息：已確認的發現加上下一個動作，一到兩句；不寫「持續優化中」。
- 結案順序：**結果**（完成／有待驗項）→ **改了什麼、為什麼** → **實測**（指令、run 編號、日期、樣本）→ **各面版本**（commit、Apps Script 版本、`/exec` 版本、Pages）→ **未驗與需要管理者做的事**。
- 涉及通知時單獨一行寫：有沒有寄送、帳本有沒有變。
- 數字要可查：測試項數、請求數、耗時，標明是本機還是正式站。
- 自己犯的錯要寫出來（例：10/10「整理程式時誤刪一個函式……GitHub 上有約 5 分鐘是會在寫入前中斷的版本」）。
- 檔案用可點的連結；外部網址用有意義的標籤。

## 7. 被糾正時

1. 先完整恢復到管理者說好的狀態（10/14 版面放大被要求「回復跟好幾前板格式」：用 git 找到那一版，逐項恢復，再只做右側子目錄這一件事）。
2. 把被糾正的規則寫進記憶或技能，標日期與原話。
3. 不辯解、不順便加新東西；回報恢復了哪些、現在只改了哪一件。
4. 如果糾正和先前的規則衝突，以最新的為準，並在技能裡更新舊規則（不是並存）。
