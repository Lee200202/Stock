# 規則調整與回測證明

擔任規則調整工程師。觸發情境：管理者指出某天分類或說明錯了、同一份原稿每次跑出不同結果、套用被答案檔或品質關卡擋下、或被要求「確保該規則適用未來新進來的資料」「拿去訓練」。逐日判讀與正式更新本身用 `stock-content-audit`；書面寫法用 `stock-public-writing`；中斷與續跑用 `stock-automation-triage`。

原則：**修流程，不修那一列**。不手動補資料讓答案過關、不針對股名寫特例、不全面放寬門檻；用有原文依據的通用規則處理成因，並在其他日期檢查回歸。保留管理者已接受的多標籤驗收政策（例如 10/15 持股／注意同組），記錄政策版本、適用範圍及案例理由；strict 診斷分數與 accepted 驗收分數分列，不能擅自用 strict 推翻已接受結果。標籤可接受不等於部位事實可互換，不得據此放寬成交與部位帳本。

讀 [規則調整手冊](references/tuning.md)：成因分類與對應修法第 1–2 節；重播模式與答案檔第 3–4 節；保留日回測與變異量測第 5–6 節；測試、提示詞同步與快取版本第 7–8 節；用量、停止條件與回報第 9–10 節。

分類／生成行為改動：先用真實原稿重現 → 最小正反例 → 受影響歷史案例 → 相關測試 → 預算內唯讀重播 → 有授權才正式套用。`raw`、`rules-only`、人工輔助預覽的資料注入不同，須讀當前腳本確認，不能只看模式名稱。文件或安裝檢查不發動模型。重跑仍冒出不同錯誤時，停止套用迴圈，檢查輸入範圍、身分、證據、快取與生成路徑。

被要求量化優化、技能路由、A/B、LLM 裁判或「測幾次就上線」時，讀 [技能與 Agent 評估](references/evaluation.md)。先凍結比較條件與成功標準，再比較路由、實際採用、任務結果及副作用；不要把多次重跑當獨立樣本，也不要將已調整過的歷史日稱為未見保留集。網站設計的行為標準由 `stock-site-design` 定義，本技能負責評估方法。

回報要寫清楚：實際跑了哪幾個 run、各是哪個 commit、用了多少模型請求、哪些日期只做了本機回測。「訓練」在本專案指回歸樣本與規則調整，不是訓練模型權重。
