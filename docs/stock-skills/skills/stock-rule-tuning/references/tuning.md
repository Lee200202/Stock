# 規則調整、重播與回測證明

## 現行解讀：語意、事實與發布邊界（2026/10/21）

本文件下方的舊案例保留診斷沿革，不表示現在仍應增加文字詞表或以網站作答案。管理者已要求語氣／文體交 AI 合批審閱；來源、日期、主體、部位與原句仍核對。候選 AI-first 實作必須實測通過才合併，不能將尚未通過的方案描述成正式系統已採用。

- **分清四種故障**：候選根本未建立、請求未含該候選、模型未回該 ID、模型有回但證據／語意不合。每批保存預期 ID、實收 ID、缺答、未知 ID、可追查的原始回覆及版本；缺答不算反對或中性。不用增加呼叫掩蓋收件／解析問題。
- **用途不是正名**：原文「一支股票叫做＋代號＋錯字名稱」仍可能是在點公司；「出大量紅棒」是量能。盤點／同音比對只提出候選，不能用官方代號存在或近似股價直接確認公司。用途覆核也可能錯，須測它造成的新增誤排。
- **部位不是語氣**：初判、覆核、收尾同為持股，不等於三份部位證據；對觀眾說你有獲利、我們來看，不證明講者持有。已確認未全出部位與當日自身分析才依現行發布政策列持股；已出場後現在重新看好，仍可列注意，不自動重開回合。
- **等待不是同一件事**：「尚未持有」本身不負面；「目前條件未到所以不進場」是目前進場限制。禁止賣與禁止買分成獨立事實，附本股原句。這些欄位不能用來借用相鄰公司的成交量、成本或資金條件。
- **待核要實測最後邊界**：`hint_only`、`needs_review`、`_repair_gaps` 等狀態不保證真的阻止錯列公開。檢查快取、`apply_verdicts`、補漏、文章與最終公開列；語氣提示未獲可用複核時不得冒稱核定。單檔未定隔離本股，整體裁決程式未執行則不能報品質已通過。
- **行情差距只是線索**：歷史成本遠離當日價格可以正確，不用價位距離挑一個較像的數字。已確認跨股／無來源數字仍須修正或隔離，不能因改為待核標記就默許公開。「數字錯了就算了」只出現在第三方貼文，不是管理者授權。
- **同檔合作按版本驗收**：保留另一工作階段未提交修改，不重置、不切換其工作樹。每個 run 綁 commit；整合前的成功不能套用到整合後。報告自身修改、他方修改、正式來源修復與未輔助品質時分列。

## 1. 判錯的成因分類（先歸類，再修）

管理者 2026/10/14 要求逐一思考「是判定資訊不足、前後文抓取範圍不足、語氣關鍵字有誤，還是判定方式過於嚴苛」。實際遇過的成因如下：

| 成因 | 典型症狀 | 實例 | 修法方向 |
|---|---|---|---|
| 紀錄資訊不足 | 持有的股票被改成觀望 | 毅嘉：持有是由持股列建立、沒有買入紀錄 | 「紀錄上持有」納入近期持股列（當時 15 天）且之後無賣出 |
| 上下文範圍 | 說明混進別的話題 | 鈺邦：說明跨到匯率與成交比重 | 大盤子句清理；名稱附近的窗口遇到別檔或轉場就停 |
| 語氣關鍵字 | 正面句被判負面 | 嘉澤「大盤大跌時逆勢大漲」被「大跌」判成不碰 | 大盤當主詞、讓步句前半不算本股的負面；「逆勢大漲、抗跌」算偏多 |
| 問句與提問者 | 觀眾的部位或問句當成講者看法 | 台化「張總，我手中有6張台化…要出嗎？」；鴻海「可不可以買」被讀成禁買 | 提問者的持有不是會員持股；問句不是表態 |
| 門檻過嚴 | 明講的結論還要三票才收 | 群聯「我說不要」、台達電「我沒有台達電」 | 明講句型直接歸類（被問能不能買→回答不要、X 不能買、X 可以買、我沒有 X） |
| 門檻的預設值 | 沒有任何一票支持卻照流程公開 | 台塑化、南亞只在「台塑、台話、南亞、台塑化」名單裡 | 觀望兩類沒有一票支持公開、且有票明講只是回顧或點名→不公開 |
| 流程順序 | 列在某一步被整筆丟掉，後面看不到 | 聖暉：日期未明的回顧列在裁決前被清空 | 沒有日期的回顧列也回頭找現況說法；直白禁令「你們不要玩」 |
| 名稱身分 | 名字對到另一家真公司 | 華義（模型代號）、宏達電（原文價位 238／239／260，待核鴻海） | 名稱、代號、原字及上下文共同核對；價格差距只提示疑點，不單憑價格改公司 |
| 一般詞撞名 | 日常用語被當股票 | 「最大量這一根 K 線」→大量（3167） | 日常用語核對排除的列不送裁決；提示詞寫明 K 棒術語不是公司 |
| 快取與版本 | 新規則沒生效 | 台塑化沿用前一輪快取的「待確認」，而套用「待確認」是不動 | 快取的「待確認」套到公開列時以「排除」套用；規則變了就升 `VERDICT_VERSION` |
| 模型單次變異 | 同稿每次漏不同檔 | 旭隼、群聯、勤誠（「成城」）在不同輪落不同類 | 找可以確定的原文依據（「這我的股票…6409旭準」）改直接歸類；名稱別名需管理者同意 |

## 2. 修法的優先順序

1. **找原文能確定的依據**，寫成直接歸類（不送問卷）：當日通知、明講今天買賣、紀錄上持有、明講持有（「我的股票…代號股名」）、明講禁令、被問後回答不要、明講可以買。
2. **修判斷用的句型或範圍**：問句、提問者、大盤主詞、讓步句、轉場、假設句、買進條件（「只能在跌的時候買，漲的時候不要追」是買進條件，不是禁令）。
3. **修預設值**：沒有證據支持時不公開、或保持流程分類，要看歷史上這個預設造成的對錯；動預設值前先列出受影響的歷史案例並核對原稿與當時通知／部位及來源判斷。正式站只核對發布結果，不作分類答案。
4. **最後才動門檻**。管理者 2026/10/08 的規則：跨公開／不公開、改進或改出買入、賣出、會員持股要三票一致；觀望兩類互換兩票；晚補的列三票。放寬只限有理由的窄例外（例：晚補列有兩票以上可用票全部一致、沒有反對票）。
5. 名稱別名（`CONFIRMED_NAMES`）屬於管理者確認的名稱表：**加入前先問**（2026/10/15 管理者拒絕在當輪直接加入「成城→勤誠」）。

不做：為某一檔寫特例；手動補列讓答案過關；把所有警告改成通過；全面降低觀望注意的門檻以增加數量。

量測來源應按三個軸拆開，不把標籤通過當作事實通過：

- 紀錄上未出場是部位事實；本集只在新聞背景點名，不能因此強制新增持股分析卡。已有部位不因未公開卡片而被自動結束。
- 「等回測支撐就可買」已給可執行條件；「等我判斷完再告訴你能不能買」還沒給可執行買點。兩者都不是當日成交，後者不能因有「等」字被當成觀望注意。此語意由既有批次問卷回答，原句／主體仍核對，不加逐股請求。
- 名稱缺漏但念出代號時保留身份待辨候選，不直接補交易。數字也可能是價位、年份或聽打錯字；官方有同號公司，不代表該段真的在講它。
- 書面化回覆未採用時，舊句不自動等於正確。批次審閱另辨「輸入原句本身是否有本股依據」；已確認跨股／缺乏依據的子句若仍留在最終文字，應隔離該列並留底，不能把文體未通過當作允許保留幻覺。未回覆或語意不確定須與已確認錯誤分開。

## 3. 重播模式（`.github/workflows/regenerate-verified.yml`）

| mode | 寫入 | 答案檔的角色 | 用途 |
|---|---|---|---|
| `raw` | 否 | 只比對 | 驗證規則本身；也不注入 reviewed_notes 與不得出現的說法 |
| `preview` | 否 | 單一分類注入成人工裁決 | 看注入後的文章；不能證明規則對 |
| `apply-rules` | 是（比對通過才寫） | 只比對，失敗就保留正式資料 | 正式更新（2026/10/15 起的作法） |
| `apply` | 是 | 注入 | 舊作法，避免使用 |
| `titles`／`verdicts` | 否 | — | 標題試問、裁決一致性量測 |
| `reviewed-notes(-preview)` | 是／否 | — | 只更新已核對的書面說明 |
| `reading-preview`／`reading-apply` | 否／是 | — | 閱讀校正版 |
| `notice-preview`／`notice-apply` | 否／是 | — | 會員通知語意修正 |

- 同一 concurrency group 只留一個 pending；連續排多個 run 會互相取消，先查。
- 單日 `apply-rules` 屬於正式資料更新：依當前明示範圍授權執行；已要求繼續其他日期驗收與網站更新時，可在來源核對、備份與限定範圍後處理，記錄選日及變更，不逐日重問。
- 每個 run 讀日誌：`最終分類`、`✗／✓` 比對行、`品質錯誤`、`寫入後核對`、`網站郵件查詢…刷新完成`。

## 4. 答案檔（`scripts/golden/YYYY-MM-DD.json`）

| 欄位 | 意義 |
|---|---|
| `names` | 代號→名稱（比對報告用；缺名稱時報告看不出是誰） |
| `must` | 該日該代號→有依據的允許分類清單；多標籤要記裁示與理由，不建立全域等價 |
| `must_not` | 不得出現的代號 |
| `required_categories` | 必須同時存在的分類（如嘉澤「會員持股＋觀望不碰」：剩餘部位與暫不買回） |
| `forbidden_categories` | 當天整體不得出現的分類（如沒有成交時禁止 buy／sell） |
| `note_must_not` | 某檔說明不得含的字串 |
| `reviewed_notes` ＋ `reviewed_notes_sha256` | 已核對的書面說明，綁原稿指紋 |
| `equivalence`、`why`、`review_basis` | 管理者裁示與判斷依據的文字紀錄 |

建立方式：完整讀當天保存的原稿與通知，**先自己獨立分類**（公司、主體、日期、部位、現況立場、原句），再看正式站與流程結果；只把有明確依據或管理者裁示的列入。可接受兩種結果的股票（教學回顧或不碰）留在 must 之外。

## 5. 保留日回測（新規則上線前必做）

- **命中回測**：把新句型套到所有有答案檔的日期（9/29 起）原稿，列出每一個命中的股票與其答案分類；命中答案不符的就是誤判，先修規則。實例：「你們不要追」的禁令在 10/02 台達電「只能在跌的時候買，漲的時候你就不要追」誤中，加「本股到禁令之間有買進條件就不算」後只剩目標案例；同一條件若檢查整句，又會被前一個話題的「跌的時候有錢買」擋住目標案例，所以範圍限定在本股名稱到禁令之間。
- **價位與名稱線索**：官方行情只供查核定位；近期價差不能證明逐字稿主體錯誤。回到完整原稿、轉場與公司行動，交語意審閱確認；不以價格帶自動換股或刪句，案例與通用回歸均保留前後證據。
- **文字規則**：對全部已發布說明回測（見 `stock-public-writing` 第 9 節）。
- **預設值改動**：列出歷史同票型案例，用原稿、當時通知／部位獨立核對；正式站只供確認發布現值。缺答是未完成，不推論成沒有立場；明確 about_itself=false 才是有效 ignored 票。
- 沒有答案檔的日期，先完整原稿及當時通知／部位獨立判定並保存，再比工作流；正式站API只核對發布結果及現值，不能充當分類答案。標註來源審核草稿與未定候選，不能宣稱通過金標。

## 6. 變異量測與停止重跑

- 同一份原稿模型每次判讀都可能不同。把當天所有 run 的「最終分類」整理成「股票 × run」表，看哪幾檔在不同 run 落在不同類；穩定的不用動，變動的逐檔追是哪一步造成。
- 同一天連續重跑三次仍有新錯誤，停止相同條件重跑，定位輸入遺漏、主體、時間軸、問卷欄位及證據結構。修通用流程後再實測，不加關鍵字方向捷徑、不灌人工分類或說明，發布僅使用已成功的同次候選。
- 裁決快取（「分類裁決」表）以段落指紋＋`VERDICT_VERSION` 為鍵。規則或可引用範圍改了就升版號；注意沿用的「待確認」不能被當成「不動」。
- 失敗的 apply 不會寫入正式資料，正式站保持上一個通過的版本；回報時寫清楚哪一版在線上。

## 7. 本機重現與測試

- 本機載入流程：設定假的 `SPREADSHEET_ID`、`GEMINI_API_KEY` 環境變數，用 `importlib` 載入 `pipeline/pipeline.py`，讀保存的原稿（如 `scratch/audit1015/original/source-audit-*/source.json` 的 `raw`），直接呼叫 `plain_current_stance`、`_audience_prohibition`、`preserve_explicit_holdings`、`verdict_class` 等函式。
- 裁決測試：用 `unittest.mock.patch` 替換 `_verdict_known`、`_verdict_cache`、`call_gemini`、`budget_left`、`GEMINI_KEYS`，餵固定的問卷答案；原文前後加無關的填充句，避免段落太短。
- 新增可交接的回歸契約應放入版控，例如 `scripts/test_coverage_contracts.py`，以實際測試入口為準。舊 `tests/` 可能被 .gitignore 排除，不會出現在新工作樹／CI；不能把另一份 checkout 的測試數當成本輪結果。先確認測試檔、相依套件及匯入路徑，缺少舊套件時明列未驗範圍，不為了綠燈重建空測試或宣稱全套通過。
- 修改既有測試的期望值前，先確認是不是違反管理者的既有規則（例：10/08「三票一致可移出持股」的測試，曾因新規則過寬而失敗，應收窄規則而不是改測試）。

## 8. 提示詞與同步

- 提示詞常數：`POLICY`、`EXTRACT_SYSTEM`、`AUDIT_SYSTEM`、`EXCLUDED_REVIEW_SYSTEM`、`ADJUDICATE_SYSTEM`、`STOCK_CONTEXT_SYSTEM`、`PUBLIC_EDIT_SYSTEM`、`EPISODE_TITLE_SYSTEM`、`INDUSTRY_PICK_SYSTEM`。預設用規則與定義描述；歷史曾把示例抄成標題。若實驗 few-shot，範例須與評分集分離、明確標成非發布資料，測是否被照抄；不能直接放進正式流程後只看單次成功。
- GAS 端有對應片段（`Adminpipeline.gs` 的 `PIPE_EXTRACT_SYSTEM`、`Cmoney.gs` 的 `CM_PARSE_SYSTEM`、`Presentationquality.gs` 與 `JavaScript.html` 的 `PUBLIC_CONFIRMED_NAMES`）由 `scripts/sync_quality.py` 從 Python 產生；改完執行一次並確認 GAS 檔有沒有差異，有就要部署 Apps Script（見 `stock-release-check`）。

## 9. 模型用量

- 額度按當前專案、模型與層級查證，不固定寫成 15 RPM／500 RPD，也不能把同專案多把 key 當多份額度。單日請求數由當前管線日誌估算；10/08、10/15 舊紀錄只能作歷史案例。實驗前計算 A／B × 日期 × 重複次數，加裁判、重試及自動流程保留量，設停止預算。
- 合併請求：問卷一輪一個請求帶多檔、校字一批、補充說明一批；不逐檔發送。
- 已核對且原稿相同的說明與裁決沿用，不重問。
- Google 文件列 RPD 於太平洋午夜重置；轉成台灣時間須按日期及日光節約時間計算，不能全年固定 15:00。晚間用量可能影響隔天上午。檢查現行 `GEMINI_RPM`、重試與實際帳戶限制；不同 API 計量與額度各自核對。

## 10. 回報格式

1. 每個錯誤的成因屬於第 1 節哪一類、證據原句。
2. 修了什麼規則（通用句型），為什麼不是放寬門檻或特例。
3. 回測：命中回測的日期與命中清單、文字回測的改動數、預設值改動的歷史案例。
4. 實際執行：run 編號、commit、模式、結果；模型請求數。
5. 線上狀態：正式站目前是哪一個 run 的結果；未驗證與仍不穩定的股票。

## 11. 比較新舊技能與 Prompt

量化品質、路由、保留集擴充、AI 裁判及離線／線上 A/B 的完整方法見 [技能與 Agent 評估](evaluation.md)。先確認是否注入分類、核對說明或人工裁決快取，分開報告 strict／accepted、獨立／人工輔助、開發／保留集。歷史資料量以完整逐字稿清單盤點，不只使用已有答案檔；模型初標不等於人工答案。數據不足時交付缺口與下一批計畫，不宣稱已證明永久穩定。

## 12. 重複漏收時先分解哪一層失敗

同一檔多次未公開，逐份核對，不只看最後的空標籤：

- **沒有候選**：名稱盤點／ASR身分／來源範圍是否根本沒有送到。候選提議不能直接變成公開公司。
