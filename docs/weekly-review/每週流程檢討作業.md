# 每週流程檢討：雲端排程作業步驟

本檔是每週五 17:00 雲端排程「盤勢有據 每週流程檢討」照做的步驟（等同技能）。管理者 2026/11/06 建立：每週五把這一週每日複核記下的錯誤、邊界與流程疑點整理起來，針對主流程 `pipeline/pipeline.py` 做通用的規則修整，並在線上完成驗收。

- **分工**：固定動作交給腳本；AI 做四件事：
  - 讀案例與原稿。
  - 歸因。
  - 改通用規則並補測試。
  - 寫報告。
- **把關**：推到分支以後，由 GitHub 工作流程 `pipeline-weekly.yml` 依序守門、跑離線契約、用真實模型重播，三項全部通過才合併 main，接著做線上驗收。
- **合併原則**：未通過的實驗不合併（AGENTS.md）。
- **與每日複核的關係**：每日複核（`docs/daily-review/每日複核作業.md`）負責當天的錯誤；本檔負責「同一類錯誤不要再發生」，以及當天沒修好的錯誤。
- **範圍**（管理者 2026/11/06）：個股分類與說明，加上郵件 ①盤勢總覽與 ③教學重點兩章。差異明細裡代號是 ① 或 ③、類型以「章節」開頭的列就是兩章的問題；品質標準見每日作業第 4-1 節。
- **總覽**：兩個排程的設定、提示詞與換帳號重建方式見 `docs/雲端排程/雲端排程總覽.md`。

## 0. 環境（與每日複核同一個雲端環境）

| 變數 | 用途 |
|---|---|
| `GOOGLE_SHEETS_SERVICE_ACCOUNT` | 服務帳戶金鑰（Base64 一行或整份 JSON） |
| `SPREADSHEET_ID` | 主資料試算表 |
| `REVIEW_LOG_ID` | 複核紀錄試算表（含「每週檢討」分頁，第一次執行時自動建立） |
| `GEMINI_API_KEY` | 填 `offline`。本排程不呼叫 Gemini；真實模型重播在 GitHub 工作流程裡跑 |

- 第一步安裝：`python -m pip install -q -r requirements.txt cryptography cffi pyyaml`（一定要用 `python -m pip`）。
- 網路與每日複核相同：`sheets.googleapis.com`、`oauth2.googleapis.com`、`www.googleapis.com`。推分支走雲端工作階段內建的 git 代理。

## 1. 取本週輸入包

```bash
python scripts/weekly_review/week.py fetch
```

- 讀複核紀錄（每日摘要、差異明細、近三週未處理的提示詞候選）。
- 讀主資料（本週網站現況、逐字稿判讀稽核）。
- 寫 `.weekly-review/<週五YYYYMMDD>/week.json` 與 `cases.md`。`cases.md` 已含「線上驗收」表：本週每一項明確錯誤，網站現在對不對。
- 「本週」是含今天的週一到週五。若由人手動在週末觸發，算剛過的那一週。

提早結束（不建分支）的兩種情況：

- **本週沒有交易日**：
  `python scripts/weekly_review/week.py log --stage 排程 --item 結論 --result 本週無交易日`
- **本週沒有差異明細、沒有未處理的提示詞候選，且線上驗收全部通過**：
  `python scripts/weekly_review/week.py log --stage 排程 --item 結論 --result 本週無需修改 --note "<一句說明>"`

## 3. 歸類每一個案例（cases.md 的每一列）

先自己判斷，再看流程怎麼判。原稿是唯一依據，網站不是答案。需要原稿時取那一天的輸入包：

```bash
python scripts/daily_review/fetch_day.py --date YYYY/MM/DD      # 不加 --hold；寫 .daily-review/<日期>/raw.txt 等
```

每一列歸到下面其中一類：

| 類 | 什麼時候 | 怎麼做 |
|---|---|---|
| A 已解決 | 線上驗收「通過」，或嚴重度是邊界／複核錯 | 不動；複核錯的模式寫進報告第 4 節（給每日複核作業的建議） |
| B 逐檔修正 | 明確錯誤，線上驗收「未通過」，且屬於每日作業第 6 步可以修的範圍（分類與說明、通知理由、①③章節、身分確定的股名聽錯） | 照每日作業第 6 步的格式寫那一天的修正計畫 `scripts/repairs/<日期>-source-review.json`（或 notice-reason／points-review），列進 plan.json 的 `repairs`。引句逐字出自那天的 raw.txt；`previous_note_sha256` 用網站現在的說明算。章節計畫整份取代兩章，推送前跑 `chapters.py check-plan` |
| C 改通用規則 | 同一類錯誤本週出現兩次以上，或提示詞候選近兩週達三次；而且流程違反的是**已經存在的裁示**或每日作業第 4-1 節的章節標準，原句清楚 | 第 4 步。章節類的成因通常在兩章的產生與補問（`SUMMARY_TOPUP_SYSTEM`、`LESSON_TOPUP_SYSTEM`、`ensure_min_lessons`、`dedupe_market_points`、`strip_macro_text` 等），先用 `grep -n` 找到實際呼叫路徑再改 |
| D 待管理者 | 裁示沒有直接規定的新邊界／新定義；要改 Apps Script 有對應片段的提示詞或名稱表；要加名稱別名 `CONFIRMED_NAMES`；牽涉成交事實、寄送帳本或其他週的資料 | 不改；寫成報告第 5 節的問卷（像 `docs/daily-review/觀望注意邊界問卷.md`：案例、原句、可選的寫法、你的初判） |

每一個 C、D 案例都要寫清楚四件事：

- 成因：`tuning.md` 第 1 節的哪一類。
- 最早分歧在哪一步：擷取、稽核、代號比對、問卷裁決、品質關卡或撰稿。
- 資訊缺口或定義缺口是什麼。
- 依據哪一條裁示。

## 4. 改通用規則（C 類，每週最多三條）

照 `stock-rule-tuning` 的順序：

1. 先找原文能確定的依據，寫成直接歸類。
2. 其次修句型或範圍。
3. 再來才是預設值。
4. 最後才動門檻。

不做的事：

- 為某一檔寫特例。
- 手動補列讓答案過關。
- 全面放寬門檻。
- 修改既有測試的期望值。守門會擋：既有 `scripts/test_*.py` 一個字都不能改。

步驟：

1. **改** `pipeline/pipeline.py`。改到裁決規則或問卷提示詞時，升 `VERDICT_VERSION` 的版號字串（格式 `vNN-YYYYMMDD-簡述`），讓舊快取失效。
2. **新增離線測試** `scripts/test_weekly_<YYYYMMDD>.py`：
   - 每條規則至少一個正例（本週原句）和一個反例（保留日或其他日子不該命中的原句）。
   - 原句前後加無關的填充句。
   - 寫法參考 `tuning.md` 第 7 節，並在 `scripts/run_offline_contracts.py` 的 `SUITES` 加上名稱。只准加，不准刪改別的。
3. **命中回測**（`tuning.md` 第 5 節）：
   - 對每個有答案檔的日期（`scripts/golden/`），用 `fetch_day.py --date` 取原稿。
   - 在本機用新規則的函式掃一遍，列出每一個命中的股票與它的答案分類。
   - 命中但答案不符，就是誤判，先收窄規則再往下走。命中清單寫進報告。
4. **答案檔**：
   - 本週要重播的日子，在 `scripts/golden/<日期>.json` 補上案例股票的 `must`／`must_not`，`why` 寫原句與依據的裁示。
   - 已有檔就只加不改。
   - 只放原句明確、合乎裁示的股票；可接受兩種結果的不列。
   - 新檔要有 `raw_sha256`（raw.txt 的 SHA256），以及 `_source`：「週檢討（雲端排程獨立判讀，非人工金標）」。
   - 兩章的回歸用三個鍵（推論後才評分，不送進模型）：
     - `chapter_min`：例 `{"macro": 3, "lessons": 3}`。
     - `chapter_required`：例 `[{"chapter": "macro", "topic": "量能1.11兆", "any_of": ["1.11兆"]}]`，`any_of` 用原稿的數字或專有名詞，不用語氣詞。
     - `chapter_must_not`：例 `[{"chapter": "lessons", "phrase": "已確認的錯誤說法"}]`。
     - 只加講者明講、本週確實漏掉或寫錯的主題；守門會擋刪改既有的章節答案。
5. **本機驗證**（雲端容器裡，不呼叫模型）：

```bash
python scripts/check_public_edit_batch.py
node scripts/check_gate_decision_contract.js
python scripts/run_offline_contracts.py
```

- 容器沒有 `node` 時略過第二支，工作流程會跑。
- 任何一支失敗：先修自己的改動，不改既有測試。修不好就放棄這條規則，改列 D 類。

6. **選重播日**：
   - 本週重播日：有案例、而且有答案檔的本週日期，1 到 3 天。
   - 保留日：至少兩天，從 `cases.md` 的「保留日候選」選最近的人工答案日。
   - 合計最多 6 天。
   - 只改了說明或修正計畫、沒改流程程式時，不必重播。

`docs/weekly-review/<YYYY-MM-DD 週五>/plan.json`：

```json
{
  "week_end": "2026/11/06",

  "changes": [
    {"cause": "語氣關鍵字", "rule": "大盤當主詞的讓步句不算本股負面", "ruling": "裁示紀錄 一-3（11/03 觀望邊界）",
     "earliest_divergence": "問卷裁決", "gap": "定義缺口：…",
     "cases": [{"date": "2026/11/04", "code": "2317", "quote": "原稿逐字"}],
     "tests": "scripts/test_weekly_20261106.py", "backtest_hits": "10/29 台積電（答案 holdings／watch_watch，符合）…"}

  "replay_days": ["2026/11/04"],
  "holdout_days": ["2026/11/03", "2026/10/29"],
  "repairs": [{"date": "2026/11/05", "file": "scripts/repairs/2026-11-05-source-review.json", "why": "鴻海仍未收錄，原句…"}],
  "questions": [{"title": "…", "cases": ["…"], "options": ["…"], "initial": "…"}]

```

`docs/weekly-review/<YYYY-MM-DD 週五>/報告.md`（公開 repo，給管理者與下一位 AI 看）依序寫：

1. **本週總結**：交易日、每日複核各嚴重度合計、線上驗收結果。
2. **改了哪些規則**：每條寫成因、最早分歧、缺口、依據的裁示，以及為什麼不是特例或放寬門檻。另附命中回測清單與新增的測試。
3. **逐檔修正**：日期、股票、網站原本、改成什麼、原句。
3-1. **①③章節品質**：本週每天兩章的點數、平均字數、機械疑點與語意問題，以及本週改了什麼、為什麼。
4. **給每日複核的建議**：複核錯的模式、每日作業哪一段寫得不清楚。只建議，不改 `docs/daily-review/`。
5. **待管理者裁示**：D 類，用問卷格式。
6. **下週要觀察的股票與句型**。

報告與計畫都**不得引用會員通知原文**。通知理由的修正只存舊句指紋。

## 6. 推分支（每週一次）

```bash
git checkout -b claude/pipeline-weekly-<YYYYMMDD>
git add pipeline/pipeline.py scripts/test_weekly_*.py scripts/run_offline_contracts.py scripts/golden/ scripts/repairs/ docs/weekly-review/
git commit -m "weekly(<YYYY/MM/DD>): <一句話>"
git push -u origin claude/pipeline-weekly-<YYYYMMDD>
python scripts/weekly_review/week.py log --stage 排程 --item 推送 --result 已推送 --note "<分支> <commit 前 9 碼> 規則 N 條、逐檔修正 N 項、待管理者 N 項"
```

- 推之前用守門自己先檢查一次：`python scripts/weekly_review/check_plan.py --base origin/main --branch claude/pipeline-weekly-<YYYYMMDD>`（先 `git fetch origin main`）。
- 不要把 `.weekly-review/`、`.daily-review/` 加進 git：原稿與會員通知不得進公開 repo。守門也會擋任何不在允許清單的檔案。

工作流程 `pipeline-weekly.yml` 收到推送後依序做：

| 步驟 | 內容 | 失敗時 |
|---|---|---|
| 守門 | `check_plan.py`：分支日期、允許的檔案、既有測試未改、答案檔只加不改、GAS 對應常數未變、重播日數 | 什麼都不做，只寫紀錄 |
| 離線契約 | 與單日重判相同的三支 | 不重播、不合併 |
| 重播 | 每個重播日與保留日跑 `replay_extract.py --fresh-verdicts --golden`（真實模型、唯讀、答案推論後才評分） | 不合併 |
| 逐檔修正 | `repairs` 的每一份計畫先預覽再套用（引句或舊說明指紋不符就不寫入） | 標套用失敗，不影響合併判斷以外的步驟 |
| 合併 | 以上全部通過，`--no-ff` 合併進 main，合併結果再跑一次離線契約後推送 | 標未合併 |
| 線上驗收 | `week.py verify`：本週每一項明確錯誤，網站現在對不對 | 寫進紀錄 |
| 紀錄 | 複核紀錄「每週檢討」分頁寫每一步結果與「結論」；差異明細中線上驗收通過的明確錯誤，處理欄標「週檢討確認已正確」；有改成規則的案例標「是否轉成規則或測試＝是（分支）」 | — |

## 7. 等結果、寫摘要

```bash
python scripts/weekly_review/week.py wait --minutes 100 --after "<推送的時間 YYYY/MM/DD HH:MM:SS>"
```

- **印出 `WORKFLOW_DONE`**：照它的結論寫最後摘要。
- **結束代碼 6（`WORKFLOW_PENDING`）**：寫「工作流程仍在執行，結果會寫在每週檢討分頁」後結束。
- **守門或離線契約沒過，而且原因是自己的改動**（例如漏登記測試、檔名錯）：可以在同一分支修一次再推。最多一次。
- **重播沒過**：工作流程會先用 main 的程式重播同一天、同一份答案做對照（2026/11/06 起）。分支的每一項不符 main 也有、通用錯誤不比 main 多，就算既有問題，不擋合併，紀錄寫「通過（與 main 相同的既有不符）」。只有本次新增的不符才擋。真的沒過時：不重推、不重跑，寫進報告摘要，下週再處理。
- **工作流程因暫時性錯誤中斷**（備份鎖忙碌、網路、Apps Script 逾時，日誌沒有任何重播或守門的 ✗）：可以在同一分支推一個空提交重跑一次（`git commit --allow-empty -m "weekly: 重跑"`），算在每週兩次推送內。同一份原稿重跑出不同錯誤時，照 `tuning.md` 第 6 節停止重跑。

## 用量與停止條件

- **用量**：本排程不呼叫 Gemini。工作流程的重播每天約數十次請求（看日誌的「實際模型HTTP」），6 天以內。
  - 週五 17:00 在太平洋時間午夜（台北 16:00，日光節約時 15:00）之後，用的是新一天的額度。
  - 隔週一早上的主流程還有完整的額度。
- **讀檔範圍**：只讀這裡列出的檔案與案例日期的原稿。不全庫搜尋，不讀 `pipeline/pipeline.py` 全文：用 `grep -n` 找相關函式，只讀那一段。
- **一週上限**：最多 3 條規則、最多 6 個重播日、最多推兩次。
