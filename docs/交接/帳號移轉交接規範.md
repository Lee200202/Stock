給接手的 AI 與管理者。這份是**入口與清單**。細節以 repo 內的正本為準，這裡只說去哪裡看、照什麼順序做。

- 本檔放在公開 repo，**不寫任何密鑰、密碼、主資料試算表 ID 或訂閱者資料**，只寫名稱與位置。
- 接手時有兩種狀況：
  - 同一台電腦、同一個 Windows 使用者，只換 Claude 帳號：本機記憶與設定都還在，只要重建「雲端排程」與「雲端環境」（第四節）。

## 四、換 Claude 帳號時要重建的東西（最重要）

雲端排程與雲端環境綁在 claude.ai 帳號上，新帳號看不到、也不能沿用。照下列順序做：

1. **新帳號連 GitHub**：在 claude.ai 的 Claude Code 設定連 GitHub，授權存取 `Lee200202/Stock`，要能推分支（`daily-review/apply-*` 或 `claude/daily-review-apply-*`）。
2. **建立雲端環境**，名稱自訂：
   - 環境變數四個：
     - `GOOGLE_SHEETS_SERVICE_ACCOUNT`：服務帳戶金鑰。整份 JSON 原始位元組的 Base64 一行；不要經過 PowerShell 的 JSON 轉換，那樣會弄壞私鑰。
     - `SPREADSHEET_ID`
     - `REVIEW_LOG_ID`
     - `GEMINI_API_KEY=offline`
   - 網路允許（自訂網路）：`sheets.googleapis.com`、`oauth2.googleapis.com`、`www.googleapis.com`。GitHub 的拉取與推送走第 1 步的 GitHub 連線；推送被拒時，排程會改推 `claude/daily-review-apply-*`。
   - **金鑰由管理者自己貼**。接手的 AI 不讀、不搜尋、不轉貼金鑰檔。
3. **建立兩個雲端排程**：照 `docs/雲端排程/雲端排程總覽.md` 第一、五、六、七節的 cron、模型、工具、repo 與提示詞全文建立。
4. **停用舊帳號的排程**：新舊同時跑，會重複暫停寄信、重複推分支、重複合併。先停舊的，再啟用新的。
5. **驗收**：
   - 盤後（13:00 以後）手動觸發一次，看執行紀錄：取輸入包 → 讀裁示 → 凍結判讀 → 比對 → 寫紀錄。
   - 13:00 前手動跑會把當天設成「複核中」，讓郵件等待，所以要避開。
   - 金鑰報錯時，腳本只印結構（`scripts/daily_review/common.py` 的 `key_diagnostics`），照訊息請管理者重貼。
6. **用量**：雲端排程扣的是該帳號訂閱的用量。兩個都用 Opus 5.5、思考強度 high：每日一次約 6–20 分鐘，每週一次約 30–60 分鐘，另外最多等工作流程 100 分鐘。

**不在 Claude 帳號上、不必重建的**：
- GitHub Secrets／Variables。
- Apps Script 屬性與觸發器。
- Worker 設定。
- 主資料與複核紀錄試算表。

GitHub Secret `ANTHROPIC_API_KEY` 是主流程的 Claude 後備模型用的 **API 金鑰**（Console 帳號），和 claude.ai 訂閱是兩回事。換組織時由管理者另外換。

## 六、部署規範（摘要；完整步驟在 `release.md`）

### 6.1 GitHub
- 先 `git fetch`。另一個工作階段（Codex）可能共用同一個工作目錄：用 worktree，不要 `git stash` 或還原別人的檔案。只 stage 本輪檔案。
- 推 main 會觸發 `offline-contracts`（離線契約測試）與 `public-site-pages`。推送前先跑 `python scripts/run_offline_contracts.py`，全部通過才推。
- commit 訊息結尾加協作者標記（依當時的指示）。

### 6.2 Apps Script
1. 建新的暫存目錄 `scratch/clasp/headNNN`，複製 `.clasp.json`，`clasp pull` 取 HEAD。
2. 和 main 逐檔比對：repo 的 `.gs` 在編輯器是 `.js`；`MailService`、`SheetService` 在編輯器是小寫的 `Mailservice`、`Sheetservice`。編輯器多出來的 Editor、Review、Versionlog 等檔案要保留。
3. 只複製本輪改的檔案，`clasp push -f`，再 `clasp create-version "說明"`，記下版本號。
4. 改了 `GAS_BUILD` 要同步 `Setup.gs` 的 `PROJECT_BUILD_`，跑 `node scripts/check_project_manifest.cjs`。`PROJECT_FILES_` 的 names 必須都還在檔案裡，否則編輯器的「專案檔案檢查」會誤報（11/03 的 `PIPE_RECLASSIFY_SYSTEM` 就是這樣）。
5. **正式 `/exec` 只能由擁有者切換**：「管理部署作業 → 編輯 → 新版本」。切完讀 `/exec?action=ping` 的 `build`。
6. 定時觸發器跑 HEAD，網站刷新與後台按鈕跑 `/exec`。兩者版本不同時要講清楚。
7. 一般更新不要執行 `installTriggers()`。

### 6.3 Worker 與 Pages
- Worker 部署、snapshot 與快取的判讀見 `release.md` 第 4 節。
- 讀回時看回應標頭 `X-Cache`、`X-Snapshot-Age`、`X-Snapshot-Content-Age`。郵件查詢內容可能落後數十分鐘，不能當成寫入失敗。

### 6.4 正式資料寫入（授權規則）
- **預覽可以自己跑；寫入正式資料要管理者在對話裡點名那一天、那一次**。範圍包括：
  - `regenerate-verified.yml` 的 `apply`／`source-review-apply`
  - `day-sync.yml`
  - 推修正分支觸發的套用
- 權限檢查擋下時照實回報，不換方式繞過。
- 只修當天確認的錯誤，不大量改寫歷史日期。
- 不重寄 Email／LINE，不重設已寄旗標，不動寄送帳本。
- 分類問題要改通用規則：加離線測試，用重播驗證，包括沒拿來調規則的日子。不寫特定股名的特例。

## 七、檔案格式規範（接手 AI 寫計畫檔時照這些格式）

所有計畫檔放 `scripts/repairs/<YYYY-MM-DD>-<種類>.json`，引句要**逐字**出自當天原稿（容許標點、空白差異）。

| 種類 | 工具 | 主要欄位 | 用途 |
|---|---|---|---|
| `source-review` | `scripts/apply_source_review.py` | `date`、`video_id`、`raw_sha256`、`authorization`、`review_basis`、`items[]`：`code`、`name`、`category`（buy／sell／holdings／watch_watch／watch_avoid）、`previous_category`、`action`（update／insert／delete）、`text`、`quotes`、`rationale`、`previous_source_id`、`previous_note_sha256` | 改某一檔的分類與說明 |
| `notice-reason` | `scripts/apply_notice_reason_fix.py` | `items[]`：`code`、`notice_source_id`、`article_id`、`previous_reason_sha256`、`previous_reason_chars`、`text`、`quotes`、`rationale` | 會員通知產生的買賣列理由；**舊句只存指紋，不寫原文** |
| `points-review` | `scripts/apply_reviewed_points.py` | `date`、`video_id`、`authorization`、`public_points_review.sha256`（＝原稿 SHA-256）、`headline`、`points[]`：`kind`（盤勢 level／volume／event／flow，教學 view）、`text`、`quotes` | 郵件①盤勢與③教學。**整份取代兩章**，原本正確的點要一起放進來；推送前跑 `python scripts/daily_review/chapters.py check-plan <計畫> <raw.txt>`。範例：`scripts/repairs/2026-11-06-points-review.json` |
| `name-memo` | `scripts/daily_review/name_memo.py` | `items[]`：`heard`、`code`、`name`、`keys`（情境詞）、`why`、`quotes`（要含唸的名稱） | 股名學習：寫進「名稱判定紀錄」，來源「複核」 |

- `previous_note_sha256`＝網站目前那一列說明的 SHA-256。可從公開 API `apiGetDashboard` 取文字計算，套用前的預覽會再核對一次。
- 答案參考檔 `scripts/golden/<日期>.json`：`raw_sha256`、`names`、`must`（代號 → 可接受分類）、`must_not`、`why`；2026/11/06 起另有兩章的 `chapter_min`、`chapter_required`、`chapter_must_not`（見 `scripts/golden/README.md`）。只在推論後評分，**不得灌入模型**。
- 每週檢討的計畫 `docs/weekly-review/<YYYY-MM-DD 週五>/plan.json`：`week_end`、`summary`、`changes[]`（`cause`、`rule`、`ruling`、`cases`…）、`replay_days`、`holdout_days`、`repairs`、`questions`。格式見 `docs/weekly-review/每週流程檢討作業.md` 第 5 節，守門規則見 `scripts/weekly_review/check_plan.py` 檔頭。

**每日複核的中間檔**：在 `.daily-review/<日期>/`，已列入 `.gitignore`，含原稿與會員通知，**絕不提交**。
- `reading.json`、`judged.json` 的欄位見 `scripts/daily_review/freeze_reading.py`、`write_log.py` 檔頭。2026/11/06 起 `reading.json` 必須有 `chapters.macro`／`chapters.lessons`（自己整理的兩章主題，原句要在 raw.txt），否則不能凍結。
- `diffs[].action` 只能填：待套用、待管理者、只記錄。

**主資料分頁**（欄位以表頭為準，程式依欄名讀寫，不依欄位順序）：
- 操作紀錄：日期、股票名稱、代號、方向、價位說明、理由摘錄、來源影片ID、序
- 會員持股：日期、股票名稱、代號、目前立場、說明重點、來源影片ID
- 影片清單（原始／修飾後逐字稿）、會員簡訊（含「解析明細」JSON）、每日推播內容（文字稿、寄送狀態）
- 修正建議（修正收據）、名稱判定紀錄、系統狀態、每日績效、持股追蹤（回合JSON）、日K快取
- 寄送帳本、使用者訂閱清單

**複核紀錄試算表分頁**：
- 每日摘要、差異明細、通知、提示詞候選：表頭定義在 `scripts/daily_review/common.py` 的 `LOG_TABS`。
- 每週檢討：`scripts/weekly_review/week.py` 的 `WEEK_HEAD`，第一次執行時自動建立。

## 八、安全與隱私（不可違反）

- 不輸入管理密鑰、Google 密碼或任何金鑰到網頁欄位，不讀、不搜尋本機金鑰檔。後台由管理者自己登入。
- 公開 repo、公開說明、日報、計畫檔都**不得出現會員通知原文**。網站上只顯示分類，不提簡訊、盤中通知這類通道字眼。
- **主資料試算表目前是「知道連結的人可檢視」**，而它含有「使用者訂閱清單」（Email、取消訂閱權杖）與「寄送帳本」（收件者）。建議管理者改成只限指定帳號。改了以後，用 gviz 公開讀取的檢查要改走服務帳戶。
- 服務帳戶金鑰、後台密碼曾在對話中出現過，建議定期輪替。
- 只用設計好的通知管道寄信：複核結果併入 12:30 狀態信，不另外寄測試信給訂閱者。

## 九、常見陷阱（已經發生過）

- Git Bash 的 heredoc 會吃掉反斜線：含 `\n`、正規式的修補用 Write 工具寫成檔案再執行。
- 簡訊整篇重新解析會重寫該篇所有列：複核修正的理由要帶 `reviewed` 標記才不會被蓋回（11/03 晶心科）。
- 部分重算績效只重算起點之後，起點前的舊列原樣保留：要補整條曲線用 `day-sync.yml` 的 `performance` 模式。
- gviz CSV 讀混合型別欄位（代號、日期）會變空或變序號（46329＝2026/11/03）。
- GitHub `schedule` 常晚數小時，準時的是 Apps Script 派的 `workflow_dispatch`。
- 模型每次判讀不同：驗收要看每一檔，同一天可多跑，但先算 Gemini 用量（每分鐘 15 次、每天 500 次）。管理者要求失敗的單檔單獨處理，不重跑整天。
- 「力致」這種本身是真公司名的聽錯，只能帶情境詞記，不能做全域別名。
- **同一天第二輪修正**（11/06 實例）：下午第二輪複核推到上午同名的 `daily-review/apply-<日期>` 分支，工作流程把分支上上午的章節計畫又套了一次，蓋掉下午另外核對過的兩章。現在 `daily-review-apply.yml` 只套用這次推送改到的計畫檔；新分支的第一次推送仍全部套用。
- **章節修正會整份取代**：`points-review` 只放新增的點，會把原本正確的點刪掉。原本的點要一起列進計畫。
- **講者的說法不等於事實**：11/06 講者說國巨「一張不是1,000股」，與實際交易單位不符。公開文字改寫成「一拆四後換算回拆分前的價格」，並用「講者指出」標明是誰的說法。
- **公開呈現會刪「講者」主詞**：計畫寫「講者以國巨為例」，網站顯示「以國巨為例」。這是 `public_narrative` 的既有清理，不是寫入失敗。
- **gviz 讀表會合併表頭**：用 gviz CSV 讀「每日推播內容」「影片清單」時，第一列表頭會和前幾列資料合併成一格。找當天的列要比對第一欄日期，不能直接用表頭名稱對應。
- **提示詞有兩份**：雲端排程的提示詞同時存在 `docs/雲端排程/雲端排程總覽.md` 與雲端排程本身。只改一邊，重建時就會拿到舊版。
- **觸發正式寫入要管理者點頭**：從 Claude Code 用 REST 觸發「單日品質核對」等正式寫入的工作流程時，自動權限可能擋下。照規定先停下說明，由管理者同意或自己執行，不要繞過。

## 十、交接時接手 AI 要回報的格式

1. **讀過的文件**：第一節的清單逐項打勾。
2. **系統現況表**：

   | 元件 | 版本或狀態 | 證據 |
   |---|---|---|
   | GitHub main | 最新 commit | `git log` |
   | Apps Script | HEAD、最新版本號、`/exec` 的 build | `clasp pull` 比對、`/exec?action=ping` |
   | Pages | 最新建置 | `pages/builds/latest` |
   | 雲端排程 | `enabled`、`next_run_at`、最近一次結果 | 排程頁面 |
   | 工作流程 | 全部 `active` | Actions API |
   | 今日資料 | 逐字稿、每日資料流程、寄送狀態 | 系統狀態、`apiGetDashboard` |

3. **與這份文件不符的地方**：列出差異與依據，不要自行假設文件是對的。
4. **待管理者決定的事項**：例如正式部署切換、權限、金鑰輪替。
