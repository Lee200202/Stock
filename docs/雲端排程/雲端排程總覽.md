# 盤勢有據：雲端排程總覽與重建手冊（2026/11/06）

給管理者與接手的 AI。目前在 Claude 雲端（claude.ai 的 Routine）上有**兩個**固定排程（另有 2026/11/08 新增、由 LINE 觸發的 ③ 管理者裁示，見第六之一節），本檔把它們的用途、設定、提示詞全文、權限、相依的 GitHub 工作流程、驗收方式與換帳號重建步驟放在一起。

- 接手時先讀完本檔，再讀兩份作業步驟：
  - `docs/daily-review/每日複核作業.md`
  - `docs/weekly-review/每週流程檢討作業.md`
- 各自的提示詞只放啟動條件、授權範圍與禁止事項，步驟細節寫在作業步驟。
- 本檔在公開 repo：**不寫任何金鑰、密碼、試算表 ID 或訂閱者資料**，只寫名稱與位置。
- 沒有本機檔案的電腦怎麼操作、回本機怎麼對齊雲端產出、換帳號／環境／金鑰後的銜接驗收清單：技能 `stock-cloud-sync`（`docs/stock-skills/skills/stock-cloud-sync/`）與唯讀腳本 `scripts/cloud_sync_status.py`。
- 改任何一個排程的提示詞或設定時，本檔與雲端上的排程要一起改。舊檔 `docs/daily-review/雲端排程設定.md` 已併入本檔，只留指向本檔的說明。

### 兩者怎麼分工

- **每日**：當天 11:40 在寄信前讀原稿、獨立判讀、比對網站，當天的明確錯誤當天修好。它只改資料，不改規則。看到同類錯誤反覆出現時，寫進「提示詞候選」。
  - 2026/11/06 起，複核範圍除了個股分類與說明，還包括郵件 ①盤勢總覽、③教學重點兩章：
    - 判讀時先自己整理兩章的主題並凍結。
    - `compare_site.py` 列出網站兩章與機械疑點（空白、點數不足、數字不在原稿、過短）。
    - 幻覺、漏主題、說明不清由 AI 判斷。
    - 明確錯誤用 `points-review` 計畫整份改寫兩章；推送前先跑 `chapters.py check-plan`。
- **每週**：把一週的錯誤、邊界、提示詞候選、流程自己的疑點（逐字稿判讀稽核）集中起來，找出成因，改通用規則，讓同一類錯誤不再發生。
  - 每日沒修好的明確錯誤（修正失敗、當時要等管理者但已有裁示），這裡逐檔補修。
  - 最後在線上逐項驗收本週每一項明確錯誤。
  - 遇到新邊界或新定義，不自己訂，寫成問卷給管理者。
  - ①③章節反覆出現同類問題時，改兩章的產生程式。答案檔用 `chapter_min`／`chapter_required`／`chapter_must_not` 做重播回歸。

## 二、共用的雲端環境

雲端環境綁在 claude.ai 帳號上。兩個排程用同一個環境；2026/11/08 在新帳號上重建時，兩個排程掛在該帳號的預設環境 `env_01X4SvVCY2ay8MWd89N6isj6`（Default）。之後若另建專用環境，兩個排程的 `environment_id` 與本行一起改。舊帳號的環境 `env_015X8iuk14WfXYWmDvt3N1Ck` 已停用。

| 環境變數 | 內容 | 誰填 |
|---|---|---|
| `GOOGLE_SHEETS_SERVICE_ACCOUNT` | 服務帳戶金鑰：整份 JSON 原始位元組的 Base64 一行（PowerShell：`[Convert]::ToBase64String([IO.File]::ReadAllBytes("金鑰.json"))`）。不要先轉成 JSON 物件再輸出，那樣會弄壞私鑰 | 管理者 |
| `SPREADSHEET_ID` | 主資料試算表 ID（與 GitHub Secret 相同） | 管理者 |
| `REVIEW_LOG_ID` | 複核紀錄試算表 ID（與 repo 變數 `REVIEW_LOG_ID` 相同） | 管理者 |
| `GEMINI_API_KEY` | `offline`（兩個排程都不呼叫 Gemini，只為了讓主流程模組能載入） | 管理者 |

- **網路**：自訂，允許 `sheets.googleapis.com`、`oauth2.googleapis.com`、`www.googleapis.com`。GitHub 的拉取與推送走 claude.ai 的 GitHub 連線（git 代理）。
- **套件**：容器的 `pip` 指向另一個 Python 版本，所以一律用 `python -m pip install -q -r requirements.txt cryptography cffi`（每週另加 `pyyaml`）。
- **金鑰診斷**：金鑰讀不了時，腳本只印結構（`scripts/daily_review/common.py` 的 `key_diagnostics`）。排程照訊息停止並回報，不自行檢查金鑰內容。**接手的 AI 不讀、不搜尋、不轉貼金鑰檔**，金鑰由管理者自己貼。
- **服務帳戶權限**：主資料與複核紀錄兩份試算表都要分享給服務帳戶（編輯者）。

- 每日：`待套用`→`已修正`／`修正失敗`、`待管理者`、`只記錄`。
- 每週：`週檢討確認已正確`。只寫在本週、嚴重度是明確錯誤、而且線上驗收通過的列。

## 五、① 每日寄信前複核

### 時間線（交易日，台北）

1. 約 11:05：抓逐字稿。約 11:14：每日資料流程寫入當天資料並刷新網站。
2. **11:40**：排程啟動，執行 `fetch_day.py --hold`，把當天設成「複核中」，郵件與 LINE 每日總覽開始等待。
3. 讀裁示 → 讀原稿獨立判讀 → 凍結判讀（之後不得改）→ 才讀網站比對 → 判斷每一項差異 → `write_log.py`。
4. 有明確錯誤：寫修正計畫、推 `daily-review/apply-YYYYMMDD`。`daily-review-apply.yml` 依序預覽、套用、讀回、標「已修正」，並把確認的股名寫進主資料「名稱判定紀錄」。
5. 12:30 起：「爬取狀態」信附複核卡片。郵件最晚等到 13:00 放行。

### 授權（管理者 2026/11/03）

- 試行期提前結束：明確錯誤當天就修。
- 股名聽錯且身分確定時直接修，並寫股名學習計畫。只有真的不確定才列待確認。
- 修正只走既有修正工具，不碰後台網頁、不用管理密碼。

## 六、② 每週流程檢討

### 時間線（每週五，台北）

1. **17:00**：排程啟動，執行 `week.py fetch`，取本週（週一到週五）的每日摘要、差異明細、近三週未處理的提示詞候選、逐字稿判讀稽核，以及網站現況。同時做第一次線上驗收。
2. 讀裁示與 `stock-rule-tuning` 方法。每個案例歸成 A 已解決、B 逐檔修正、C 改通用規則、D 待管理者。
3. C 類：
   - 改 `pipeline/pipeline.py`（通用規則，不寫股名特例）。
   - 新增離線測試、做命中回測、補本週答案檔。
   - 在容器裡跑完離線契約。
4. 寫 `docs/weekly-review/<週五>/plan.json` 與 `報告.md`，推 `claude/pipeline-weekly-YYYYMMDD`。
5. `pipeline-weekly.yml` 依序執行：
   1. 守門。
   2. 離線契約。
   3. 真實模型重播：本週重播日＋至少兩個保留日，最多 6 天，停用裁決快取，答案只在推論後評分。
   4. 逐檔修正。
   5. 以上全部通過才合併 main。
   6. 線上驗收。
   7. 寫「每週檢討」。
6. 排程用 `week.py wait` 等結論，最多 100 分鐘，再輸出摘要。
7. 合併後，下週一 11:14 的每日資料流程就用新規則。

### 守門擋什麼（`scripts/weekly_review/check_plan.py`）
